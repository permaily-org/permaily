# 0029 The operator's scripts send the token and secrets only to the attested key

Status: Accepted.
Date: 2026-11-15

## Context

The operator's scripts (`scripts/provider.sh`, `accounts.sh`, `invite.sh`, `handoff.sh` and `sigstore-trust-root.sh --send`) send the admin token with every request, and `provider.sh set` also sends a provider's client secret. They did it with a plain curl: the CA and the hostname checked, nothing else. `scripts/verify.sh` was to be run first, but on another connection, so it proved nothing about the one that carried the secret: someone with another valid certificate for `api.permaily.com` (a CA made to issue one, or one from before the enclave's key existed) and a place on the network would have received the token or the secret. The verifier already binds what it reads from `/status` to the key it attested, for the same reason (docs/verification.md).

## Options

1. **Keep "verify first" as an instruction.** Nothing ties the two connections together; the operator's own step is the gap.
2. **Each script verifies, in the same run, and pins the key it attested.** It runs `permaily-verify -json` against the enclave, takes the `tls_spki_sha256` of the host it verified, and sends every request with `curl --pinnedpubkey sha256//<base64>`, the CA and hostname checks kept. A server with another key ends the TLS handshake before curl sends the request.
3. **Send through the verifier itself.** A Go command that attests and then makes the request on the same connection. Stronger by a little (one connection), but every script would change into Go, and the key does not change between connections anyway: it is sealed, kept across restarts, and Certificate Transparency is watched for any other.

## Decision

2. The shared part is `scripts/attested.sh`, sourced by the scripts: `attest` runs the verifier and sets the pin, `enclave_curl` is the only way a script reaches the enclave with the token, and `enclave_error` prints only `error.message` of an answer.

- **Nothing is sent before the enclave verifies.** The scripts need the measurements to verify against: `PERMAILY_PCRS` (the `pcrs.json` of the running release, from `scripts/release-image.sh` or a rebuild) or `PERMAILY_RELEASE` (its tag, which trusts CI: the release's `pcrs.json` is downloaded once and authenticated by its build provenance, `release_pcrs` below, and that very file is what the verifier checks, with `-pcrs`; never `-release`, which would download it again after the check, and what a second download brings is what nothing authenticated: the release's asset replaced in between would make the verifier accept another image). `PERMAILY_PCRS`, when given, is what is checked. `handoff.sh` verifies against the `pcrs.json` of `<running>`, checked against its build provenance for a tag. Without them, or when the verifier fails on anything, the script stops and says nothing was sent.
- **`PERMAILY_API` is an origin, read with a deliberately narrow grammar**, the same in both modes and before either is chosen: `https://<host>` or `https://<host>:<port>` (1 to 65535, no leading zero), with or without a `/` at the end. The host is a lowercase DNS name whose last label starts with a letter, a dotted IPv4 address or `[::1]`. A user or password before `@`, a path, query or fragment, percent-encoding, upper case, a trailing dot and other IP spellings are refused, and the value is not printed (it may hold a password). curl, the verifier and the check must read the same host: the first version took the text before the first colon for it, and `https://localhost:x@api.permaily.com` passed the dev check while curl connected to `api.permaily.com`.
- **The verifier is the running release's.** `permaily-verify` checks the Sigstore trust root the enclave reports against the one compiled into itself (`checkSigstore`): one built from a later source, with a later trust root, refuses an older release that is right, before and after that release was given the later trust root in place, which is when `handoff.sh` and `sigstore-trust-root.sh --send` are needed. So when the release is named (`PERMAILY_RELEASE`, or the `<running>` tag of `handoff.sh`), the scripts build `permaily-verify` from that release's source with go, in a private repository in the run's temporary directory, removed after: reproducible from source, no downloaded binary. `handoff.sh` passes that one binary to the `sigstore-trust-root.sh --send` it runs, which uses it also to decide about the trust root. `PERMAILY_VERIFY`, when given, is used as it is.
- **The verifier's source is never taken from a tag's name.** The verifier decides which key the secrets go to: code built from a tag that someone moved, a tag already cached here, or the tag of a fork that is `origin` can print success with an impostor's key, whatever the PCRs. A tag is a name anyone with the repository, or with the clone, can point elsewhere; building from source does not authenticate the source. So, before anything is built, `release_pcrs` (in `scripts/attested.sh`, the one path every script and `handoff.sh`'s measurements take) downloads the release's `pcrs.json` and authenticates it with `gh attestation verify`, constrained to the repository `permaily-org/permaily`, the release workflow, `refs/heads/main` and GitHub-hosted runners. It takes the source commit from the verified attestation (`sourceRepositoryDigest` of the certificate), requires the release's tag at `github.com/permaily-org/permaily` to name that same commit (the release workflow tags the commit it built), and builds that commit id, fetched by its id from `https://github.com/permaily-org/permaily` (never from `origin` or from the clone, and nothing is read or written in the clone). The log names the full commit. Without `gh`, offline, or for a tag with no release or no matching provenance, nothing is built or sent: the script says to set `PERMAILY_VERIFY` to a verifier the operator trusts as that release's.
- **What is compiled is exactly that commit's tree.** A commit id says nothing by itself about what git reads for it: in the clone, a replacement ref (`git replace`) makes the authenticated id read as another commit's tree, while `rev-parse HEAD` and `git status` still say the id and a clean checkout; `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` and `GIT_CONFIG_*` can point git at other objects or configuration, and hooks, filters and attributes files run or change content on checkout. And go compiles more than the files: `GOFLAGS` (`-overlay`, `-modfile`, `-toolexec`) from the environment or a `go.env` file, and a `go.work` above the directory. So the commit is fetched by its id from the repository, one commit without history, into a new repository in the run's temporary directory (`git init --template=`: no hook) and checked out there. Every git call drops each `GIT_*` variable of the environment and runs with replacement objects off (`--no-replace-objects` and `GIT_NO_REPLACE_OBJECTS=1`), hooks off (`core.hooksPath=/dev/null`) and no prompt; the `init`, the checkout and the check of `HEAD` also read no configuration file (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`, `core.attributesFile=/dev/null`). Only the fetch and `ls-remote` read the operator's configuration files (a proxy, a mirror under `insteadOf`): what the fetch brings is checked against its object id, so they can make it fail, not change it. It is a checkout and not `git archive`: the files are what a checkout of the commit writes, its own `.gitattributes` applied and nothing else, as in the release workflow; `git archive` would also apply `export-ignore` and `export-subst`, which a checkout does not. No filter runs, since no configuration defines one. Then `go build -modcacherw -trimpath -buildvcs=false` runs with every `GO*` and `CGO_*` variable dropped but `GOTMPDIR` and `GOPROXY` (the commit's `go.sum` checks every module it downloads, whatever the proxy), with a new, empty module cache and build cache inside the run's temporary directory (go compiles a module already extracted in a cache, and reuses a build result, without hashing it again, so an operator's cache altered after its download would be compiled as it is; the review of pull request #113 showed it), and with `GOENV=off` (no `go.env` file, so no `GOFLAGS` from anywhere), `GOWORK=off`, `CGO_ENABLED=0` (as the release builds it) and `GOTOOLCHAIN=auto`: the module's toolchain policy applies, so a go older than `go.mod`'s `toolchain` line downloads that toolchain, which go checks against the checksum database (the operator's `GOSUMDB`, `GONOSUMDB`, `GOPRIVATE` and `GOINSECURE` are dropped with the rest). This defends against configuration and repository state, not against a compromised go, git or computer: the toolchain, git and the operating system they run on are trusted, as the operator's computer is.
- **With only `PERMAILY_PCRS`** (a staging image built from a branch has no release) the verifier is built from the checkout, with a warning. That is an extra assumption, not a check: the scripts do not establish that the checkout is the source of the measured image, and its code is built as it is, uncommitted changes included, so the operator trusts the checkout as they would a `PERMAILY_VERIFY` they give. A trusted but incompatible verifier (a later release's, for example) fails closed: it refuses, and nothing is sent. Arbitrary code in the checkout does not fail closed; trusting it is the assumption. Refusing outright would cost staging rehearsals, and the operator who can change the checkout can as well set `PERMAILY_VERIFY`, so it adds no safety there.
- **Dev mode** has no attestation to verify. `PERMAILY_DEV_UNVERIFIED=1`, and only the literal `1` (any other value, `0` and `false` included, is refused), sends without verifying, and only to `localhost`, `127.0.0.1`, `[::1]`, a name under `.localhost` or under `.test` (RFC 6761: never in public DNS; the dev enclave serves `permaily.test`, docs/web.md). A reserved name is not an address, so the connection is forced to this machine as well: a name goes to `127.0.0.1` (`curl --resolve`, whatever DNS or a hosts file says), no proxy is used (`--noproxy '*'`, whatever `HTTPS_PROXY` or `ALL_PROXY` say), and TLS still checks the name.
- **curl** runs with `-q` (no `~/.curlrc`, which could turn a check off), `--proto =https`, `--max-redirs 0` and no `-L`, so a redirect is a failure; plain `http://` is refused before anything runs.
- **Nothing of the token or a secret is traced.** Under `bash -x`, the helper's functions that touch them (`load_token`, `read_secret`, `with_token`, `enclave_curl`, which makes the `Authorization` header) turn xtrace off while they run, and the scripts never expand the token themselves.
- **What an answer holds is not printed whole** after a request that carried the token or a secret: only fixed fields, without control characters, so an answer that echoes the request does not put it on the terminal.
- **Tests** (`scripts/operator-scripts.test.ts`) serve the same name with a second key from the same test CA: no request reaches it. Others refuse every malformed `PERMAILY_API` and every `PERMAILY_DEV_UNVERIFIED` but `1`, send dev requests through HTTP and SOCKS proxies and to a name DNS does not answer with loopback and see them reach only this machine, run the scripts under `bash -x` without the token or a secret in the trace, run a handoff from an older release with its own trust root and after a later one was given to it, fail if a script makes the token's header itself, and, with fixtures for `gh` and the repository, show that a tag moved at the repository and at `origin`, a hostile tag already here and a fork as `origin` neither run a tag's code nor send a request, that a replacement ref in the clone for the authenticated commit, `GIT_*` variables pointing at the clone's object store and at an index file, and `GOFLAGS` (an overlay), `GOWORK`, `GOENV` and the rest of the Go environment change nothing of what is built (the build's environment is checked), that a release's `pcrs.json` replaced after its provenance was verified is not downloaded again (the verifier gets the authenticated file), that no release or provenance builds nothing, and that a run stopped while it builds leaves no worktree registered. `TestTheVerifierMustBeTheRunningRelease` shows the same about the verifier with the real `checkSigstore` and Sigstore's real metadata.

## Consequences

- Each run verifies the enclave first: a few seconds, and network access to the enclave's `/attestation` and `/status`. A check that fails, even one unrelated to the token (the SES state, the KMS key's history), stops the operator's scripts until it is understood. That is on purpose: the token goes only to an enclave that verifies.
- The operator has to say which release runs. During a deployment, `handoff.sh` takes it from its own argument.
- Naming the release builds its verifier with go from the commit its build provenance names: that needs `gh`, git 2.32 or later (`GIT_CONFIG_GLOBAL`) and network access to GitHub (its release, its attestation and its tag, and the commit, fetched each run: one commit, a few megabytes), and the commit's Go toolchain and modules. Offline, the operator gives `PERMAILY_VERIFY`. With `PERMAILY_VERIFY` and `PERMAILY_RELEASE` but no `PERMAILY_PCRS`, `gh` is needed too, to authenticate the `pcrs.json` the verifier is given. The callers' EXIT trap (`attested_cleanup`) removes the run's temporary directory, the private repository with it; nothing is registered in the clone, so even a `SIGKILL` leaves only a directory under the system's temporary directory.
- `sigstore-trust-root.sh --send`, called by `handoff.sh`, verifies again against the same measurements, with the same verifier: two attestations and one build a handoff.
- Nothing changes in the image or in what the enclave accepts.
