# 0026 Mailboxes per account: how they are built

Status: Accepted. Designed on 2026-11-12 for step 2 of F2 (docs/plan.md); built by its six implementation pull requests: 0 to 4 merged on 2026-11-12 (#87, #91, #90, #88, #89), 5 in #92, released once the browser checks of docs/acceptance.md pass. The owner decided its open choices on 2026-11-12 (listed in "What it rests on, and what is left"), among them that messages are shown as HTML from the start ("Showing a message's HTML"). Revised the same day after three adversarial reviews of its core and one of its HTML; what each changed is listed in the pull request that carried it. No further review of the design is planned: each implementation pull request gets an adversarial review of its code.
Date: 2026-11-12

## Context

ADR 0018 decided what mailboxes are: forwarding only, several per account, nothing from before the forwarding started, retention as F1 has it, a full inbox in the app, disconnecting deletes the mail, and which account is behind a mailbox is verified for Gmail by Google's signed confirmation. This record says how, exactly enough that the store, the server, the web app and the operator's side can be built at the same time by different people against interfaces that are already in the repository (see "Implementation pull requests").

It builds on: the records that refuse an earlier copy, `store.Anchored` (ADR 0016), which it extends with strict records ("The store"); the patterns of accounts (ADR 0017): signed records changed only at the version read, pointers that prove nothing, sealed entries, limits; two enclaves at once (ADR 0017, ADR 0024); confirming again and the admins (ADR 0022); public logs (ADR 0015); mail only over TLS (ADR 0011). The F1 test mailbox (ADR 0009) is retired, not moved ("The test mailbox: retired").

The rules this design keeps, from the maintainer: nothing that decides anything lives only in one enclave's memory; the operator and admins can see that mailboxes exist and how many, and cannot read mail or enter an account; logs never hold an address, a subject, a sender, content, a token, or an account, mailbox or message identifier; whoever writes to the table or the bucket cannot read mail, move a mailbox to another account, make a disconnected mailbox accept mail again, or put a mailbox back to an earlier state where that matters; mail that a sender was told is delivered is stored.

Proportion, kept from the third review: none of the attacks on the store it found lets whoever writes to the storage read mail or move it to another account. What they allowed was making a mailbox its person disconnected (or a removed account's mailbox) accept and hold mail again, or an account exceed five. The fixes below are the smallest that make disconnection terminal, not a redesign of the store.

## Decision in short

- **A mailbox is an anchored record**, readable and signed, with a sealed part: who owns it, its state, when it started receiving, whether Google confirmed its Gmail account, its data key wrapped under the root secret, and sealed inside it the address and the Gmail account. What a person edits freely (the label, the retention) is a signed, versioned entry next to it that is not anchored.
- **An account's mailboxes are listed in one anchored record**, which also fences creation and removal: identifiers are reserved there, a record is made only where no commit was ever made for its name, and removing an account always leaves the list closed, made closed if there was none. The limit of five holds with any number of enclaves.
- **Both are strict records** ("The store"): a fork anywhere in a record's history, two commits of different digests at one version, makes every read and write of it fail, on every enclave and after every restart. What production already stores (accounts, the TLS identity, the providers' applications) is not strict and is read and written exactly as before.
- **An address finds its mailbox through a pointer** named by an HMAC of the address, holding only the mailbox's identifier. Ownership and state are read only from the record.
- **One random data key per mailbox**, never cached across requests. Disconnecting always ends in a terminal commit of the record before the slot is freed: from then on no request of any enclave opens the mailbox, and its mail is deleted by a sweep. That is a refusal enforced by approved code, not destruction proof against a later theft of the root secret ("What disconnecting does to the key").
- **Delivery never loses mail.** A message is claimed per mailbox before it is stored; the claim fixes its identifier, when it was received and when it expires, so a retry writes the same items; the parts are written so that the message becomes visible last; `250` only when every accepted mailbox holds it. Memory is taken as bytes arrive, and every phase of an SMTP session has an absolute deadline.
- **The inbox** lists, opens, deletes and searches one mailbox at a time, each page reading a bounded number of stored items, under a deadline from the request's start, and shows a message formatted in a sandboxed frame or as text.
- **The test mailbox is retired**: the release that builds this has no code that reads it, its token goes, and its address answers like any unknown one.
- **The operator and admins** see counts and the readable part of each record, never an address; they can pause and resume a mailbox, never disconnect or read it; an admin does so through the actor-bound admin facade of accounts.
- **A closing account** can read, search and download its mail and disconnect mailboxes; **an account that has not agreed to changed terms** can download its mail and disconnect mailboxes. The server enforces it route by route.

## Records and layout

All in the one DynamoDB table (`permaily-mail`), the mail bucket and the anchors bucket, as F1 and accounts are. "Signed" is `envelope.Sign` with a key derived from the root secret for mailboxes (`Derive("permaily mailboxes sign v1")`), bound to where the value is stored; "sealed" is `envelope.Seal` or `SealText` under the mailbox's data key, bound to the mailbox (and message) by `envelope.AAD`.

| What | Where | Treatment | Written how |
|---|---|---|---|
| A mailbox | Record `mailbox-<id>` (`pk=system`, `sk=record#mailbox-<id>@<version>-<hash>`), its commits in the anchors bucket | Signed, readable: `v`, `id`, `account`, `state` (`active`, `disconnecting`, `cancelled`), `rcpt` (the address's HMAC, hex), `created_at`, `receiving_since`, `verified_at`, `paused_at`, `state_changes` (times of the last ten pauses and resumes), `disconnected_at`, `disconnected_by` (`person`, `account_removed`). Sealed inside it as `sealed` (bound to `mailbox-private` and the id): the address, and the Gmail account Google confirmed. The data key, wrapped under the root secret, is the record's `WrappedKey` | `store.Anchored` with `Strict` and `OnlyNewest`: made with `CreateNew`, changed with `GetRecordAt` and `PutRecordAt`, ended with `RemoveRecord` ("State machines") |
| An account's mailboxes | Record `mailboxes-<account id>` | Signed: `{v, account, state: open or closed, mailboxes: [{id, rcpt, added_at}], made: [times of the last ten creations]}`, identifiers and HMACs only | Anchored, `Strict` and `OnlyNewest`: made with `CreateNew` (open by a first creation, closed by an account's removal), changed at the version read, never removed: a closed list stays, emptied of what left it |
| A mailbox's settings | Entry `pk=mailbox#<id>`, `sk=settings` | Signed with where it is stored: `{v, retention_days, label}`, the label sealed (`SealText`, bound to `mailbox-label` and the id) | `PutEntry` at version 0, then at the version read; absent means 90 days and no label |
| The pointer from an address | Entry `pk=rcpt#<hex HMAC-SHA-256 of the local part>`, `sk=mailbox` | Signed with where it is stored: `{mailbox, write}` (`write` random per write, as accounts' pointers) | `PutEntry` at version 0; deleted as it was read (`DeleteEntryAt`), found from the list's `rcpt` when the record cannot be read; never moved or rewritten |
| The index of mailboxes, for counts | Entry `pk=mailboxes`, `sk=<mailbox id>` | Signed: `{account}`. It proves nothing and is only counted | Written after the record is made; deleted when the record ends |
| A message (F1's format) | Item `pk=mailbox#<id>`, `sk=msg#<message id>`; raw in S3 `raw/<mailbox id>/<message id>`, tagged with its retention | Meta (`inbox.StoredMeta`) sealed (`message-meta`); raw sealed (`message-raw`); plain identifiers, sizes, times | Written by a delivery under what its claim fixed, raw first and the item last ("The claim, and the order of writes"). DynamoDB's TTL and the S3 lifecycle rule of its tag delete it |
| What search reads of a message | Entry `pk=mailbox#<id>`, `sk=txt#<message id>` | Sealed (`message-search`): `inbox.SearchEntry`, the senders, the subject, the first 16 KiB of the text, when it arrived | `PutEntry` at version 0 (`ErrExists` from an earlier try of the same delivery is success), before the item; the message's expiry |
| A delivery's claim, then its mark | Entry `pk=mailbox#<id>`, `sk=seen#<hex HMAC, under a key derived from the mailbox key, of the envelope sender and the SHA-256 of the raw message>` | Sealed (`message-seen`, bound to the mailbox and the entry's whole key): `inbox.SeenEntry`, `{stored, message, received_at, expires_at, retention_days, claimed_at, stored_at}` | Version 0 to claim; at the version read to take a stale claim over or to mark it stored; expires seven days after `received_at`, never renewed |
| A forwarding confirmation | Entry `pk=mailbox#<id>`, `sk=confirm#<message id>` | Sealed (`message-confirm`): `inbox.ConfirmEntry`, code, requester, when, verified, for another address, when it stops being shown | `PutEntry` at version 0, before the item; thirty days, read from the sealed `ends` |
| The mailboxes being disconnected | Entry `pk=mailboxes-disconnecting`, `sk=<disconnected_at, RFC 3339>#<mailbox id>` | Signed: `{mailbox}`. It proves nothing: the record does | Version 0, before the terminal commit, or by whoever finds a record `disconnecting` without one; deleted as it was read when nothing of the mailbox is left |

- **Identifiers.** A mailbox is `mbx_` and 26 base32 characters (16 random bytes), made as accounts make theirs, and never reused. Message identifiers stay F1's: 32 hex characters, time first, so an identifier says when its message arrived. `scrub` learns `mbx_`, and no message identifier goes in a log line or a logged error.
- **Why the record is readable and signed, with a sealed part.** The operator needs the state, the owner and the dates to give support and to count; none of it is the person's mail. The address is what lets anyone put mail into the person's inbox (and, from step 5, in front of their agents); the Gmail account is a second address of theirs; the label is typed by the person and may be anything. Those are sealed. ADR 0017's table listed the forwarding address as readable; this changes it.
- **Why the list holds `rcpt`.** The HMAC of the address is readable in the record already and says nothing of the address. Kept in the list too, it lets a disconnect delete the pointer of a mailbox whose record cannot be read.
- **Why a record of its own for the list**, not a field of the account's record: a mailbox's life has nothing to do with who gets into the account, and the account's record changes only through `change`, with the checks of sign-in. Kept apart, the mailboxes service never writes `accountDoc` and accounts never learn a mailbox's format.

**Rejected.** A pointer named by the address in plain text: the table would list every address. A scan of mailboxes at `RCPT TO`: the cost grows with the number of mailboxes. The address readable, as ADR 0017 listed it. The list as entries: an earlier copy put back would hide a mailbox from its person while it went on receiving. The label and retention in the anchored record: every rename would be a commit that can never be deleted ("What is anchored, and what is not").

## The address

- **Made of** twenty characters of `abcdefghijkmnpqrstuvwxyz23456789` (32 letters and digits, without `l`, `o`, `0` and `1`), drawn with `crypto/rand`, at `inbox.permaily.com`: 100 bits. `domain.NewMailboxAddress` makes one.
- **Collisions** are found by the pointer's write at version 0 (`ErrExists`). With a million mailboxes the chance of one is about one in 10^18; the creation then cancels its own reservation and answers an error ("Making a mailbox").
- **An address is a capability to send, never to read.** An ordinary mailbox's address is private: the person gives it only to Gmail, and knowing it lets anyone send mail to the mailbox and never lets anyone read it. The mailbox that receives TLS reports is the exception by design: its address is known to the operator and published in DNS (`_smtp._tls`), so anyone can send to it, and nobody but its account reads it ("The test mailbox: retired", TLS-RPT).
- **Guessing.** With a million mailboxes a made-up address finds one with a chance of one in 10^24, so `RCPT TO` is not limited per sender. Every refusal is the same `550 5.1.1 No such mailbox`: an address never made, one disconnected, one paused, one whose record cannot be read, one of another domain. An address that exists costs two reads more than one that does not, which tells only someone who guessed it already.
- **What is compared.** The local part, lowercased, at most 64 bytes; one with a `+tag` is refused (Gmail forwards to the exact address it was given). The domain must be the inbox host, compared without case.
- **The HMAC key** is `Derive("permaily mailbox addresses v1")` from the root secret: the same in every enclave of the deployment, unknown outside.
- **What the pointer says.** Only which mailbox. Whose it is and whether it accepts mail are read from the record, whose `rcpt` must be the HMAC the pointer is named by: a pointer copied under another name, or put back after a disconnect, leads to a record that refuses.

## Keys

- **One data key per mailbox**: 32 random bytes from `keys.Root.NewDataKey`, wrapped under the root secret with the context `{purpose: mailbox, mailbox: <id>}`. No KMS call: wrapping and unwrapping are AES-GCM under a key the enclave holds.
- **Not derived.** A key derived from the root secret and the identifier could not be taken away short of losing the root secret.
- **Not cached.** Every request that opens mail reads the record anyway (owner and state), and unwrapping costs microseconds, so the key is unwrapped from the record just read, put in the request's `inbox.Box`, and dropped with the request.

### What disconnecting does to the key, and what it does not

- **What it does.** Disconnecting writes the next version of the record without `WrappedKey`, at the version read; `OnlyNewest` then deletes the version before, which held it. When the mail is gone the record is removed (`RemoveRecord`): a commit says it is gone, and every stored version left is deleted. A record whose newest value was lost is removed at once. From the first of these commits on, every read of the record by any enclave of the deployment goes through the newest commit, which has no key or says the record is gone, so the approved code never unwraps that key again. An earlier copy of the record put back in the table is refused (ADR 0016). The wrapped key cannot be moved into another record: the wrap is bound to the mailbox identifier, and records are signed and committed.
- **What it does not.** It is a refusal enforced by the code of public releases, not cryptographic destruction. The wrapped key was in the table under the root secret: a saved copy of the table from before the disconnect, together with the root secret, decrypts a saved copy of the mail. The root secret exists only inside enclaves of public releases and in records locked by their KMS keys (ADR 0013), so that takes breaking an enclave or KMS; and every release whose KMS key still exists can open the root secret, so an old release with a flaw stays part of the boundary until its key is deleted (docs/operations.md, "Delete the key of an old release"). A request that unwrapped the key before the disconnect keeps it until its deadline (at most a minute, "Disconnecting"). A KMS key per mailbox would make destruction real, at the cost of a key per mailbox and seven days to delete one; not done.
- **What stays.** The anchored commits of the record and of the account's list: the record's name (which holds the mailbox identifier), versions, times, hashes and authentication codes, for the lock period: ten years in production, then S3 may delete them. Never a key, an address or a value of a record. A closed list stays as a record too ("An account's list").
- The app, the notice by mail, docs/data.md, docs/threat-model.md and ADR 0018 say exactly this and nothing stronger.

## State machines

Each machine says its states, the writes that move between them and how each is written: **create-only** (`CreateNew` for records, `PutEntry` at version 0 for entries), **at the version read** (`PutRecordAt` after `GetRecordAt`; `PutEntry` at the version read; `DeleteEntryAt` as read), or **removal** (`RemoveRecord`, which reads the record's history and never its value). Every write that fails because another enclave wrote first (`ErrChanged`, `ErrExists`, `ErrConflict`) reads again and decides again, four times at most, then fails. `ErrForked` is never retried: it does not pass. The fixed numbers of tries, and what running out of them answers: four for a change of the list, of the settings, of a record's state (pause, resume, disconnect) and of `receiving_since` or the confirmed source; two for a delivery's claim (then `ErrClaimed`); nine for an account's removal (`maxTries` plus `MaxMailboxes`). Running out is an error, never a state accepted as it is: the person's request answers 500 `internal` (and may be asked again), a delivery answers `451 4.3.0` (the sender retries), and the account's removal is tried again by the account's loop. Every retry is safe: each try reads again and decides again from what it read, and writes only at the version read.

### A mailbox's record

| From | To | When | Write |
|---|---|---|---|
| none | `active` | Making a mailbox, its identifier reserved in an open list | `CreateNew` |
| none | `cancelled` | A reader of the list found the identifier reserved more than ten minutes ago with no record, the creator itself gave it up, or the account is being removed | `CreateNew`: a tombstone `{account, state: cancelled, cancelled_at}`, no key |
| `active` | `active` | `verified_at` and the sealed Gmail account (once), `receiving_since` (once), `paused_at` set or cleared (ten in thirty days) | At the version read |
| `active` | `disconnecting` | The person disconnects, or the account is removed | At the version read: `disconnected_at`, `disconnected_by`, no key, no sealed part |
| `disconnecting`, `cancelled` | gone | Nothing of the mailbox is left (the sweep) | `RemoveRecord` |
| lost (`store.ErrLost`) | gone | The person disconnects it, or the account is removed | `RemoveRecord`, at once: it needs no value |
| forked (`store.ErrForked`) | (none) | Whoever writes to the bucket made two commits of different digests at one version | Nothing can be written: every read fails closed; shown as `unreadable` |

Because a record is made only with `CreateNew`, which fails wherever any commit of this deployment was ever made for its name, a removal included, nothing turns a cancelled or removed mailbox back into one that accepts mail. The fence of a reservation is the record itself: whoever cancels writes the tombstone, and the creator's own `CreateNew` then fails. Every way out of `active` that a person or a removal can take ends in a commit that no read gets past: `disconnecting`, then gone; or gone at once for a lost record. The one record that takes no commit is a forked one, and it accepts nothing either.

### An account's list

| From | To | When | Write |
|---|---|---|---|
| none | `open` | The first mailbox of the account | `CreateNew` |
| none | `closed` | The account is removed and never had a list | `CreateNew` |
| `open` | `open` | An identifier added (a reservation, with its `rcpt` and its time in `made`), or taken out (its record is `disconnecting`, `cancelled` or gone) | At the version read |
| `open` | `closed` | The account is being removed | At the version read; `made` emptied |
| `closed` | `closed` | Identifiers taken out as their records end | At the version read |

Nothing is added to a closed list, and a closed list is never removed: the record of a removed account is the closed list, naming the account and, at most, the identifiers of mailboxes whose records were forked, for good (docs/data.md). Creation reads the list at its version and writes it at that version, so a close that happens in between fails the creation's write, and the reread sees `closed`. A first creation and a removal race on `CreateNew`: whichever loses gets `ErrExists` and reads what the other made: the creation finds the list closed and answers `account_closing`; the removal finds it open, closes it at its version and goes on.

### An identifier in the list (a reservation)

| State | What it is | What any reader of the list does |
|---|---|---|
| reserved | In the list; no commit for `mailbox-<id>` | Counts it while younger than ten minutes; older, writes the tombstone (`CreateNew`; `ErrExists` means the record was made: read it) and takes the identifier out |
| active | The record is `active` | Counts it |
| lost | The record's newest value is gone | Counts it; shows it as `unreadable`; disconnecting it (or the account's removal) removes the record and frees the slot |
| forked | The record has a fork | Counts it; shows it as `unreadable`; nothing frees the slot ("An unreadable mailbox") |
| leaving | The record is `disconnecting`, `cancelled` or gone | Does not count it; puts the disconnect entry back for a `disconnecting` record that has none (create-only); takes the identifier out of the list at the version read |

"Any reader of the list" is listing the mailboxes, making one, disconnecting one, `Count`, `Records`, `RemoveAccount` and the sweep. The queue of disconnects is an optimisation: a slot is never counted for a mailbox that is leaving, whether or not its cleanup ran, and the next reader finishes it.

### Invariants, and why they hold

1. **Every `active` record's identifier is in an open list of its account.** A record is made only after its identifier is in the list (making, step 3), and an identifier leaves the list only when its record is `disconnecting`, `cancelled` or gone, or after the tombstone was written, which stops the record ever being `active`.
2. **An account never has more than five mailboxes that count**, with any number of enclaves: the count is made from the list and the records it names, and the new identifier is written at the version the count was made at.
3. **Nothing is added to an account being removed**: the list is closed at its version, or made closed, before its mailboxes are enumerated, and a reservation older than the close is fenced by a tombstone.
4. **From the commit of `disconnecting`, no new request opens the mailbox and no new mail is accepted for it**, on any enclave: every request and every delivery reads the record, and nothing caches it.
5. **A slot is never kept by a mailbox that is leaving**: it does not count, whatever its cleanup did.
6. **A slot is freed only after a terminal commit of its record**: `disconnecting`, a tombstone, or a removal. A forked record takes none and keeps its slot; a lost one is removed before its slot is freed.

### Making a mailbox

`POST mailboxes {label}`, by an account that is open and agreed (`Standing`).

1. Read `mailboxes-<account>` at its version (none: `CreateNew` it `open` and empty; `ErrExists`: read it again). `closed`: `account_closing`. Read the record of each identifier and do what the reservation table says. Ten creations in the last thirty days (`made`): `too_many_requests`. Five that count: `too_many_mailboxes`.
2. Draw the address and compute its `rcpt`.
3. Add `{id, rcpt, added_at}` and the time to `made` (the last ten kept), and write the list at the version read.
4. Write the pointer at version 0. `ErrExists` (another mailbox's address, one chance in 10^18): give the reservation up at once (the tombstone, then the identifier out of the list), answer an internal error.
5. `CreateNew` the record: `active`, the account, `rcpt`, a new data key, the sealed address. `ErrExists` means a reader cancelled the reservation (step 3 took longer than ten minutes): delete the pointer as written, answer an internal error; the identifier leaves the list with its tombstone.
6. Write the settings entry at version 0 (retention 90, the sealed label) and the index entry. A failure here leaves a mailbox with the default settings, shown in the list; the answer is an error and the person can rename it.
7. Send the notice "a mailbox was added". Answer 201.

A failure after 3 holds a slot for ten minutes; after 4 leaves a pointer to a record that does not exist, which refuses mail like no pointer and is never handed to anyone. Nothing half made receives mail or shows an address.

### Label and retention

`PATCH mailboxes/{id}`: the record is read (it must be `active` and the caller's), then the settings entry is read and written at its version, four tries, under the request's deadline. The label is one printable line of at most 64 characters (`domain.MailboxLabel`), may be empty, and is sealed. A new retention applies to mail first received afterwards: each message's expiry is fixed by its claim. Neither needs a fresh proof; both need an open, agreed account.

### Gmail's forwarding confirmation

What Gmail sends, from what the repository holds and from Google's message: `From: forwarding-noreply@google.com`, `To:` the forwarding address it was asked to use, `Subject: (#<code>) Gmail Forwarding Confirmation - Receive Mail from <requester>`, and a body that says the requester "has requested to automatically forward mail to your email address" (naming it, in Google's message), with the code and a link. Google signs it with DKIM for `google.com`. The repository's fixture (`internal/inbox/inbox_test.go`, `gmailConfirmation`) is written by hand: its body does not name the destination, and it carries no signature.

- **Recognised** at ingest when the message has exactly one `From` header, its address is exactly `forwarding-noreply@google.com`, and its subject or body carries a code. The envelope sender plays no part: nobody signs it. It is stored as a message of the inbox like any other, marked `confirmation`, and kept as a sealed `confirm#` entry for thirty days so the set-up shows the code without opening the inbox. A flood of fake confirmations writes no commit.
- **Verified** (`ConfirmEntry.Verified`) only when all of these hold: exactly one `From`, one `To` and one `Subject` header (a second of any refuses: a signature does not say which of two the parser read); the `From` address is exactly the forwarding service's; a DKIM signature with `d=google.com` passes, its `h=` covers `From`, `To` and `Subject`, and it has no `l=` (the whole body is covered); the `Subject` header is the forwarding template, and the code and the requester are read from it (a code found only in the body recognises a confirmation and never verifies one; PR #91's review); the `To` header holds exactly one address and it is this mailbox's; and the body matches the recognised forwarding template and names this mailbox's address as where mail will be forwarded. `d=google.com` alone is not enough: Google signs other products' mail (Calendar invitations among them) whose content an attacker chooses, and only the template and the named address make it this message. `msgauth` returns, for each signature, the header fields it covers and whether it limits the body (`inbox.AuthResult` gains `Headers []string` and `BodyLimited bool`, never stored). The requester and the code are read from the signed subject.
- **The mark is off until it is proven on what Google sends.** Pull request 1 builds the predicate and tests it on messages signed in the test with a test key; `inbox.VerifyGmail` stays `false`, so every confirmation is stored with `Verified` false. It is turned on only by a pull request that adds a real confirmation captured in a staging rehearsal (the first that can read mail is pull request 2's), with the DNS record of its key at capture time, and shows the predicate passes on it and fails on each altered copy: a second `From`, `To` or `Subject`; another `To`; an `l=` signature; a body naming another address; a Calendar invitation signed by google.com. docs/plan.md carries it as a condition of the release's verified mark, not of the release.
- **Without the mark the product works.** The set-up shows each confirmation's code and requester, with "Not confirmed by Google" and "Copy this code into Gmail only if <requester> is your account."; the person completes Gmail's step; no `verified_at`, no `source`, no `forwarding_asked` notice.
- **For another address** (`ForAnotherAddress`, only with the mark on): every check passes but the address `To` and the body name is another one. Someone sent here a genuine confirmation meant for an address they control. It is shown without its code ("Gmail sent this for another address; it says nothing about this mailbox") and changes nothing.
- **What "verified" means, everywhere it is said**: Google confirms that this Gmail account asked to forward to this mailbox. Not that forwarding is on, and not that later mail comes from it.
- **The verified Gmail account of the mailbox** (`Mailbox.source`) is the first verified confirmation that arrives while the mailbox is waiting (no `receiving_since`): written once into the record at the version read, with `verified_at`, and the notice "Gmail asked to forward" sent. Later verified confirmations, from the same or another Gmail account, are listed in `confirmations` with their requester and change nothing. Someone who learns the address can ask Gmail to forward their own account to it, and win the first arrival: the app then shows their Gmail address, with its code, as the one Google confirmed. That statement is true. Forwarding starts only when someone types the code into Gmail's settings of the requesting account; Permaily never follows the link, and the person sees which Gmail account asked before they copy anything. The set-up says so: "Copy this code into Gmail only if <requester> is your account."
- **For a mailbox that was disconnected or paused** the confirmation is refused at `RCPT TO` like any mail, and Gmail tells its account the address does not accept mail.

### Mail starts arriving

The first message that is not a confirmation sets `receiving_since` in the record (at the version read; when another enclave set it first, the earlier time stays). The state shown is `waiting` without it, `receiving` with it, `paused` while `paused_at` is set, and `unreadable` when the record cannot be read.

### Disconnecting

`DELETE mailboxes/{id}`, with a fresh proof (ADR 0022), in every standing: an account closing or that has not agreed to changed terms can leave. It always ends in a terminal commit of the mailbox's record before the slot is freed and before it answers.

1. Read the list and find the identifier (not there: `not_found`, the same for an identifier of another account and for one never made). Read the record at its version. Not the caller's account: `not_found`. Already `disconnecting`, `cancelled` or gone: finish what the reservation table says, answer 204 (a second disconnect, of the caller's own mailbox, answers as the first did, until the sweep's last pass has removed the mailbox; after it the mailbox cannot be told from one never made, and the answer is `not_found` to everyone, its owner included: no permanent receipt is kept; C17). Lost: go to step 2, then remove it (`RemoveRecord`) in place of step 3. Forked: delete the pointer through the list's `rcpt` (as in step 5), answer `mailbox_unreadable` with the words of `contracts.ErrMailboxForked` ("An unreadable mailbox"), and change nothing else.
2. Write the disconnect entry at version 0 (`ErrExists`: there already).
3. Write the record at its version: `disconnecting`, `disconnected_at`, `disconnected_by: person`, no key, no sealed part. `ErrChanged`: read again; another request disconnected it, the answer is the same (204). This is the moment of invariant 4. The call that made this commit (or removed a lost record) sends the notice "a mailbox was disconnected" at once, before any step that can fail: a retry finds it disconnected and tells nobody, so a notice sent after the cleanup would be lost with the cleanup's failure.
4. Take the identifier out of the list at its version.
5. Delete the pointer, found by the list's `rcpt`, as it was read, if it names this mailbox.
6. Answer 204.

**What it promises, exactly.** From the commit of step 3 (or the removal of a lost record): no new request opens the mailbox and no new mail is accepted, on any enclave. A request or a delivery that read the record before it is not cut short, and writes nothing after its own deadline, measured on its own monotonic clock from before that read: a request that opens a mailbox or writes into its partition, at most `mailboxes.RequestDeadline` (one minute) from its start; a delivery, at most `mailboxes.IngestDeadline` (one minute) from the end of `DATA`. Each runs under a context with that deadline, handed to `Open`, the store, parsing and the response, and long loops check it: the HTTP server's write timeout only stops the writes to the socket, not the handler. What a late delivery leaves is ciphertext under a key no record holds any more: the sweep's last pass waits it out (below), and anything later still, on storage that misbehaves, expires with DynamoDB's TTL and the S3 lifecycle rule (at most 365 days, the longest retention). The design does not claim the mail is physically gone at the answer.

**The sweep's wait, worked out.** A write by a request or delivery that read the record before the commit ends at most max(1, 1) = 1 minute after that commit, in real time (deadlines are durations on the writer's monotonic clock). `disconnected_at` is the disconnecting enclave's wall clock, and the sweep's "now" another's; ADR 0024 lets two differ by one minute. So the sweep's last pass, made when its clock says `disconnected_at` plus `SweepGrace`, happens at least `SweepGrace` minus one minute after the commit. `SweepGrace` = max(`IngestDeadline`, `RequestDeadline`) + `ClockSkew` + one minute of margin = 3 minutes, so the last pass is at least two minutes after the commit, a minute after the last such write. For a lost record the time is the one in the disconnect entry's key.

**The sweep** (`mailboxes.Service.Sweep`) is run by every enclave every ten minutes and once right after a disconnect. It goes through the disconnect entries, the oldest first, and for each reads the record:

- `disconnecting`: make sure the identifier is out of the list and the pointer is gone; delete the mailbox's messages, a page at a time, only through the message path (`DeleteMessage`: the raw object, then the item), then its entries kind by kind, each listed by its prefix (`txt#`, `confirm#`, `seen#`, `settings`), never by a listing without one: on DynamoDB a mailbox's messages and entries share a partition, and such a listing reads the message rows too, which the entry path would delete without their raw objects (`store.AWS.ListEntries`; `TestReview4ListingEntriesWithoutAPrefixReadsMessages` on the emulator). A pass deletes at most 50 pages of 100 in all; one whose budget runs out says so and leaves everything, the disconnect entry included, for the next sweep. Once `SweepGrace` has passed since `disconnected_at`, one more pass is made, and only when it ends within its budget, the partition empty, are the record removed (`RemoveRecord`), the index entry deleted and the entry deleted as it was read.
- gone: the same deletions, which find nothing after a sweep that finished and everything after a lost record was removed; then delete the entry once `SweepGrace` has passed since the time in its key.
- `active` an hour after the entry was written: the disconnect failed before step 3; delete the entry.
- forked: delete the entry (nothing of the mailbox will be deleted while the record is forked: its mail is opened by nobody and expires with its retention).

Every deletion can be done twice, by two enclaves at once; `ErrNotFound` counts as done. A raw object written by a delivery after the last pass has no item and is deleted by the lifecycle rule of its tag.

**A failure in between** leaves, after 2, a mailbox exactly as it was, and the person sees an error and asks again; after 3, a mailbox that accepts nothing and that nobody can open, whose person was told, whose slot, pointer and mail the next reader of the list and the sweep free and delete, even when the disconnect entry was deleted by hand (the next reader puts it back). Never a mailbox that receives mail nobody can see, and never mail that can be opened after the answer said the mailbox was disconnected.

### An unreadable mailbox

A record that is lost (`store.ErrLost`: its newest value is gone or is not what was committed) or forked (`store.ErrForked`) cannot be read by any enclave: it refuses mail (`550 5.1.1`), its mail cannot be opened, and it is listed as `unreadable` with its identifier and when it was added. It counts against the five. The operator sees it in `/status` (a regression marked `fork` for a fork, `lost` for a strict record, a mailbox's or an account's list, whose newest commit names a value the table no longer holds; each once per record and enclave) and in the account's records.

- **Lost.** The person can disconnect it: since the record cannot say whose it is, the account's list, which is anchored too, is the proof. The disconnect entry is written, the record removed (`RemoveRecord` appends a removal from the history and opens no value), the identifier taken out of the list, the pointer deleted through the list's `rcpt`, and the sweep deletes the partition and the raw objects (it needs no key to delete). A saved value put back in the table afterwards leads to a removed record: nothing (M23).
- **Forked.** Nothing can be committed for it that would help: the strict writers append nothing to a forked record. So it is never freed from the list: it keeps counting against the five, its pointer is deleted through the list's `rcpt` when the person asks to disconnect it, and the person is told in plain words that it could not be disconnected and why ("This mailbox can't be disconnected: what Permaily stores for it was changed by someone else. It accepts no mail and nobody can open it. Write to support@permaily.com"). Both enclaves refuse it for as long as the two commits exist: each is locked for the lock period, ten years in production from when it was written, one day in staging. At the end of the lock, whoever writes to the bucket can delete one of the two; the record then reads by the other, and if that one is `active` the mailbox is back in its person's list (it never left it), without a pointer, so it accepts nothing until a pointer is put back by whoever writes to the table, and its person can disconnect it then. That is ADR 0016's "The lock has an end", which applies to every record. A removal commit above the fork would end it for good at the end of the lock too; it is not done ("What it rests on, and what is left").

### Accounts removed, closing and blocked

- **Removed.** `accounts.removeLocked` calls `Mailboxes.RemoveAccount(ctx, id)` before it removes the account's record. It always leaves the list closed: it closes the list at its version, or makes it closed with `CreateNew` when the account never had one, so a first creation in flight either loses that race and refuses, or wins it and is closed and enumerated on the removal's next try. Then every identifier in it ends as the reservation table says, each in a terminal commit: an `active` one disconnected as above (steps 2 and 3, `disconnected_by: account_removed`, no notice), a lost one removed, a reserved one fenced by a tombstone; a forked one stays named. The list stays, closed. The sweep deletes the mail afterwards. Every step can be done twice; a failure fails the removal, which the account's loop tries again (ADR 0017). Delivery does not rely on every mailbox's commit having been written: at `RCPT TO` and again before storing it reads the account's list too, and takes mail only while the list is read, open and names the mailbox; a list that is missing, lost, forked or closed refuses (`550 5.1.1` at `RCPT TO`, the transaction's `451 4.3.0` at the second check), so a removal that closed the list and then failed to write a mailbox's record stops its mail at once (PR #91's review).
- **Closing** (the seven days): mailboxes go on receiving. The person can read, search and download their mail and disconnect mailboxes; they cannot make a mailbox, change one or delete messages (`account_closing`).
- **Terms not agreed** (changed terms): mailboxes go on receiving. The person can list their mailboxes and messages, download messages and attachments, and disconnect mailboxes; nothing else (`terms_needed`). Leaving never requires agreeing.
- **Blocked** by the operator (decided by the owner): mailboxes go on receiving and storing. Nobody reads them while the account is blocked: every request reads the account's record (`Standing`), and a blocked account's sessions are signed out.

### Paused by the operator

For abuse (an address flooded, or mail that harms the service); decided by the owner. `paused_at` is written in the record at the version read, and the time added to `state_changes`; past ten changes in thirty days the operator gets `too_many_requests`. A paused mailbox refuses mail at `RCPT TO` with the same `550 5.1.1`, keeps everything it holds; the person reads, deletes and disconnects as before, sees "Paused by Permaily", and is told by mail. Resuming clears it. Everything the answer needs (the settings, for the retention) is read before the commit, so a call that committed never fails afterwards: it alone tells the person, and it says so to accounts (`changed`), which counts and logs it; a call that finds the mailbox paused already, or not paused, answers it as it is, tells nobody, and is counted and logged nowhere. The operator cannot disconnect a mailbox or delete mail: that destroys what is the person's, and pausing stops the harm.

## Delivery

Both enclaves listen on port 25 behind one address, and a connection lands on either.

### Admission, before anything is buffered

The enclave has 2 GiB (`enclave_memory_mib`), and the Go runtime is held under 1,536 MiB (`GOMEMLIMIT`, `nix/eif.nix`). What can grow with what senders do is bounded per enclave, by counted semaphores that wait a bounded time (`smtpd` declares the numbers):

| Budget | Value | When it is taken | Over it |
|---|---|---|---|
| SMTP sessions at once | 64 | When a connection is accepted | `421 4.3.2 Too busy, try again later`, and the connection closes |
| Sessions from one remote address | 8 | By the host's proxy (`internal/hostproxy`), which sees the address | The proxy refuses the connection |
| Bytes of `DATA` held at once | 128 MiB | As bytes arrive, a MiB at a time, from the first byte of `DATA` or the first `BDAT` chunk: never at `MAIL FROM`, never from a declared `SIZE` | A step waits at most 10 seconds, then `452 4.3.1 Insufficient system storage, try again later`, and the connection closes |
| Bytes of mail open for reading at once (a message, an attachment, a download, the HTML frame) | 128 MiB | Before a raw message is read from the bucket: the item's size and the seal's overhead, which is also the bound given to `ReadRaw` | Waits at most 10 seconds, then 429 `too_many_requests` |
| Searches at once | 4 | Before a search page | Waits at most 10 seconds, then 429 |

A message held for delivery takes about three times its size at its peak (the buffer, its sealed copy, what parsing and DKIM keep), and an opened one about the same (the sealed object, the raw message, and the HTML document no larger than "The document sent to the frame" allows in the Limits of "Showing a message's HTML", rendered under its own budget there): 128 MiB each, so at most about 384 MiB for each side, plus two renders of "Memory for one render" each and four search pages of about 2 MiB, about 900 MiB in all, with the rest of 1,536 MiB for the runtime, TLS and everything else. A declared `SIZE` over 25 MiB is refused at `MAIL FROM`; otherwise `SIZE` is a hint and reserves nothing, so a sender that declares one and sends nothing holds nothing. A message that passes 25 MiB is answered `552 5.3.4` and the connection closed. The read budget is held until the response's buffer is released, and the raw read stops at its bound: the size stored unsealed beside the message is whoever writes to the table's to set, so it can make a read fail, never make one allocate more than the budget gave. These are per enclave by nature: two enclaves have twice the memory. The four search slots and the read budget are shared by all the accounts of an enclave, not divided among them: one account can occupy them for as long as its requests last, which the request's deadline (a minute) and its thirty search pages a minute bound, and the others then wait or are answered 429; a share per account is left for later. How many sessions come from one remote address is about fairness, which the host can break anyway by refusing connections; the enclave's own budgets hold whatever it does.

### Deadlines of a session

`go-smtp` v0.25.1 (the pinned version) gives a `ReadTimeout` set before each command line it reads, a `WriteTimeout` before each answer, `MaxMessageBytes`, `MaxRecipients`, `MaxLineLength`, and closes a session after three syntax errors or unknown commands (`errThreshold`). It has no absolute deadline, and its `ReadTimeout` is not reset while `DATA` is read. It always offers `CHUNKING`, so `BDAT` must be handled as `DATA` is: it calls `Session.Data` once, at the first chunk, in a goroutine that reads every chunk through a pipe. Built around it (pull request 1): the listener wraps each connection, and the deadline `go-smtp` sets is cut to the earliest of the limits below that applies; `tls.Conn` sets its deadlines on that wrapped connection, so the cut holds after `STARTTLS` too. The session moves the limits as it goes (`NewSession` after the TLS handshake, `Mail`, `Data`, the final answer). While a message's bytes are read (`DATA`, and `BDAT` from its first chunk to its last) the read limit is the stall's, restarted by every read of the connection that brings bytes, however few (a 32 KiB read of the session's need not return), and cut to the transaction's and the session's ends: never the deadline of the command that started it. The delivery's context ends at the transaction's end and the session's, whichever is first.

**`CHUNKING` stays, counted at the connection** (PR #91's review). The pinned `go-smtp` cannot turn `CHUNKING` off (EHLO always lists it), and Exchange Online uses `BDAT` when it is offered, so `BDAT` is handled, and bounded where every line is seen: `go-smtp` sets the read deadline once before each command line it reads, through `tls.Conn` after `STARTTLS`, and the wrapped connection counts every line there, `BDAT`'s after the first chunk included, which no method of the session sees. The session is given no `MaxMessageBytes`: `go-smtp`'s reader of `DATA` refuses a message of exactly that many bytes, and it refuses a `BDAT` chunk past it before the session sees it and keeps the connection open. Without it EHLO advertises `SIZE` with no number (a sender still declares `SIZE=` at `MAIL FROM`, and one over 25 MiB is refused there with `552 5.3.4`), and the session counts every byte of `DATA` and of every chunk itself: a message of exactly 25 MiB is taken, one byte more refused, by `DATA` and by `BDAT`.

| Limit | Value | From, to | Over it |
|---|---|---|---|
| TLS | 30 s (`TLSDeadline`) | The connection accepted, to the EHLO that follows `STARTTLS` | `421 4.4.2`, closed (`go-smtp`'s idle answer) |
| Idle | 30 s (`IdleDeadline`) | That EHLO to the first `MAIL FROM`; the end of a transaction (its final answer, or `RSET` or EHLO inside it) to the next `MAIL FROM` or `QUIT`. `RSET`, EHLO, `NOOP` or any command outside a transaction does not start it again | `421 4.4.2`, closed |
| A command, an answer | 1 min (`CommandTimeout`, `go-smtp`'s `ReadTimeout` and `WriteTimeout`) | One line read, one answer written | `421 4.4.2`, closed |
| A transaction | 12 min (`TransactionDeadline`) | `MAIL FROM` to its final answer: every `RCPT TO`, all of `DATA` or every `BDAT` chunk, and the delivery | `451 4.4.2` once `DATA` started, `421 4.4.2` before; closed |
| `DATA` that stops | 30 s (`DataStall`) | Between two reads of the connection that bring bytes, cut to the transaction's and the session's ends; the command's deadline does not apply | `451 4.4.2`, closed (between two `BDAT` chunks `go-smtp` is reading a command line, and answers `421 4.4.0`; corrected by pull request 1) |
| The delivery | 1 min (`mailboxes.IngestDeadline`) | The last byte of `DATA` to the answer, no later than the transaction's end and the session's | `451 4.3.0` |
| A session | 30 min (`SessionDeadline`) | The connection to its close | `421 4.4.2`, closed |
| Transactions in a session | 20 (`MaxTransactions`) | Counted at `MAIL FROM` | `421 4.7.0`, closed |
| Command lines | 200 (`MaxCommands`) | Every line `go-smtp` reads as a command, counted at the connection: EHLO, `STARTTLS`, `MAIL`, `RCPT`, `DATA`, every `BDAT`, `RSET`, `NOOP`, `VRFY`, unknown ones | `421 4.7.0`, closed, for the 201st when it is EHLO, `MAIL`, `RCPT`, `DATA` or a first `BDAT`; any other is answered by `go-smtp`, and the read of the next line fails at once (`421 4.4.2`), closed |
| Answers 4xx or 5xx of its own | 10 (`MaxFailedCommands`) | Every refusal the session gives, a `SIZE` over the limit and a delivery that fails (`451 4.3.0`) included | `421 4.7.0`, closed |
| Syntax errors and unknown commands | 3 (`go-smtp`) | | `500 5.5.1`, closed by `go-smtp` |

`NOOP`, `VRFY` and `HELP` reach no hook of the session's; they are counted with every other line at the connection (above).

**Closing, never draining.** After a refused `DATA` or `BDAT` (too large, not admitted, stopped, past its deadline) the connection is closed: the session sets the connection's read limit to now and its write limit to `CloseGrace` (10 seconds) ahead, then returns its answer. `go-smtp` then tries to read and discard the rest of the message (`handleData`'s `io.Copy(io.Discard, r)`, or the rest of a `BDAT` chunk), which fails at once; writes the answer; and closes on its next read with `421 4.4.2`. A `421` decided outside `DATA` is answered the same way. A `BDAT` chunk is read at most one byte past 25 MiB: the rest of the chunk stays unread, so `go-smtp`'s copy of it fails and it is answered `552 5.3.4`, closed; a chunk that ends exactly one byte past the limit has been copied whole when the session reads that byte, so `go-smtp` answers it `250` and the session ends at the next command, nothing stored.

**Giving bytes back.** Every byte taken is given back by a deferred release in `Session.Data`, which every path ends in: the answer, an error, a `BDAT` that is abandoned (`RSET`, `QUIT`, a lost connection, `STARTTLS` or a second EHLO, all of which make `go-smtp` close the pipe with `ErrDataReset`), a deadline, a panic. `Reset` and `Logout` give back whatever a session still holds, too; giving back twice gives back once. Pull request 1 has a test per path (D6).

### What a message may hold

Parsing (`inbox`) stops reading what is past these, and the message is still stored whole, with `StoredMeta.Partial`: the header block 256 KiB; one header field 16 KiB decoded; 100 addresses in one of `From`, `To`, `Cc`, `Reply-To`; the subject 2 KiB decoded; MIME nesting 16 deep; 500 parts; 100 attachments listed (the rest are in the raw message); an attachment's name 255 bytes before it is cleaned; the header block of every MIME entity, not only the message's, 256 KiB (past it the walk stops); an attachment's content type 255 bytes (past it `application/octet-stream`); a message's metadata, serialised, 256 KiB (`inbox.MaxMetaBytes`), checked before it is written, under DynamoDB's 400 KB item with room for the seal and the rest: past it the lists of recipients, the `Message-ID` and the `Date`, the attachments' names, the senders and the snippet are emptied in that order. Mail is never refused for its content: a sender told `250` must find it stored.

### The claim, and the order of writes

A message is claimed in each mailbox before it is stored, by a `seen#` entry named by an HMAC of the envelope sender and the SHA-256 of the raw message (`inbox.SeenEntry`).

- **What the first claim fixes**, from what the delivery read then: the message's identifier, when it was received, its retention and so when it expires. Every later try, through any enclave, writes under those values, whatever the mailbox's settings say by then: the same keys, the same received time, the same expiry for the item, its search entry and the raw object's tag. When the claim was taken (`claimed_at`) is a separate field.
- **Its lifetime.** The entry lives seven days from the first receipt (`SeenFor`), set when it is made and never renewed. The claim stands for `ClaimStale` (two minutes, `IngestDeadline` plus `ClockSkew`) from `claimed_at`; nothing renews it but a takeover, which sets `claimed_at` and nothing else. A delivery's own work ends within `IngestDeadline`, so a claim older than that is one whose delivery stopped; two deliveries that overlap anyway (a clock a minute off) write the same items with the same fields (M29).
- **A message is stored once while its entry lives.** Sent again with the same sender and bytes within seven days of its first receipt, it is found stored (or claimed and taken over); after, it is a new message and stored a second time. A sender that changes its bytes between tries (another `Received` line, a new signature) is sending another message.
- **The order of writes makes a message visible last.** The raw object (`PutRaw`, which writes only where nothing is: an earlier try's object is whole and keeps the date its lifecycle counts from), then the search entry and any confirmation entry (version 0), then the message item that listings read (`PutItem`), then the mark. A listing never shows a message whose search entry or raw object is not there yet, and a search that finds an entry without its item leaves it out.

### The sequence, and what each failure leaves

1. **`RCPT TO`** (at most 10 recipients): normalise the address; refuse another domain or a `+tag`; compute the HMAC; read the pointer and check its signature; read the record (a strict read); check that its `rcpt` is the pointer's name, that it is `active` and `paused_at` is unset; read its account's list (a strict read) and check that it is open and names the mailbox; check this enclave's counts for the mailbox (600 messages an hour, 2 GiB a day). Two recipients of one mailbox are one.
2. **The end of `DATA`**: from here a context of one minute (`mailboxes.IngestDeadline`). Verify DKIM (at most 15 seconds, inside the minute) and parse once. Then for each accepted mailbox, one after the other:
   1. Read the record again, and its account's list. No longer `active`, or paused, or unreadable, or the list missing, lost, forked, closed or not naming it: this mailbox is **not stored**; go on with the next.
   2. Unwrap the key; read the settings for the retention.
   3. Read `seen#<digest>`. Marked stored: this mailbox is **done**. Claimed less than `ClaimStale` ago: another delivery of the same message is storing it; **not stored**. Claimed longer ago: take the claim over at the version read, keeping what it fixed. None: claim it at version 0 with a new identifier, now as its received time, the retention just read and the expiry they give. `ErrExists` or `ErrConflict`: read once more and decide again; still contended: **not stored**.
   4. Store, under the claim's values, in the order above: the raw object, the `txt#` entry and, for a confirmation, the `confirm#` entry (each `ErrExists` an earlier try's, the same message), the message item.
   5. For a verified confirmation of a waiting mailbox with no source, `verified_at` and the requester; for the first other mail, `receiving_since`: each at the version read, decided again on `ErrChanged`.
   6. Mark `seen#<digest>` stored at the version of the claim. `ErrConflict`: read it again and open it. This message's mark: **done**. This message's claim, taken over by a delivery that has not marked it: write the mark at the version read (step 4 wrote every part under the same values), once more on a second conflict. Anything else, an entry gone or that does not open: **not stored**, never done (PR #91's review).
   Any error in 1 to 6 makes this mailbox **not stored** and the next one is tried.
3. **The answer**: every accepted mailbox done: `250 2.0.0`; otherwise `451 4.3.0 Temporary failure, try again later`. The admitted bytes are given back.

**What `250` promises, exactly.** At the moment it is sent, every accepted mailbox holds the message complete: its raw object, its search entry (and confirmation entry), its message item and its mark, each acknowledged by S3 or DynamoDB; and it stays until its person deletes it, its retention ends, the mailbox is disconnected or the account removed. Nothing else is excluded, except what whoever controls the storage deletes or alters afterwards (until the audit log of ADR 0019) and storage losing what it acknowledged.

| Interrupted after | What it leaves | What the sender's retry does |
|---|---|---|
| 2.3, the claim | A claim, nothing stored | Within `ClaimStale`, `451` again; after, takes it over, same identifier and expiry |
| The raw object | The raw object, shown nowhere | Takes the claim over; `PutRaw` finds it (`ErrExists`); writes the rest |
| The search entry | The raw object and the search entry; a search leaves the entry out (no item) | The same: writes the item, then marks |
| 2.4, before the mark | The message, complete and listed, unmarked | Takes the claim over, finds each part there, marks it |
| 2.6, before the answer | The message, marked | Finds the mark: `250`, nothing written |
| Never retried (the sender gave up) | A claim that ends with its entry; at most a raw object and search entry without an item (shown nowhere), each expiring with the claim's retention | — |

So a crash never loses a message and never stores it twice while its claim lives: the store is idempotent because the claim decides the keys and the values of the message's items.

## What is anchored, and what is not

**Anchored and strict** (`store.Anchored` with `Strict`: an earlier copy refused, a fork anywhere in the history refused): the mailbox's record, for what going back would matter: its owner, its state (a disconnected or paused mailbox accepting mail again, a cancelled reservation coming alive), its key (a removed key coming back), its `rcpt`, `verified_at` and the Gmail account (undoing which account Google confirmed); and the account's list (going back would hide a mailbox from its person while it received, give back a slot, or reopen a closed list).

**How many commits that is.** S3 keeps every commit for the lock period, and the store refuses a record with more than 10,000 objects (`maxCommitObjects`), so ordinary use must stay far below. A mailbox's record gets at most: one when made, one for `verified_at`, one for `receiving_since`, ten pauses and resumes in thirty days, one at disconnect, one at removal: at the maximum rate, 10,000 commits last about 1,000 periods of thirty days, about 82 years. An account's list gets at most: one when made, ten reservations and ten departures in thirty days, one close, and a departure for each mailbox at the account's removal: about 500 periods, 41 years. Both outlast the ten-year lock, after which ADR 0016's "The lock has an end" applies to them as to every record. Moving a record's head to a new name when its commits grow ("head rollover") is future work of the store.

**Not anchored**, and what putting back an earlier copy, or deleting one, gives whoever writes to the table:

| Record | Put back or deleted | What it gives |
|---|---|---|
| The settings (label, retention) | An earlier label, an earlier retention | The old label shown. An older retention applied to mail first received afterwards: shorter, mail expires sooner; longer, it stays longer. Whoever writes to the table already controls when mail is deleted (the TTL, the lifecycle rules, deleting items), so it gives nothing they lack |
| The pointer | Put back after a disconnect, or copied under another address's name | Nothing: the record refuses it |
| A message, its `txt#`, its raw object | Deleted, or put back after the person deleted it | A message lost or shown again, until the audit log of ADR 0019 (accepted by ADR 0018). Nothing moves between mailboxes or accounts: each is sealed under its mailbox's key, bound to its mailbox and message |
| A `confirm#` entry | Put back after it ended | Nothing: the sealed `ends` hides it |
| A `seen#` entry | Deleted | A message sent again is stored twice |
| A `seen#` entry | An old mark put back | A message sent again with exactly the same bytes is not stored again: dropping mail, which whoever runs the host can do anyway by dropping connections |
| A disconnect entry | Deleted | Nothing lasting: the next reader of the list puts it back while the identifier is in the list; after that, ciphertext under a key no record holds expires with its retention |
| The index of mailboxes | Anything | Wrong counts in the admin panel |

## The store

Built first, in pull request 0, with its tests (S1 to S17) and ADR 0016 updated. The declarations below are in the repository already (`internal/store/strict.go`, `scan.go`, `parts.go`); nothing implements them before pull request 0. Everything else of the store, and every record that is not strict, stays as it is, byte for byte.

**What a fork is.** Two commits of one record at one version, both with this deployment's authentication code, with different digests. Copies of one commit (the same digest), however many object versions hold it, locked or not, are one commit. A commit object is written only where nothing is at its key (`IfNoneMatch: "*"`, `s3commits.go`, since #51), so no legitimate race leaves two commits of different digests at one version: two enclaves that write the same version get one `ErrExists`. Two can only be there if whoever writes to the bucket hid the first behind a delete marker while an enclave wrote the second (`TestAnchoredOverS3CommitsWithADeleteMarkerInBetween`). A copy of a commit's bytes written again at its key, which anyone who writes to the bucket can do, is the same commit: the authentication code covers the record's name, the version, the digest and the time, and the object key carries the version, so a copy cannot be moved to another version or record, and it is not a fork.

**Where it is looked for: at every version.** `S3Commits.Head` lists every object version under the record's prefix already (`ListObjectVersions`, page after page, up to `maxCommitObjects`, 10,000), but reads them only from the highest version down to the first commit, and of two there keeps the smaller digest. That is why a pending write could bury a fork (S6): a commit above a fork made the fork invisible. A strict reader reads the whole history (`History`): every object version listed, so a fork at any version makes every later read and write of the record fail with `ErrForked`, on every enclave and after any restart, for as long as both commits exist: both are genuine commits written by an enclave with its lock, which nobody can remove during the lock period. Whatever lands above a fork is unreadable too.

**What a read costs.** One `ListObjectVersions` per 1,000 object versions of the record (a mailbox's record has from five to a few dozen in its life), and one `GetObject` for each object version this enclave has not read before, at most `MaxHistoryReads` (500) per read and sixteen at once. Object versions are immutable (S3 never changes the bytes of a version id, and a lock can only be extended), so what was read of one is kept in the enclave's memory, by key and version id, for the next read (at most 100,000 kept, the oldest dropped first); every decision is still made from the full listing of that read, and an enclave that starts empty reads everything and decides the same. A record read once on an enclave is read again with one listing; at delivery that is two listings per accepted mailbox and message, about $0.01 per thousand messages and 20 to 50 ms each. A record with objects this enclave never read beyond 500 fails that read with an error that is not `ErrForked` (refused as an unreadable record is, for now), and the next read goes on from what was kept (S10). A read holds what it learnt of every object it listed, from the memory or fetched, until it has decided, so what the memory drops meanwhile (for this record or another's read) cannot take a commit out of its decision; it never decides from part of a history (changed after the code review of pull request 0, finding 1). The listing's bound counts everything listed, delete markers and keys that are not versions included (10,000), and its pages (100, each moving on): past either the read fails with an error that says the history is too long, not `ErrForked`, and records no `Regression` (it is not evidence that a commit went, and the failing reads show it; finding 5). `Head`, for records that are not strict, lists as before.

**What an unlocked commit means.** `Append` writes the object with its lock in the same request, in compliance mode (`ObjectLockMode`, `ObjectLockRetainUntilDate`), and a bucket without Object Lock refuses the request: an enclave never writes a commit without its lock. `read` today accepts a commit whatever its lock says, and only notes the date (`LockedUntil`) when it is in compliance mode; the enclave's role may read the lock (`s3:GetObjectRetention`, `deploy/tofu/anchors.tf`), so the headers come back. The bucket has no default retention (`anchors.tf`), so a copy written by anyone else carries the lock they choose, or none. So a strict reader checks the lock per digest, on its best copy: locked as `Append` locks, in compliance mode until no earlier than its time plus `MinCommitLock` (one day, the staging images' period). A digest with no such copy means the store of commits did not keep a lock it took, which is an alarm (`History.Unlocked`, a `Regression` with `Unlocked`, reported by `/status` as `unlocked` and failed on by `permaily-verify`), never something a reader decides by: the commit is counted all the same. Ignoring it could let the record go back to before it if S3 ever failed to keep a lock; refusing the record for it would let anyone who writes to the bucket stop a record by copying a commit, which a copy of a locked commit cannot do here since the original's lock is the best copy.

**Scope: strict records only.** `Strict` is an option an `Anchored` is made with, as `OnlyNewest` is, and one `Anchored` serves one kind of record. It is on for the two kinds this step adds (`mailbox-…`, `mailboxes-…`, an `Anchored` of their own in the composition, with `OnlyNewest`), and off for what production already stores: accounts and the providers' applications (accounts' `Anchored`, `OnlyNewest`) and the TLS identity (its own, neither). Those keep today's behaviour exactly, smaller digest included, with the same requests to S3 (S2): pull request 0 changes nothing in how production's records are read or written, nor in `/status`. Making accounts strict is future work with its own decision ("What it rests on, and what is left"); the TLS identity's recovery from a fork is ADR 0024's, unchanged. Strictness is per `Anchored` instance and knows nothing of names: the layer that composes the store guarantees that a strict name is never read or written through an `Anchored` that is not strict (that one would read by `Head`, adopt a plain value and write over a fork), and that strict records are made only with `CreateNew` (decision D).

**What a strict record's own writers do.** `PutRecordAt` and `RemoveRecord` on a strict record read the history again before they append, and refuse on a fork (`ErrForked`) without appending; `PutRecordAt` also answers `ErrChanged` without appending when the history moved past its mark. That narrows the pending-write case, and the every-version rule closes it: whatever another writer appends above a fork in between is unreadable all the same (S6). `RemoveRecord` reads the history and never the value, so it removes a lost record as well as a readable one, and a forked one takes no commit. A strict append that S3 refuses reads the history again, and a fork found then is `ErrForked`, not `ErrChanged` or `ErrExists` (finding 3).

**`CreateNew`, and its precedence.** `CreateNew(ctx, r)` makes a record only if no commit of this deployment was ever made for its name and nothing is stored under its plain name from before commits existed. One stated precedence, tested (S8): a name whose history has a fork answers `ErrForked`; a name with any other commit, a removal included, answers `ErrExists`; so does one whose newest value is lost, or one with a value under the plain name. `PutRecord(create)` stays as it is for the TLS identity and accounts, which may make a removed or lost name again; strict kinds use only `CreateNew`, so a name once made is never made again. A strict read never takes a value from the plain name as a record that is not strict does: strict kinds came after commits, so such a value with no commit is refused with `ErrRolledBack`, which is not an `ErrNotFound`, so nobody makes the record over it without noticing (decision A). When `CreateNew`'s append is refused and the history read again shows no commit, the value it staged stays: two enclaves making one record with the same bytes stage it under one name, and S3 answers 409 to one while the other's append lands, so deleting it could delete an acknowledged record's value; it is deleted only when a commit of another digest took the version. An orphan is a value no commit names, read by nobody, and `RemoveRecord` deletes it with the record's other versions (finding 2). **What remains assumed:** if every commit of a record vanished from the bucket, an empty history would look like a name never used; Object Lock lets nobody do that during the lock period, and it is the stated limit of the guarantee.

**Older releases** read by digest and know nothing of the new kinds: the strict rule does not apply to the kinds they read, and they neither read nor write a mailbox or a list. The guarantees of this step assume that releases from before it no longer run against the deployment's data once mailboxes exist: after the release that builds this is verified, the operator deletes the KMS keys of the releases before it (docs/operations.md, "Mailboxes per account: what changes for the operator"). Until then a rollback is possible, and what this step guarantees holds only while this release or a later one runs.

- **The errors, in the order a strict method checks them:** `ErrForked` (the history), then `ErrRolledBack` (this enclave saw more than the store answers), then `ErrChanged` (`PutRecordAt`: the history moved past the mark) or `ErrExists` (`CreateNew`), then `ErrNotFound` and `ErrLost` (reads). `ErrForked` is not an `ErrNotFound`.
- **`ScanEntriesDown`, `ScanMessagesDown`.** One DynamoDB `Query`, `ScanIndexForward: false`, `Limit: maxRead` (which counts items evaluated, not returned), consistent, with the key condition `begins_with(sk, :prefix)` (none for an empty prefix) and `ExclusiveStartKey` at `before`, which needs no item there, so `before` itself is never read or counted (a key condition `sk BETWEEN :prefix AND :before` would read it, count it in `Read`, and with `maxRead` 1 answer it as `Last` page after page; corrected by pull request 0), expired items left out after reading. `Read` is the `ScannedCount`; `Last` is the key of the last item read, expired or not; `More` is `LastEvaluatedKey` being set, never derived from `Read` reaching `maxRead`: DynamoDB stops a page at 1 MB of items read whatever the limit (S11). It never reads a second page. `ListEntries` and `ListMessages` stay as they are for accounts and F1's callers.
- **`PutRaw`.** S3 `PutObject` with `IfNoneMatch: "*"`: `PreconditionFailed` (412) is `ErrExists`; a concurrent write's `ConditionalRequestConflict` (409) is an error to retry, not `ErrExists`, since the other write may yet fail.
- **`Item`, `ReadRaw`.** `Item` is the `GetItem` of `GetMessage` without the object. `ReadRaw` reads the object through `io.LimitReader(body, max+1)` and answers `ErrTooLarge` when more than `max` came, before keeping more (S15).
- **`DeleteMessage`** deletes the raw object first (S3 answers a missing key as deleted) and the item after, and may be called again after any failure: it answers `ErrNotFound` only when the item was not there, the raw object deleted all the same (S14). Today it deletes the item first: a failure at the raw object then answers `ErrNotFound` when asked again and leaves the object (`aws.go`).
- **`Memory.Interrupt`** is called before every read, write and delete of `Memory` with its step, partition and key; an error fails that request and leaves every earlier one done; it may block, and the method returns the context's error when the context ends first (S17). `PutMessage` is two steps there, as it is two requests on AWS.
- **Added after the code review of pull request 0.** A mailbox's and a message's identifiers are checked before any request that builds a key from them, raw objects and items alike: empty, or anything but letters, digits, `_` and `-`, is refused (a read or a delete answers `ErrNotFound`, a write an error), with an error that does not hold the identifier; the identifiers the service makes are unchanged (finding 6). `ReadRaw` takes a bound from 0 to 32 MiB (the largest message accepted, 25 MiB, and its seal); anything else is an error before any request, the same on both stores (finding 7). `Memory.PageItems` cuts every scan's page at that many items read, as DynamoDB's 1 MB does, so services built on `Memory` see short pages with `More`; `Memory`'s scans sort the whole partition before taking a page, bounded in what they return, not in their work (decision C). The errors of a strict record do not hold its name (decision B).

## Access while an account is closing or has not agreed

## The inbox

Every route that opens a mailbox runs under a context with `mailboxes.RequestDeadline` (one minute) from the request's start, set by the adapter before anything else, handed to `Open`, the store, parsing and writing the response; loops over items check it between items, and no page is answered once it has ended. The HTTP server's write timeout (also a minute, `cmd/permaily-enclave`) only stops writes to the socket.

### What a message returns

- **Text, always.** The text/plain part (the first, decoded); with none, text the enclave takes out of the text/html part with `golang.org/x/net/html`'s tokenizer (already in the module graph through `go-message`): text nodes, a line break for each block element, nothing of `script`, `style` or `head`, entities decoded, and each link's target written after its text in brackets. With neither, nothing (`text_from: none`). At most 256 KiB; `text_truncated` past it, or when the HTML read for text (2 MiB) was cut, or the context ended. There is one extraction in the tree: pull request 1 takes pull request 2's, on the tokenizer (`golang.org/x/net` a direct dependency from pull request 1), after its own hand-written reader was found quadratic and out of bounds on some input (PR #91's review); it is linear, keeps at most 32 open links' targets of at most 2 KiB each, and checks its context every 1,024 tokens, so a delivery's deadline stops it. `inbox.MessageText(ctx, raw, max) (text, from string, truncated bool)` makes it, at delivery for the search entry and at read for `Get`, over the one MIME walk (`walkParts`) that also lists attachments at delivery and finds one by its index at read. An attachment is a file: it is listed at the size of, and downloads as, the bytes its sender attached, its transfer encoding (base64, quoted-printable) undone and no charset converted, whatever its type (`text/*` and a message inside the message included), read through one bound on both sides (`attachmentBody`: 25 MiB, which undoing a transfer encoding of a message delivery accepted never reaches); so a body whose transfer encoding breaks half way is the bytes before the break, and listed and downloaded are the same bytes. The text view and search read the text parts converted to UTF-8 from their charset.
- **And HTML, formatted**, as "Showing a message's HTML" says.
- **Attachments** are listed by index, name, type and size, and downloaded only as files: `GET .../attachments/{index}` answers `Content-Type: application/octet-stream` whatever the message said, `Content-Disposition: attachment` with the name cleaned (`domain.AttachmentFilename`: no path, no control or format characters (bidirectional overrides among them), no line or paragraph separators, quotes or the characters file systems refuse (`<>:|?*`), trimmed of spaces and dots, at most 120 characters, prefixed with `_` when Windows reserves it for a device (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, with or without an extension, in any case), `attachment-<n>` when nothing is left; executable and double extensions are kept as the sender wrote them; `filename*` in UTF-8 and an ASCII `filename`), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: no-store`. The raw message the same way, as `message/rfc822`.
- **Who sent it**: the DKIM results are returned (`auth`), and the app says "Signed by <domain>" or nothing; it never says a sender is who they claim to be.
- **Reading the raw message** takes the read budget of "Admission" first, for the item's size and the seal's overhead, and reads with `ReadRaw` bounded by it; the budget is held until the response's buffer is released.

### Listing and paging

Newest first; `limit` 1 to 100 (50 without one); `after` is the `next` of the page before, a message identifier (32 hex characters, otherwise `invalid_cursor`). A page reads at most 500 message items (`ScanMessagesDown` in batches of 100), every item read counting, expired ones included, and stops at `limit` messages or 500 read. `next` is where the caller stopped: the last message put on the page when the page filled inside a batch (the rest of that batch is read again by the next page, never skipped); the scan's `Last` when the page ended at a batch's end and the scan said `More`; absent when the scan said no `More` and nothing of its last batch was left over. So a page may hold fewer than `limit` messages, or none, and still have `next`: the app offers "Older" whenever `next` is there.

### Searching

- **What**: the senders' names and addresses, the subject and the text (its first 16 KiB). The query is split on spaces; each part must appear in one of them, without regard to case: the terms and the fields are compared under Unicode simple case folding (each character the smallest of its `unicode.SimpleFold` orbit, so `ος`, `οσ` and `ΟΣ` match, `ß` matches `ẞ` but not `ss`, and `İ` and `ı` match only themselves), each field folded once per entry. There is no Unicode normalisation: accents, and composed and decomposed forms, stay distinct. No operators, no phrases.
- **How**: `ScanEntriesDown` over the `txt#` entries from below `after`, a hundred at a time, opening each and matching, until `limit` matches or 2,000 entries read. What counts toward the 2,000: every item read under `txt#` (`Read`), an expired one and one that does not open under the key included. A match whose message item is gone is left out (it counted): that is checked with `Item`, which never reads the raw object. `next` is the message identifier of the last entry the search consumed, matched or not: the `limit`-th match when it stopped inside a batch, otherwise the scan's `Last` when the scan said `More`; absent otherwise. `searched_to` is when that same entry's message arrived: `SearchEntry.received_at` when it opens, and otherwise the time in its message identifier, which every key carries, so a last page of nothing but expired entries still says how far back it looked. A page with no match has `messages: []`, `searched_to` and, unless nothing older is left, `next`: the app says "Searched mail back to <searched_to>" and offers "Search older mail". With no migration (the test mailbox is retired) every message has its `txt#` entry, written before its item.
- **Cost, at most, per page**: 2,000 entries of about 18 KiB, so about 36 MiB read from DynamoDB in twenty or more queries (a query stops at 1 MB), about 4,600 read units (a thousandth of a dollar on demand), about a second, and 2 MiB in memory at a time. At the forty messages a day the forwarding screens expect, ninety days are 3,600 messages: two pages search a whole mailbox.
- **Rejected: a sealed index** (an HMAC per word). It would answer in one read, but it shows whoever reads the table how often each hidden word appears and when, and it has to be kept right as messages are deleted or expire. To be revisited when a mailbox holds more than about 20,000 messages.

### Deleting

One (`DELETE .../messages/{id}`, 204, `not_found` when it is not there) or up to 100 (`POST .../messages/delete`, answering how many were there). Each deletes the raw object, then the item (`DeleteMessage`, which a retry finishes), then its `txt#` and `confirm#` entries. No fresh proof: a session that can read a message can delete it, as in any mail app.

- **Counts and records, never addresses.** `AccountRecord` gains `mailboxes` (how many the account has), `Stats` gains `mailboxes: {total}` (from the index), and an account's mailboxes are listed as `MailboxRecord`s: identifier, account, state, created, retention, receiving since, paused at, verified or not. - **Finding a mailbox by its address**, for an abuse report that names one: the address is hashed as `RCPT TO` hashes it, the pointer followed and the record must bear it out; a list of none or one. It tells the operator which account owns an address they know already.
- **Pause and resume**, counted on `/status` as `mailbox_paused` and `mailbox_resumed` (added to `attestation.AdminActions` and printed by `permaily-verify`), logged by kind alone, and, through the panel, written in the admin log with the account and the mailbox. - **Not**: reading, disconnecting, deleting mail, changing a label or a retention, moving a mailbox.
- **`/status` shows no count of mailboxes**: it is public, and one enclave's.
- **`/status` shows the strict records' alarms**: a regression of a mailbox's record or an account's list is reported under the name `mailbox` (the names hold identifiers), with `fork: true` for a fork and `unlocked: true` for a commit S3 did not keep locked (`attestation.AnchorRegression` gains both, pull request 1); `permaily-verify` fails on either, as on any regression.

## Options considered

- **A list inside the account's record**, or entries: rejected above.
- **Moving the test mailbox into the owner's account**: a release that reads F1's items could bring back a disconnected test mailbox, and a rollback would keep a reader that ignores disconnection and holds the token. Retired instead.
- **A cache of mailbox records for ingest** (a minute): one enclave would accept mail for a minute after the other disconnected or paused the mailbox.
- **Marking a message seen before storing it**: a failure between the two loses mail. The claim, then the mark after, instead.
- **Choosing one of two commits at a version by digest**, for mailboxes and lists (ADR 0016's rule, kept for the records that are not strict): whoever writes to the bucket would decide which change counts. Refused instead.
- **Looking for forks at the newest version only**: a write pending above a fork buries it (S6). Every version instead.
- **Counting copies of a commit as a fork**: anyone who writes to the bucket could stop a record by copying a commit, and then delete the copy to bring it back (S7). By digest instead.
- **The strict rule for every record now**: it would change how accounts and the TLS identity are read in production in the same step, and raise how the TLS identity recovers from a fork. Strict for the new kinds only; the rest is future work.
- **Reserving `DATA`'s bytes at `MAIL FROM`, or by the declared `SIZE`**: six sessions that never send `DATA` would hold the whole budget. As bytes arrive instead.
- **Draining a refused `DATA`**: the sender keeps the enclave reading up to 25 MiB it will throw away. Closed instead.
- **Refusing the mail of a blocked account**: Gmail would tell the person forwarding fails, and nothing is gained while nobody can read it.
- **Letting the operator disconnect**: it destroys the person's mail without their word; pausing stops the harm.
- **Deleting the mail inside the request that disconnects**: up to tens of thousands of objects in one request; removing the key from the record stops access at once, and the deletion can wait for the sweep.
- **A KMS key per mailbox**: real destruction of a key, at a key per mailbox and a seven-day wait; not now ("What disconnecting does to the key").
- **Text only, HTML deferred**: rejected by the owner on 2026-11-12 ("Showing a message's HTML").
- **One inbox merging every mailbox**: each page would read every mailbox's partition and merge by time. One mailbox at a time first; a merged view needs no change of format later.

### The brief for pull request 0

For an engineer who reads only this. Permaily keeps some records in DynamoDB with a commit per change in an S3 bucket with Object Lock (`store.Anchored` over `store.S3Commits`, ADR 0016): a record is read by its newest commit, so an earlier copy put back in the table is refused. Whoever writes to the bucket can still hide a commit behind a delete marker and let an enclave write a second commit at the same version; today the reader keeps the one with the smaller digest. This pull request adds a second way to read, **strict**, for two kinds of record that do not exist yet (a mailbox, an account's list of mailboxes): a fork anywhere in the history refuses the record. It adds `CreateNew`, a descending scan, a message's parts and a test hook to the store. It must change nothing in how the records production already stores are read and written. Read "The store" above, ADR 0016, `internal/store/anchor.go`, `s3commits.go`, `aws.go`, `memory.go`, and the declarations in `strict.go`, `scan.go`, `parts.go`.

**The changes, in order, each with its tests.**

1. **`MemoryCommits` can hold what S3 can.** `Fork(name, version, digest)` adds a second commit at a version (what a delete marker allows); `Copy(name, version, locked)` adds a replayed copy of the commit at a version, which holds that version for `Head`, `Next` and `Append` as the original does (it stays when the original is forgotten, as in S3); commits gain a lock flag in memory. `MemoryCommits.Head` with two commits at one version keeps the smaller digest, as `S3Commits.Head` does. Tests: `Head` on a fork in memory and in the fake bucket (`lockedBucket`) answers the same commit.
2. **`History`** on `S3Commits` and `MemoryCommits` (`HistoryReader`; not added to `Commits`: `failingCommits` in `anchor_test.go`, a test that must not change, implements only `Head` and `Append` and would no longer compile). `S3Commits.History` lists every object version under the prefix (pages of 1,000, at most `maxCommitObjects`), fetches each object version not yet in the enclave's cache (key and version id; immutable), at most `MaxHistoryReads` per call and sixteen at once, verifies each as `read` does, groups the commits by version and then by digest, and answers `Head` (the highest version with a commit), `Next` (as `Head`'s rule), `Forks` (versions with two digests or more) and `Unlocked` (a digest with no copy in compliance mode until at least its time plus `MinCommitLock`). `Head` itself does not change. Tests: S7, S9, S10 on the fake bucket; a history on a record with junk objects at free versions answers the same `Next` as `Head`.
3. **`Anchored.Strict`.** With it, every method reads the history instead of `Head`: `ErrForked` before anything else when `Forks` is not empty (and a `Regression` with `Fork`, once per record and enclave); `Unlocked` recorded as a `Regression` with `Unlocked` and otherwise ignored; then the same regression check against what this enclave saw (`ErrRolledBack`), the same reading of the value, `OnlyNewest` and `discard` as today. `PutRecordAt` reads the history before it appends: `ErrForked` on a fork, `ErrChanged` without appending when the history's `Next` is past the mark's. `RemoveRecord` reads the history and never the value. 4. **`Anchored.CreateNew`**, for strict records (an error on one that is not): `ErrForked`, then `ErrExists` for any commit or a value under the plain name, else `Append` at the history's `Next` after storing the value; an `ErrExists` from `Append` reads the history again and answers `ErrForked` or `ErrExists`. ## Showing a message's HTML

Decided by the owner on 2026-11-12: the inbox shows messages formatted from the start. Mail is hostile input from anyone on the internet, and it is shown inside the app that holds the person's session, their passkeys' settings and, from step 5, the consent screen for agents. This section says what showing it guarantees and what it does not, which mechanism holds each guarantee and which is only a second line, and every limit with its number. It was revised after an adversarial review on 2026-11-12 (no script-execution escape and no cross-account disclosure found; eight findings carried in below).

### What it guarantees, and what it does not

**A message can never**: run anything (script, event handler, `javascript:` URL, plugin, form, `<meta>` refresh, nested frame); read or change the app's DOM, cookies, storage, clipboard or address; call the API with the person's session; navigate the app's window; fetch anything from anywhere because it was opened or read (images, fonts, stylesheets, prefetch hints); send the person anywhere without the link page between, where the real destination is shown and nothing is contacted until the person presses "Open"; put a link's box over other content or make a link invisible; change the trusted chrome around the frame.

**A message can still**: draw a picture of anything inside its frame, a fake Permaily screen or a fake sign-in included, as any mail client's content can; make its text say one address while its link leads to another (the link page shows the real one, and says so when they differ); be long, ugly or hard to read (the "Text" view is always there); show an image the sender attached, with whatever metadata (EXIF) is inside it, which stays inside the `data:` URI in the frame and goes nowhere.

**Following a link** is the person's act. It goes to the address the link page shows, and that site learns that the link was followed and when, from the person's browser and network address; a link can be unique to a reader (`https://sender.example/read/recipient-7c91`), so the site may know who followed it, whatever the referrer policy. No referrer and no opener go with it.

**Opening or reading a message** makes no request that the sender or anyone outside Permaily can see.

**Outside it**: what browser services the person turns on see what the browser shows them (translation in Safari and Chrome sends page text to Apple or Google; reader mode; extensions, which can read any page). The frame carries `translate="no"` and `<meta name="google" content="notranslate">` as a courtesy, not a guarantee. A browser bug that breaks both the sandbox attribute and the CSP `sandbox` (a separate origin for message content is the third line, below, and when it is reopened).

### The frame

The viewer is an `<iframe>` whose `src` is `/api/v1/mailboxes/{id}/messages/{message}/html`, with `sandbox="allow-popups allow-popups-to-escape-sandbox"`, `referrerpolicy="no-referrer"`, a `title` for assistive technology ("Message: <subject>", "Message: No subject") and nothing else. A new `<iframe>` element per message (React `key` on the message identifier), its `src` never changed: the first navigation of a new frame replaces its initial `about:blank` and adds no history entry.

- **Both popup flags are needed.** `allow-popups` lets the frame's link open a tab. `allow-popups-to-escape-sandbox` unsets the "sandbox propagates to auxiliary browsing contexts" flag (HTML); without it the link page's tab would inherit the frame's sandbox, run no script, and the link page, an app page, would not work.
- **Why a URL and not `srcdoc`.** A `srcdoc` document takes a copy of its parent's policy container, so the app's own CSP would apply inside it and mail would show without its styles and images, unless the whole app's CSP were loosened. `srcdoc` would also put the hostile HTML into a string in the app's JavaScript. A URL gives the frame a CSP of its own and keeps the HTML out of the app's JavaScript entirely.
- **The app's CSP.** `default-src 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'` today (`internal/router`). The fifth pull request writes `frame-src 'self'` out, so a later change to `default-src` cannot widen or break it unnoticed, and a test pins it.
- **The frame's response headers**, on every answer of the route, errors included, replacing the router's: `Content-Type: text/html; charset=utf-8`; `Content-Security-Policy: sandbox allow-popups allow-popups-to-escape-sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:; form-action 'none'; base-uri 'none'; frame-ancestors https://app.permaily.com` (the app's host from the image's configuration; dev mode's own); `X-Content-Type-Options: nosniff`; `Cross-Origin-Resource-Policy: same-origin`; `Referrer-Policy: no-referrer`; `Cache-Control: no-store`; `X-DNS-Prefetch-Control: off`; `Strict-Transport-Security` as the router's.
- **The document** is written by the sanitiser from nothing: `<!DOCTYPE html><html lang dir translate="no" style="…">` (the message's `lang` and `dir` when valid), `<head>` with `<meta charset="utf-8">` first, `<meta name="referrer" content="no-referrer">`, `<meta name="google" content="notranslate">`, the sender's CSS, then the frame's stylesheet; then `<body>` with the message's content.
- **How the session authorises it.** The frame's request is made by the app's own document for a frame whose every ancestor is the app, so by the specifications it is same-site and carries the `SameSite=Strict` session cookie; the sandbox applies to the document that comes back, not to the request that fetches it. Whether each browser sends it is release evidence ("The release gate"); when it does not, the route answers 401 with the frame's headers and the fixed body, and the viewer says "This message can't be shown formatted here" with the text view. The route opens the mailbox like `GET message` (`Open` with `AccessReadMessage`: the owner, the record, the account's standing) before reading anything, and takes the raw message's size from the bytes of mail open for reading ("Admission").
- **A request without a frame's Fetch Metadata.** When the request carries any `Sec-Fetch-*` header, the route needs `Sec-Fetch-Dest: iframe` and `Sec-Fetch-Site: same-origin`, and answers 404 otherwise: opening the frame's URL in a tab, from history or from session restore gets "This message can't be shown here." A request with none is served, and the CSP `sandbox` holds as above. Fetch Metadata is Baseline since March 2023 (Safari 16.4).
- **Back, forward and the back/forward cache.** `Cache-Control: no-store` keeps the frame's document out of the HTTP cache. It does not keep a page out of the back/forward cache everywhere (web.dev: browsers have historically declined, and Chrome is changing it), and the app's own page is `no-cache`, so a restored app page brings its frame back. The message view listens for `pageshow`; when `persisted` is true it removes the frame and the text at once, shows "Checking…", asks `GET me` and `GET message` again, and shows the message again only when both answer; otherwise what the session gate shows, or "That isn't there any more."
- **A separate origin** for message content (a host such as `content.permaily.com`) would be a third line, independent of the sandbox. Not now: it needs a new name in the enclave's certificate, its CAA and verification steps (docs/verification.md), and a signed, short-lived ticket in the frame's URL since the `__Host-` cookie is not sent to another host. Reopened by a published bypass of both the sandbox attribute and the CSP `sandbox`, by a need for scripts in the frame, or by a release-gate check that fails in a browser people use.

### The sanitiser

A new package, `internal/mailhtml`, pure (no storage, no network), on `golang.org/x/net/html`, already in the module graph (`go.mod` moves it from indirect to direct with pull request 1, whose text extraction uses its tokenizer; `golang.org/x/net/html/charset` and `golang.org/x/net/idna` come from the same module, v0.62.0 today). No third-party sanitiser: `github.com/microcosm-cc/bluemonday` would add itself, `github.com/aymerick/douceur` and `github.com/gorilla/css` to the image and to third-party-notices.md, and would still leave to us `cid:` images, links rewritten to the link page, counting what was removed, the budgets, and CSS by value.

**Input.** `internal/inbox/htmlpart.go` (pull request 5) walks the raw message with `go-message` and takes the text/html part a mail client would show: the last text/html of a `multipart/alternative`, else the first inline text/html; and the parts of its `multipart/related` by `Content-ID`. `go-message` undoes the transfer encoding. The charset is decided in this order, written in the package rather than taken from `charset.DetermineEncoding`, which looks at the first 1,024 bytes only, puts a byte order mark before the header, and falls back to Windows-1252 whenever those 1,024 bytes are not UTF-8 with a byte above 0x7F (read in x/net v0.62.0's source):

1. the MIME header's `charset`, when it is a label of the WHATWG Encoding Standard (`charset.Lookup`);
2. a byte order mark (UTF-8, UTF-16LE, UTF-16BE), which is then removed;
3. a `<meta charset>` or `<meta http-equiv=content-type>` within the first 1,024 bytes (the HTML standard's prescan);
4. UTF-8, when the whole part is valid UTF-8;
5. Windows-1252.

The HTML standard puts the byte order mark first; mail puts the MIME header first, as every mail client does, and since the frame receives only the sanitiser's own UTF-8 the order changes how text looks, never what runs. A label that names the WHATWG "replacement" encoding, or no WHATWG encoding (UTF-7 among them), makes the HTML `unreadable`. Invalid sequences become U+FFFD. The size limit applies before and after transcoding (a Windows-1252 byte can become three).

**Budgets, enforced while the work happens.** Every render (for `Message.html`, for the frame, for a link) runs under one `context.Context` with the deadline below, after taking a render slot ("Renders at once") and before the raw message is read from the bucket, and stops at the first limit it meets:

1. **Before any tree.** A pass of `html.NewTokenizer` over the decoded part counts start tags, attributes per element and in all, attribute bytes, and an upper bound of the tree the parser will build: each start tag and text token adds one, plus the formatting elements (`a b big code em font i nobr s small strike strong tt u`) opened and not yet closed, which the parser's "reconstruct the active formatting elements" step can clone at that token. Past any limit the HTML is `too_large` and no tree is built. This is what stops input whose tree is much larger than its tokens (the amplification case of "Tests").
2. **The parse.** `html.ParseWithOptions(r, html.ParseOptionEnableScripting(false))`, the HTML standard's tree construction with scripting off as it is in the frame, so `<noscript>` parses the same in both. `r` returns at most 4 KiB a read and fails once the deadline has passed, so the parse stops within one read of it. The parser itself refuses a stack of open elements deeper than 512 (`insertOpenElement`), which the sanitiser reports as `too_large`.
3. **The walk.** The sanitiser builds a new tree from nothing, copying only what the allowlist names; it never moves a node of the input into the output. It counts output elements and depth as it goes and checks the context every 1,024 nodes.
4. **The output.** Written by `html.Render` into a writer that counts bytes and fails at the cap; `Message.html` renders into a counting writer that keeps nothing, so its status is the frame's. Then the output is parsed again with the same options and rendered again, and the two renderings must be byte for byte the same, else the HTML is `unreadable`. That check catches a tree that x/net/html would itself parse differently; it does not show what a browser builds, and it is not what stops mutation XSS. The sandbox and the CSP are first for running anything; the browser tests inspect the DOM each browser actually builds from the output ("Tests").

- Kept, with the attributes below: `a abbr address article aside b bdi bdo big blockquote br caption center cite code col colgroup dd del details dfn div dl dt em figcaption figure font footer h1 h2 h3 h4 h5 h6 header hr i img ins kbd li main mark nav ol p pre q rp rt ruby s samp section small span strike strong sub summary sup table tbody td tfoot th thead time tr tt u ul var wbr`; `style` only through the CSS filter, moved into the head.
- Dropped with everything inside: `script noscript template style` (outside the filter) `title head` (the message's; ours is written) `iframe frame frameset object embed applet param svg math canvas audio video source track picture map area link meta base input select option optgroup textarea button datalist output progress meter dialog portal slot xmp plaintext noembed noframes listing`, comments, processing instructions, `<!DOCTYPE>`, and any element in the SVG or MathML namespace.
- Unwrapped (the element goes, its children stay): `html`, `body`, `form`, `label`, `fieldset`, `legend`, `marquee`, `blink`, and every element not named in either list (`o:p`, Outlook's `v:` elements, custom tags).

**Attributes** (all others go, every `on*`, `srcset`, `sizes`, `loading`, `poster`, `background`, `dynsrc`, `lowsrc`, `longdesc`, `usemap`, `ping`, `formaction`, `xmlns`, `cite`, `name`, `target`, `rel` among them):

- On any kept element: `dir` (`ltr`, `rtl`, `auto`), `lang` (letters, digits and `-`, at most 35), `title`, `align`, `valign`, `class` and `id` (each a list of `[A-Za-z0-9_-]` tokens, for the message's own CSS), `style` (filtered).
- `table`, `tr`, `td`, `th`: `width`, `height`, `border`, `cellpadding`, `cellspacing`, `bgcolor`, `colspan`, `rowspan`, `nowrap`, `scope`, `headers`; `col`, `colgroup`: `span`, `width`; `ol`: `start`, `type`, `reversed`; `li`: `value`; `font`: `color`, `face`, `size`; `time`: `datetime`; `img`: `src` (below), `alt`, `width`, `height`, `border`, `hspace`, `vspace`; `a`: `href` (below), and the `target`, `rel`, `title` and `style` the sanitiser writes. Numbers are non-negative numbers or percentages, colours a `#` and hex digits or a name of letters.
- The message's `<body>` gives its `bgcolor` and `text` to ours, and its `<html>` its `lang` and `dir`.

**Links.** Each `a href` is read as a URL after the WHATWG trimming (leading and trailing C0 controls and spaces removed, tabs and newlines inside removed) and kept only when it matches this grammar exactly, checked by the package's own parser before `net/url` sees it:

- `scheme "://" host [":" port] [path] ["?" query] ["#" fragment]`, at most 4,096 bytes;
- `scheme` is `http` or `https`, in any case, written in lower case;
- no userinfo: no `@` before the path; no `\` anywhere (a browser reads it as `/` in these schemes, Go does not); no `%` in the host (a browser percent-decodes a host, Go refuses it);
- `host` is a DNS name: the host as written goes through `idna.Lookup.ToASCII` (x/net/idna's `Lookup` profile: UTS 46 non-transitional mapping, STD3 rules, hyphen and joiner checks, the Bidi rule), stricter than the WHATWG's "domain to ASCII", which uses the same mapping with `beStrict` false; the result, lower case, must be two to 127 labels of `[a-z0-9-]`, each 1 to 63 characters, not starting or ending with `-`, 253 characters at most, no trailing dot, and its last label must be letters only (`[a-z]{2,63}`) or `xn--` and letters, digits and hyphens. That last rule is what refuses every IP address in every spelling: the WHATWG URL parser treats a host whose last label is all digits, or `0x` and hex digits, as IPv4 (its "ends in a number checker"), so `2130706433`, `0x7f000001`, `0177.0.0.1` and `127.1` all mean `127.0.0.1` to a browser while Go keeps their spelling (`net/url` follows RFC 3986); an IPv6 literal (`[…]`) has no DNS name at all;
- `port`, when present, is 1 to 65535 without a leading zero, and is dropped when it is the scheme's default (80, 443);
- path, query and fragment are written again with every byte outside the URL code points of the WHATWG standard, and every non-ASCII character, percent-encoded as UTF-8, so the stored URL is ASCII and a browser parses it to itself.

A link that does not match becomes its text. A `mailto:` or `tel:` link becomes its text too, with the address written after it in brackets when the text does not contain it: Permaily neither writes mail nor calls, and the sandbox's `allow-popups` would follow other protocols ("What holds each guarantee"). Fragments (`#top`) become text, since they would navigate the frame.

A kept link is numbered in document order of the output (at most 1,000; past that the rest are text) and written as `href="/inbox/<mailbox>/<message>/links/<n>.<tag>"`, `target="_blank"`, `rel="noopener noreferrer"`, `title` set to the canonical URL (so hovering shows it; a `title` is not navigable), and the forced link style below. The address the message wrote is never in an `href`.

**The link's token.** `<tag>` is HMAC-SHA-256, under a key derived with HKDF-SHA-256 from the mailbox's data key with the info `permaily link v1`, over the message identifier, the number `n` and the canonical URL, truncated to 12 bytes and written in unpadded base64url (16 characters). The link route recomputes the walk, finds link `n`, recomputes the tag and compares in constant time: a tag that does not match, or an `n` past the links there now, answers 409 `link_changed`, and the link page says "This link changed since the message was opened. Close this tab, open the message again, then the link." So a link opened from a page rendered by one release never leads to another destination under a later sanitiser. Nothing is stored. Why an HMAC and not a plain truncated SHA-256 of the URL: the link page's address stays in the browser's history and whatever syncs it; a plain hash there would let anyone holding it confirm a guessed destination, which the mailbox's key prevents. The key is already unwrapped for the request that reads the message, and the derivation (purpose `link`) is added to the purposes of `internal/inbox/box.go`.

**Images.**

- `img src` of `cid:<id>` is replaced by a `data:` URI the sanitiser builds from that part of `multipart/related`; `data:image/png|jpeg|gif|webp;base64,` is decoded and rebuilt the same way. Nothing is decoded into pixels and nothing is re-encoded inside the enclave in this version: decoding hostile images there would move a decoder's risk into the enclave, and re-encoding needs a decoder. Metadata such as EXIF stays inside the data URI, which only the frame shows and nothing fetches.
- **Structure, read before anything else**, by a walker in the package that reads headers and chunk or block lengths and no pixel data: PNG (signature, `IHDR` first, then every chunk to `IEND`; an `acTL`, `fcTL` or `fdAT` chunk is APNG), JPEG (markers to the first `SOFn`), GIF (header, logical screen, then every block; more than one image descriptor, or a frame outside the logical screen, is animated or refused), WebP (RIFF chunks: `VP8 ` or `VP8L` alone, or `VP8X` with its animation flag clear and no `ANIM` or `ANMF`). `image.DecodeConfig` alone is not enough: for PNG it reads the 33 bytes up to `IHDR` and reports an 8192 x 8192 image from them, and it says nothing of animation; the standard library has no WebP decoder, and no new dependency is added for one.
- **Shown** only when the bytes are PNG, JPEG, GIF or WebP whatever type the message declared (written with the type found), static, and within the limits. Otherwise a box with its `alt` text, counted in `inline_images_omitted` and in `inline_images_omitted_by` as `too_large`, `animated` or `unsupported` (SVG, any other type, a `cid:` naming no part, a structure that does not read). SVG is never shown as an image.
- `http`, `https` and protocol-relative sources are removed and counted in `remote_images`; anything else is removed.

**Remote images: what the person sees, and why there is no "Load images".** A remote image is replaced by a small bordered box with its `alt` text (or nothing, for an image whose `width` or `height` is 0, 1 or 2 or that is hidden, which is how open-tracking pixels are made: counted, not boxed). Above the frame the app says "3 remote images were not loaded". There is no button to load them, now or as a setting: loading them in the browser tells the sender that and when the message was opened, from which address and with which browser; loading them through the enclave would still tell that and when, and would make the enclave fetch any address, which its egress allowlist forbids (docs/threat-model.md). Any of these needs an ADR of its own.

### CSS

Real mail needs it: tables laid out by inline `style`, colours, fonts, and in newsletters a `<style>` block with `@media` rules for phones. It is kept through an allowlist, and the CSP stays first for fetching.

- **Parsing.** A tokeniser written in the package from CSS Syntax Level 3 (about 400 lines; fuzzed), so escapes such as `\75 rl(` are read as the browser reads them. The output is written from the tokens kept, never the input's text; `<` in it is written as `\3c `, so a `<style>` cannot be closed from inside.
- **The principle**, for any property not listed here: a declaration is kept only when it changes how a box looks or flows in normal order; never where a box is drawn relative to the boxes around it, whether it is drawn, whether it takes the pointer, or what is drawn over what. Nothing may make a link's box invisible or put it over other content.
- **Properties kept**: `color`, `background-color`, `background` (colours and keywords only), `font`, `font-family`, `font-size` (bounded), `font-style`, `font-weight`, `font-variant`, `line-height` (bounded), `letter-spacing`, `word-spacing`, `text-align`, `text-decoration` and its `-line`, `-color` and `-style`, `text-indent` (bounded), `text-transform`, `text-overflow`, `white-space`, `word-break`, `word-wrap`, `overflow-wrap`, `vertical-align`, `direction`, `margin` and `padding` and their sides, `border` and its sides, widths, styles, colours and radii, `border-collapse`, `border-spacing`, `width`, `min-width`, `max-width`, `min-height`, `height` and `max-height` (a length only in a `style` attribute of `td`, `th`, `tr`, `table` and `img`, where a height is a minimum or the box has no children; `auto` anywhere), `display` (`none`, `block`, `inline`, `inline-block`, `list-item` and the `table*` values; not `flex`, `grid` or `contents`), `float` (`left`, `right`, `none`), `clear`, `table-layout`, `caption-side`, `empty-cells`, `list-style-type`, `list-style-position`, `overflow`, `overflow-x`, `overflow-y`, `box-sizing`.
- **Removed**, besides everything not listed: `position` (every value), `top`, `right`, `bottom`, `left`, `inset*`, `transform`, `translate`, `rotate`, `scale`, `z-index`, `opacity`, `visibility`, `clip`, `clip-path`, `mask*`, `pointer-events`, `mix-blend-mode`, `filter`, `backdrop-filter`, `content`, `cursor`, `outline*`, `box-shadow`, `text-shadow`, `order`, `grid*`, `flex*`, custom properties and `var()`, `behavior`, `-moz-binding`, `expression`, every `*-image`, `animation*`, `transition*`, `color-scheme` and `mso-*`.
- **`float` stays.** Mail built for every client lays out with tables, since Outlook on Windows ignores most of CSS, but real newsletters and receipts float an image beside its text or a logo to one side, and two-column blocks fall back to floats where tables are not used. Without `position`, negative values and fixed heights, a float cannot put a box over another's content: the line boxes beside a float are shortened around it (CSS 2.1, 9.5), so its text and links move aside instead of being covered. Dropping it would make that mail read in one column with images above their text, which is readable; keeping it costs nothing of the principle.
- **Values**: identifiers, numbers, percentages, dimensions in `px em rem % pt pc cm mm in ex ch vw vh`, `#` colours, strings (in `font-family` only), commas and `/`; functions `rgb() rgba() hsl() hsla()` only. No negative number anywhere (that removes negative margins and the `text-indent: -9999px` trick); `font-size` from 6 to 96 px, 5 to 72 pt, 0.5 to 6 em or rem, 50 to 600 % or a keyword; `line-height` `normal`, or 1 to 3 unitless, em or 100 to 300 %, or 10 to 150 px; `text-indent` at most 160 px or 10 em. A declaration outside these, or with any other token (a `url()`, another function, `@`, `\` left after unescaping), goes; a `url()` of `http`, `https` or `//` is counted in `remote_images` (in image properties) or `remote_other`.
- **`!important`** is removed from `style` attributes and kept in `<style>` rules, where newsletters need it for their `@media` rules to beat inline styles.
- **Rules of a `<style>`**: style rules whose selectors are made of type, `#` and `.` names, `*`, combinators, attribute selectors and the pseudo-classes `:first-child :last-child :nth-child() :nth-of-type() :not()` (of simple selectors) `:link :visited :hover`; `@media` with a prelude of media types, features and `and`, `not`, `only`, commas, its rules filtered the same way. Every other at-rule goes, `@import` and `@font-face` among them (counted in `remote_other` when they name an address), with `@charset`, `@namespace`, `@keyframes`, `@supports`, `@page`, `@layer`, `@container` and `@property`.
- **What each link carries.** The sanitiser removes from the link's own declarations every property below and writes them after, with `!important`, in the link's `style` attribute: `display: inline-block; max-width: 100%; overflow: hidden; color: #1a4fd6; background-color: #fff; text-decoration: underline; font-size: max(1em, 12px); line-height: normal; letter-spacing: normal; text-indent: 0`. A declaration attached to the element with `!important` wins over every rule of a stylesheet, `!important` ones included (CSS Cascading and Inheritance Level 5, "Cascade Sorting Order", element-attached styles), so nothing the sender wrote changes how a link looks: underlined, the renderer's blue on white, in its own box that holds what it draws and fits its container. Bulletproof buttons (a styled `<a>` in a coloured cell) show as an underlined link on white in that cell: readable and honest.
- **The frame's stylesheet, after the sender's**: `html { color-scheme: light; background: #fff; color: #111 } body { margin: 16px; font: 16px/1.5 system-ui, sans-serif; overflow-wrap: anywhere } img { max-width: 100% !important; height: auto } table { max-width: 100% !important } a img { border: 0 }` and the box of an image not shown. The same canvas properties are also written in our `<html>` element's `style` with `!important`, so the sheet is white whatever the sender's rules say; the body's own colour stays the sender's (`bgcolor`, `text`, CSS). System fonts only: the frame can load none.

When the HTML is `too_large` or `unreadable`, the app shows the text with a line that says why, and "Download original". When it is `unavailable`, the text with "The formatted view isn't available right now. Try again in a moment." and "Try again".

`Message.html` and both routes render on read: every request parses the raw message again, and the same image gives the same output on every enclave. Nothing is stored or cached: no sanitised HTML, no image, no link. `GET message` renders into a counting writer to know the status and the counts; the frame's route renders the document; the link route runs the token pass, the parse and the walk with images, CSS and output skipped (`mailhtml.Links`), sharing the walk's code with `Render`, so its numbering is the frame's by construction. Each takes a render slot. Nothing changes for an operator or a second enclave; there is no new record, entry or key.

### Text, honestly labelled

The message view has two views, "Formatted" and "Text" (two buttons with `aria-pressed`), Formatted first when `html.status` is `shown`. The choice is kept in the app's memory for the session, never in storage. A message with no HTML part shows text and no switch. The sender controls the text part independently of the HTML, so the Text view says which it shows:

- A message with both (`text_from: plain` and `html`): "This is the plain-text version the sender included. It may differ from the formatted one."
- A message with only HTML (`text_from: html`): "This is the text of the formatted message, without its formatting."
- A message with only text: no note.

Search reads the first 16 KiB of the same text the Text view shows (`txt#` holds text, never HTML), so in a message with both, a word that is only in the HTML is not found. The Text view is the one to use where the frame cannot help: a screen reader that handles frames badly, a dark page, a message whose formatting hides things.

### Dark theme, height, keyboard, zoom

- **Colours.** Mail is written for a white page, so the frame is always a white sheet in both themes, inside the app's border. Nothing is inverted: inverting colours breaks logos, images and mail that has its own dark design. The Text view follows the app's theme.
- **Height without scripts.** A frame with no script cannot report its height, and its opaque origin hides its document from the app, rightly. The message view is a column filling the viewport: the compact head (sender, subject, date, "Details" for recipients and signatures, the switch, the notes), the label, and the frame, which takes the rest of the height (`flex: 1`, at least 24 rem) and scrolls inside itself. Nothing the message says sets a size the app uses.
- **Keyboard and screen readers.** The page's focus goes to the subject, the `h1`, as on every page; Tab goes through the head's controls, then into the frame's links in order, then out. A link is announced by its text; its `title` is the canonical URL. Images keep their `alt`; the box of a remote image says "Remote image not loaded" and its `alt`; the box of an image not shown says why ("Image too large", "Animated image not shown", "Image not shown").
- **Zoom.** The browser's zoom and text size apply inside the frame. No animation reaches the frame: animated images are not shown and CSS animations are dropped.

### Routes

| Request | Needs | Answers | Errors |
|---|---|---|---|
| `GET mailboxes/{id}/messages/{message}/html` | a session; when any `Sec-Fetch-*` header is sent, `Sec-Fetch-Dest: iframe` and `Sec-Fetch-Site: same-origin` | 200 `text/html; charset=utf-8`, the document, with the frame's headers | 404 when the message is not the account's, has no HTML that is `shown`, or the request is not a frame's; 401; 429 (the account's share, "Admission"); 503 (busy); 500. Every answer has the frame's headers and a fixed HTML body ("This message can't be shown here."), never JSON and never text from the message |
| `GET mailboxes/{id}/messages/{message}/links/{link}` | a session | 200 `MessageLink`: `{link, url, host, shown?}` | 404 `not_found` for a `{link}` that is not `<n>.<tag>` or a message that is not there; 409 `link_changed`; 429; 503 `busy` |

`{link}` is `<n>.<tag>`: `n` in decimal without leading zeros, below 1,000, and the 16-character tag. `MessageLink.url` is the canonical URL; `host` is its host and, when not the default, `:port`, exactly as the WHATWG `URL.host` writes it; `shown` is the host the link's text named when it named another one.

### The link page

`/inbox/:mailbox/:message/links/:link`, inside `RequireSession`, opened in a new tab by the frame's link. That tab was opened from the frame's opaque origin, so its first request is cross-site: it carries the `Lax` device and provider cookies and not the `Strict` session (Playwright's WebKit sends the session too), and needs neither (the app's page is static). Its calls to the API are made by the app's own top-level document, same-site, and carry the session (release evidence: "the new tab's session").

It asks `GET .../links/{link}`, then parses `url` with the browser's own `new URL()`, requires `protocol` to be `http:` or `https:` and `URL.host` to equal the server's `host` (a disagreement shows "This link can't be opened from Permaily." and no button), and uses that one `URL` object for everything it shows and for where it goes. It shows:

- "This link leads to" and the host (`URL.hostname`, ASCII, an `xn--` form as it is), large; the port after it when there is one; and the scheme ("https", or "http, not encrypted");
- the whole address (`URL.href`) in monospace, breaking anywhere, as text, never a link, inside a left-to-right isolate (`<bdi dir="ltr">`), with any code point outside printable ASCII written as `\u{…}` (the server writes ASCII only, so this is a second line);
- when `shown` is set: "The message showed <shown>, but this link leads to <host>.";
- "Opening it tells <host> that the link was followed, and when. The address itself may tell them who you are. Nothing is sent to <host> until you press Open.";
- a `<button>` "Open <host>", and "Back to the message", a link to the app's message view.

Pressing the button calls `window.open(url.href, '_blank', 'noopener,noreferrer')` from its click handler, then the page says "Opened in a new tab. You can close this one." The destination is in no `href`, no `src`, no prefetchable attribute and not in the address bar before the button is pressed. A middle-click, "Open in new tab", a long press or a link preview on the button does nothing: a button is not a link. The button is reached by Tab after the address and "Back to the message" comes after it; a screen reader announces "Open <host>, button"; Enter and Space press it; focus starts on the page's `h1`, "This link leads to <host>". On `link_changed`, `not_found`, `busy` or a failed `new URL()`, the page says so and offers no button.

This is the second place the app leaves for another site, always for an address the server answered and the browser parsed, never for one read from the app's address bar; `web/AGENTS.md` names it with the fifth pull request.

### The release gate

A release that shows HTML ships only when every check of docs/acceptance.md, "F2 step 2: showing a message's HTML", has passed in the real browsers it names and is recorded there with the browser versions and the date. ### What this rests on (looked up on 2026-11-12)

- HTML, sandboxing: the sandboxed navigation flag stops a frame navigating others but not itself; the sandboxed origin flag gives an opaque origin; the automatic features flag, set without `allow-scripts`, keeps a `<meta>` refresh from navigating; the custom protocols navigation flag is unset by `allow-popups` (and `allow-top-navigation*`); "sandbox propagates to auxiliary browsing contexts" is unset only by `allow-popups-to-escape-sandbox` (https://html.spec.whatwg.org/multipage/browsers.html#sandboxing, "parse a sandboxing directive"; https://html.spec.whatwg.org/multipage/semantics.html#shared-declarative-refresh-steps).
- HTML, policy containers: an `about:srcdoc` document takes a clone of its parent's (https://html.spec.whatwg.org/multipage/browsers.html#policy-containers).
- CSP Level 3: `frame-src` falls back to `child-src` and then `default-src`; `frame-ancestors` does not fall back; resource hints only to listed sources; `sandbox` is not honoured in `<meta>` (https://w3c.github.io/webappsec-csp/).
- WHATWG URL: the host parser percent-decodes a host before "domain to ASCII"; "domain to ASCII" runs UTS 46 with `CheckBidi` and `CheckJoiners` true, `Transitional_Processing` false, and `CheckHyphens`, `UseSTD3ASCIIRules` and `VerifyDnsLength` set to `beStrict` (false for a URL); the "ends in a number checker" sends a host whose last label is all digits, or parses as an IPv4 number (`0x` hex, leading-zero octal), to the IPv4 parser; `\` is a path separator in special schemes (https://url.spec.whatwg.org/#host-parsing, #concept-ipv4-parser).
- Go: `net/url.Parse` keeps `2130706433`, `0x7f000001` and `0177.0.0.1` as hosts, refuses `%6D` in a host, and refuses `\` in userinfo; `idna.Lookup` is non-transitional (`transitionalLookup = false`), with STD3 rules, hyphen and joiner checks and the Bidi rule, and refuses `ab--cd` and `a_b`; `image.DecodeConfig` reports 8192 x 8192 from a 33-byte PNG header; `charset.DetermineEncoding` reads 1,024 bytes, puts a BOM first, and falls back to Windows-1252; `html.Parse` refuses more than 512 open elements; `reconstructActiveFormattingElements` clones every active formatting element not on the stack (x/net v0.62.0, Go 1.26, run and read on 2026-11-12).
- CSS Cascading and Inheritance Level 5, "Cascade Sorting Order": element-attached declarations win over rule sets of the same origin and importance (https://www.w3.org/TR/css-cascade-5/#cascade-sort); CSS 2.1, 9.5: line boxes next to a float are shortened (https://www.w3.org/TR/CSS21/visuren.html#floats).
- MDN: `Sec-Fetch-Site` and `Sec-Fetch-Dest` Baseline since March 2023 (Safari 16.4) (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site); `<iframe>` and its sandbox tokens (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).
- web.dev, back/forward cache: pages with `Cache-Control: no-store` have historically not been cached, Chrome is changing that; `pageshow`'s `persisted` (https://web.dev/articles/bfcache).
- Apple, Safari on iPhone: touch and hold a link to preview it (https://support.apple.com/guide/iphone/browse-the-web-iph1fbef4daa/ios); the preview loads the page.
- Requests from a sandboxed frame's opaque origin are cross-site (https://github.com/sbingler/schemeful-same-site, https://github.com/w3ctag/design-reviews/issues/1004).
- Not settled by reading, and therefore in the release gate: each browser's cookies on the frame's request and on the link page's tab, `<link rel=preconnect>` under `default-src 'none'`, and the image limits on a phone.
