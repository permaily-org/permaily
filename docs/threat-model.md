# Threat model

## What verification proves

That the service answering on the Permaily hosts runs an enclave image built from a specific public commit, and that your TLS connection terminates inside that enclave. It does not prove that the code is correct or free of bugs; it proves that the code you can read is the code that runs.

## Trusted

- **AWS Nitro hardware and hypervisor**, the Nitro Security Module and the AWS Nitro Enclaves root certificate (pinned by fingerprint in `pkg/attestation`).
- **AWS prebuilt enclave kernel, init and nsm.ko** from aws-nitro-enclaves-cli (pinned by hash in `nix/aws-blobs.nix`, each binary described in `nix/aws-blobs.json` and checked in every image CI builds).
- **The source code and its pinned dependencies**: Go modules (`go.sum`, `vendorHash`), npm packages (`bun.lock` and the `node_modules` hash), nixpkgs (`flake.lock`).
- **Let's Encrypt** for issuing certificates to the enclave's key, and the public WebPKI for the verifier's TLS checks and for the enclave's connections to KMS.
- **Sigstore's public instance** (Fulcio, the Rekor transparency logs and, for entries of Rekor v2, the timestamp authority that says when a signature existed; all pinned in `pkg/provenance`; three of the five keyholders of Sigstore's TUF root can give a running enclave other logs and timestamp authorities, never another issuer of certificates, ADR 0013) and **GitHub Actions** (its token issuer, its hosted runners, and the rule that `main` only changes through reviewed merges): together they say which images are public releases, and a running enclave hands the root secret only to those.
- In later phases: the LLM provider used for classification (model and prompts are in the image).

## Not trusted

- **The parent EC2 instance and its operator.** It sees only ciphertext and destination hostnames. It can drop, delay or replay traffic, and stop the service; it cannot read or alter content without the verifier detecting it.
- **DNS (Cloudflare) and the network.** A hijacked record points clients elsewhere; the verifier detects it because no other server can present a TLS key bound into a valid attestation. The zone is signed with DNSSEC, so a resolver that validates refuses records forged on the way; whoever controls the Cloudflare account controls the zone all the same.
- **Anything the parent supplies at runtime.** The enclave takes no configuration from the parent; hosts and the ACME directory are compiled into the image.

## Mechanisms

| Threat | Mitigation |
|---|---|
| Service runs different code | PCR0-2 in a fresh, AWS-signed attestation must equal the PCRs reproduced from source |
| Debug mode (console access, PCRs zero) | the verifier rejects all-zero PCRs |
| Replay of an old attestation | random 32-byte nonce per verification, 5-minute freshness window |
| TLS terminated outside the enclave (MITM, parent, CDN) | attestation `user_data = sha256(SPKI)` of the certificate on the same connection |
| Certificate for the hosts issued to someone else | detected per connection by the binding above, so only for people who verify: a browser accepts any valid certificate. CAA restricts the hosts to Let's Encrypt and forbids wildcards for the domain; Cloudflare Universal SSL is off and the site has an exact-name certificate (ADR 0012). CAA names the enclave's ACME account, whose key is sealed, and `permaily-verify` reads Certificate Transparency and fails on a certificate for the hosts with another key issued since the enclave's key exists (`pkg/certwatch`). Four wildcards issued before 2026-11-10 with keys at Cloudflare and AWS stay valid until 2027-05-26 at the latest. DNS is the operator's, so CAA can change between checks; Certificate Transparency shows it afterwards |
| Build tampering in CI | anyone can rebuild; CI builds on x86_64 and arm64 and compares; releases carry Sigstore provenance |
| Supply chain of dependencies | all inputs pinned by hash; review dependency changes |

## Known limits (F0)

- The TLS key and the ACME account key are created once inside an enclave and stored sealed under the root secret (ADR 0012, ADR 0013), so restarts and upgrades keep the same key, certificate and account. Only what can get the root secret can open them, like stored mail.
- The enclave keeps nothing itself: what it stores is sealed and lives in DynamoDB and S3, which the operator can delete, not read. Putting back an earlier copy is refused for the records that go through `store.Anchored` (ADR 0016): today the TLS identity. The mailbox's state and the messages can still be put back to an earlier copy, or removed; they get the same protection, and an audit log, with the data model.
- Availability is not protected: the operator can always take the service down.
- Metadata visible to the operator: connection timing, sizes, destination hostnames of egress.

## Egress allowlist

The host proxy only tunnels to:

| Destination | Why |
|---|---|
| `acme-v02.api.letsencrypt.org:443` | certificate issuance |
| `acme-staging-v02.api.letsencrypt.org:443` | test deployments |
| `kms.us-east-2.amazonaws.com:443` | mailbox data keys (Recipient with attestation) |
| `dynamodb.us-east-2.amazonaws.com:443` | sealed mailbox and message records |
| `s3.us-east-2.amazonaws.com:443` | sealed raw messages (path-style requests) |
| `cloudflare-dns.com:443` | DNS-over-HTTPS for DKIM lookups, so the host cannot forge DNS answers |
| `email.us-east-2.amazonaws.com:443` | SES: the service's own mail (sign-in messages), and reading who else could get a copy of it |
| `oauth2.googleapis.com:443`, `www.googleapis.com:443` | Signing in with Google: the code for an ID token, and the keys it is signed with |
| `github.com:443`, `api.github.com:443` | Signing in with GitHub: the code for an access token, who holds it and their verified address |
| `graph.facebook.com:443` | Signing in with Meta: the code for an access token, and who holds it |
| `login.microsoftonline.com:443` | Signing in with Microsoft: the code for an ID token, and the keys it is signed with |

## Mail (F1)

- **Root secret.** Everything stored is sealed under data keys, and every data key is wrapped under one root secret created inside an enclave (ADR 0013). Outside enclaves the root secret exists only in records, one per image, each locked by a KMS key that belongs to that image alone.
- **Keys nobody in the account can open or change.** The policy of an image's KMS key lets only an enclave that proves that image (PCR0) decrypt, and gives nobody `kms:PutKeyPolicy` or `kms:CreateGrant`, so KMS refuses to change it: account administrators were denied `PutKeyPolicy`, `CreateGrant`, `Decrypt`, `Encrypt`, `DisableKey`, `ReplicateKey` and more on such a key (checked 2026-11-10). Anyone in the account can create a data key under it, which gives them nothing: see the next point.
- **Only public releases receive the root secret.** An image accepts a record only with an AWS-signed attestation document from the enclave that wrote it, which must have run the same image or a public release, proved by that release's Sigstore bundle. The running enclave writes a record only for a release that was published, in the public transparency log, after itself, and whose key passes the check above. So neither a private image nor a record made by the operator gets the root secret, whoever asks.
- **Pinned account.** The AWS account and region are compiled into the image and every key must be in them; every KMS answer must name the key that was asked (`keys.ErrKeyMismatch`). The host supplies the AWS credentials (its own instance role); credentials for another account cannot make the enclave use a key elsewhere.
- **Encryption.** Message metadata, raw message and mailbox state are sealed with AES-256-GCM plus a key commitment, bound to mailbox, message id and purpose (`internal/envelope`).
- **What the operator sees.** Message sizes and arrival times, retention period, the number of messages, and of each mailbox its account, state and dates (ADR 0026; until its release, the single test mailbox). Not addresses, labels, senders, subjects, bodies or attachments.
- **Transport.** SMTP STARTTLS terminates in the enclave with the attested certificate, and the MX refuses `MAIL` on a connection without TLS. MTA-STS (`mode: enforce`) tells senders to deliver only to `inbox.permaily.com` with a valid certificate; TLS-RPT reports go to the mailbox `tls_rpt_address` names (`deploy/tofu`), an ordinary mailbox the super admin makes after the release that retires the test mailbox; until it is set no TLS-RPT record is published. `permaily-verify` checks the policy (served with the attested key), the `_mta-sts` and MX records, and that port 25 answers with the attested key (ADR 0011).
- **Gap: senders without MTA-STS, and DNS.** A sender that does not implement MTA-STS can be made to deliver in clear to whoever answers on port 25. DNS is the operator's: removing the `_mta-sts` record stops new senders from applying the policy (cached policies last a week); the verifier fails when it is missing.
- **Port 25 between manual checks.** The scheduled verification cannot reach port 25 (GitHub's runners block it), so the certificate served there is only checked by hand, from a server, with `-require-smtp`. Decided on 2026-11-11 to leave it so: a certificate for the host with a key outside the enclave shows in the certificate check, which runs every half hour, and what stays unwatched is the gap above, for senders without MTA-STS.
- **Senders.** Any sender may deliver to an address they know; DKIM results are recorded with each message. A Gmail forwarding confirmation is marked verified only by the checks below ("Senders", ADR 0026), and none is until the mark is turned on.
- **Who can use the key is public.** The enclave reads the policy, the grants and the properties of its image's key from KMS and serves them on `/status`; `permaily-verify` accepts that only over the attested TLS key and applies the same rule the enclave does (`kmspolicy.Sealed`): this image only, no way to change the policy from the account, no grants, key material that never left KMS.
- **The policy between checks.** AWS documents that its Support can restore the account owner's access to a key that nobody can manage. So the enclave reads the policy and the grants of its key once a minute and reports every state it has seen since it started; the verifier requires a reading made just now and checks every state, and a public job runs the verifier every half hour (ADR 0013). That job is started from the operator's AWS account, with a GitHub token that can start, cancel and delete workflow runs of this repository and nothing else; so the operator chooses when it runs, and GitHub's own schedule, which the operator does not time, starts it a few times a day as well. What remains: a change made while the enclave is cut off from KMS shows only as a gap, and restarting the enclave starts the history again (the start time is printed).
- **What remains.** An older release can still open its own record until its key is deleted, so a flaw in an old image stays a way in for that long (docs/operations.md). Whoever controls Sigstore's signing or GitHub's runners for this repository can publish an image that is accepted; it would be public in the transparency log and in the repository. The account's owner, with AWS Support, could regain control of a key and then open the root secret; it takes a support case and shows in the enclave's report from then on. The operator can still delete keys or records, which destroys data and reads nothing.
- **The old mail key.** Releases up to v0.6.0 wrapped data keys with `alias/permaily-mail`, whose policy administrators could replace. v0.7.0 moved those data keys under the root secret, the key was retired on 2026-11-10 with a policy that lets nobody use it, and it is scheduled for deletion.

## Accounts (F2)

- **The storage is not a way into an account.** An account's record is readable and signed with a key that comes from the root secret, and read through `store.Anchored`; sessions and invitations are signed with where they are stored and kept by the hash of their secret; a sign-in that was started is sealed in the storage and works once, and its count of wrong codes is in each enclave's memory (ADR 0017). So whoever runs DynamoDB and S3 can read who has an account, and can delete accounts, and cannot add a way to sign in, bring a removed one back, or make a session.
- **What the operator sees.** Contact addresses, names, dates, which ways each account signs in with, how many sessions it has and when each was used. That is the promise: account data is seen, mail is not.
- **Sign-in by mail trusts three parties.** The person's own mail provider, which can read the message; AWS, which carries it (SES); and, in part, whoever administers the AWS account, as the next point says. An account in "passkey only" mode trusts none of them.
- **A copy of the mail the enclave sends.** The message with the code and the link goes from the enclave to SES over TLS, so the host does not see it. An administrator of the AWS account can make SES keep a copy of everything sent: a configuration set tied to an archive, set as the default of the identity. With the copy of a sign-in message they would enter the account. The enclave never names a configuration set, so it reads from SES whether one applies to the domain it sends from, or to the address (whose settings would win over the domain's): before a message unless it read within the last five seconds, after each message, and once a minute. It sends only while the answer is that none applies and the answer can be had. Every state it saw since it started is on `/status`, and `permaily-verify`, which runs every half hour, fails on one that was ever not clean (ADR 0021).
- **What that leaves.** It is noticed, not prevented: nothing in AWS stops an administrator from changing those settings. A configuration set put in place and taken away between two readings, in the moment a message leaves, is not seen; the readings around each message leave about a second for it, up to six when many messages leave at once, where a watch once a minute would leave a minute. Restarting the enclave starts the history again (the start time is printed). A way to copy outgoing mail that AWS adds later, or one this does not read, is not covered. AWS itself reads the message in any case.
- **Other settings of SES are not read.** A notification topic on the identity can carry the headers of a message, so the subject of a sign-in message is fixed text and never holds the code or the link. A message that bounces is sent back to the sender's address, whose mail the operator could receive by adding an MX record: that copy exists only for a message that did not reach the person. Sending authorization lets others send, not read.
- **A link sent by someone else.** Someone can start a sign-in for their own account and send its link to another person, to have them act inside an account that is not theirs (connect their mailbox to it, for one). So opening the link signs nobody in: the page asks the enclave whose sign-in it is (`POST /api/v1/auth/email/look`, which ends nothing), shows the address, says not to go on with a link someone else sent, and signs in only when the person says so. What is left is a person who reads another's address and goes on all the same.
- **The HTML of the mail the enclave sends** (ADR 0025). Every message goes as plain text and as HTML with the same words, both written in the enclave from one list of blocks, through the templates committed in `internal/domain/mail/templates` (covered by PCR0; React Email only writes them, at authoring time). The HTML fetches nothing (no image, font, stylesheet or script, no `url(...)`), so opening a message tells nobody that it was opened or from where. Its only link is the one the text shows (the sign-in link, behind a button labelled "Sign in", with the address in full under it as text); a notice, and a message with a code that deliberately has no link, has none in the HTML either. Every value is escaped by `html/template` in its context, and no account, session or attempt identifier is in the markup. Tests hold each of these on every message (`internal/domain/mail`). A mail client's own handling of HTML is trusted as it is for any other message the person receives.
- **Mail in Permaily's name proves nothing.** The parent instance holds the role the enclave sends with, so the operator can send mail from the same address without the enclave; DNS is the operator's too. A message from Permaily is not proof that the enclave wrote it. What a sign-in message leads to is: the link opens `app.permaily.com`, where the verifier's check applies, and the code is only good in the browser that asked for it.
- **Passkeys.** What the browser answers is checked by this repository's own code (`internal/webauthn`): the challenge the enclave gave, the app's origin and host, the person present and verified, and the signature of the key kept in the account's record. No attestation is trusted, so which device holds a key is not known, and the signature counter is not kept, so a copied authenticator is not noticed by it. A ceremony is sealed in the storage, works once and for five minutes. Signing in with a passkey asks for no address and its failures are all the same, so it tells nobody who has an account. Trusted here, besides the code: the browser and the authenticator of the person, and for synced passkeys whoever syncs them.
- **Two enclaves at once.** One runs today, and accounts are ready for two behind one address (ADR 0017, "Two enclaves at once"). A change to an account's record is written only if nothing was committed for the record since it was read, so two enclaves do not undo each other's change (a passkey removed stays removed, a recovery code works once) and neither brings back an account the other removed. Whoever writes to the bucket of commits can still, in the moment between two changes, add a commit where one is and lose one of the two; the enclave whose commit does not count says so in `/status` (ADR 0016). A sign-in started through one enclave ends through the other: it is an entry sealed with a key from the root secret, so whoever reads the table learns nothing of it (no address, no code or hash of one, no token, challenge, verifier, state or nonce), and it works once: a mark written only where none is decides which enclave ends it, and a copy put back is refused while the mark is there, and always by the enclave that ended it. Whoever deletes the mark and puts the copy back can have it end once more in each other enclave, for whoever holds its code or link, within its ten minutes. An enclave ends nothing made before it started, so restarting one gives no tries back. The counts of tries and messages are in each enclave's memory, on purpose: with two, each is at most twice what it says. A cancelled deletion is not carried out by an enclave that read the account as due a moment before, a session made in the moment every device is signed out stands for nothing, and one provider account ends linked to one account. What `/status` says is the enclave's that answered (the mail watch, the key policy, the commits it saw, the counts of what the operator and the admins did): whoever verifies a deployment with several enclaves has to reach each.
- **Two enclaves and the TLS identity** (ADR 0024). Both serve one key. The one that asks the CA writes a claim into the sealed identity, only if nothing changed since it read it; the other waits and serves what it stores. Whoever writes to the storage cannot make a claim, so cannot stop an enclave from renewing other than by withholding the storage, which stops everything anyway. They cannot make an enclave serve a certificate it did not get either: a stored certificate is taken only for the key the enclave already holds, and an identity with another key is refused until a restart. While an order is open, the certificate and the private key that answer the CA's check are in the table, sealed under the identity's data key and with their end sealed in them. In the clear they would give nothing either: the certificate is sent to anyone who asks the enclave with `acme-tls/1`, and answering the check only helps the enclave's own ACME account, whose key is sealed. A mailbox is made once (`CreateNew`) and every change of it written at the version read, so two enclaves use one data key (ADR 0026).
- **"Passkey only" and recovery codes.** With the switch on, mail no longer signs in, so neither the person's mail provider, nor SES, nor whoever administers the AWS account is a way into the account. The ten recovery codes are kept by their hash in the anchored record: one that was used does not come back, and whoever writes to the storage can neither add one nor turn the switch off. Five wrong codes an hour for an address, counted in memory, which a restart sets back.
- **Signing in with a provider** (Google, GitHub, Meta, Microsoft). The provider is trusted for the accounts linked to it: one that lies about who signed in takes them, and so does one that says an address is verified when it is not, for an account with that address that never linked it. What the provider says reaches the enclave over TLS that ends inside it, and Google's and Microsoft's is signed besides, checked by this repository's own code (`internal/idp`). The answer is ended only in the browser that started it (a cookie for that browser alone), so one carried to another person signs nobody in. An address is believed only where the provider vouches for it: Google and GitHub when they say verified, Microsoft only for a verified domain or a personal account, Meta never; otherwise it is confirmed by a message with a code. Nothing of the provider is kept but which one and which subject. "Passkey only" turns providers off for that account.
- **The providers' secrets** are given to the enclave by the operator with the admin token and kept sealed under the root secret, in an anchored record: not in the image, the table or a log. The operator knows them, having registered the applications; with them nobody can make an ID token or stand in for the provider, whose answers come over TLS the host cannot open. Whoever holds the admin token can replace an application with one of their own at the same provider, which lets them sign in as nobody but themselves there.
- **What a provider's answer puts in the address.** The callback sends the browser to a path of the app with a fragment: `#provider_confirm`, or `#provider_error=<reason>` and, when the enclave still knew the trip, `&provider=<id>`. A fragment reaches no server and no other site. The reason is one of seven fixed codes and the provider one of four fixed identifiers, the one this browser asked for itself, so neither tells a stranger whether an address or a provider account has an account here. Anyone can write an address, so the web app believes nothing of it: a reason and a provider it does not know are dropped, both only ever become fixed words, and "linked" is said only when the server's own list agrees. The worst a made-up address does is show one of those fixed sentences.
- **What the web app keeps in the browser.** The session is the server's `HttpOnly` cookie, which scripts cannot read. No code, token, invitation, address or account id goes to `localStorage`, `sessionStorage`, the address bar or the history, with two exceptions that hold no secret and name nobody. `localStorage` keeps, besides the theme, the day a closing account is removed, while the app sees that account closing (`permaily-closes-at`): once the day has passed and nobody is signed in, the sign-in screen says once that an account used in this browser was deleted on that day, and forgets it. Someone else who uses the same browser profile learns that much and not whose account it was; cancelling the deletion or seeing an account that works forgets it sooner. `sessionStorage` keeps an invitation only while the browser is away at a provider (`permaily-invitation`), written when it is about to leave and taken out as soon as the app loads again, whatever the outcome. An invitation is a one-use code that names nobody, the storage ends with the tab, and a script that could read it could as well read the page's memory, where it was before. Both are read back only as what they are (a date this app wrote, twelve characters of the invitation alphabet); anything else is dropped unread.
- **Deleting an account.** It ends seven days after the person asks, and what is removed does not come back: the newest commit of its record says it is gone, so an earlier copy of the record, of its pointer or of its sessions put back in the table brings nothing back. Whoever runs the storage can delay a removal by taking the account out of the list of what is closing, only until someone tries to use it; and can hide an account from the operator's tool by taking it out of the list of accounts. Neither list can show an account that is not there or remove one that is not due: what counts is the signed record.
- **Agreeing to the terms** (ADR 0017). Which version of the terms an account's person agreed to, and when, is in the account's signed record: whoever writes to the table cannot make an account look agreed, or not, without the record failing to verify, and an earlier copy is refused like any other. The agreement given at the start of a sign-up travels sealed in the sign-in in progress, with its invitation, and is checked again where the account is made: whoever writes to the table cannot add an agreement to an attempt or a trip, nor move one between them, without it failing to open. The gate that asks again is the server's: an account that did not agree to the version in force changes nothing but what lets its person leave. The links to the terms lead to the public site, in a new tab; the app loads nothing from it.
- **The operator's tool** (`/v1/admin/accounts`, with the admin token) shows what the enclave reads from signed records. Whoever holds the admin token sees every account's address, name and state, which whoever runs the storage sees already.
- **What the operator can do to an account, and what not.** With the admin token the operator blocks and unblocks an account, asks to delete one and cancels a deletion the operator asked for (one the person asked for is theirs alone to cancel: `not_cancellable`), signs its devices out, and lists and revokes invitations (ADR 0017). All of it keeps people out or lets them back; none of it lets the operator in. There is no route to change a contact address, add or remove a way to sign in, turn "passkey only" off or sign in as someone, and the handlers of the operator's routes are given a service that has no such method, so a route added by mistake could not do it either. The cost is accepted: someone who lost their mail, their passkeys and their recovery codes cannot be given the account back.
- **The admin token is a way to keep everyone out.** Whoever holds it can block every account and ask to delete every account. A block is undone by unblocking. A deletion takes seven days, its person is told by mail and can cancel from the app unless the account is blocked too; blocked and deleted together, only the operator can stop it. This is the operator's power over availability, which whoever runs the storage has already by deleting records.
- **What the operator does is visible, by kind.** The enclave counts each kind of action, the token's and the admins' together (with `admin_made` and `admin_removed`, and `mailbox_paused` and `mailbox_resumed`), and serves the counts on `/status`, which `permaily-verify` prints twice an hour; each is logged by its kind. Never which account. The count is in one enclave's memory: a restart, which the operator can cause, starts it again, and the time it started is printed. It shows that accounts were blocked or deleted, not whether it was right to.
- **A blocked account, from the outside.** That an account is blocked is told only to whoever just proved who they are (the code or the link of a message, a passkey, a provider's answer, a recovery code). Before that, every answer is the same as for an account that is not blocked, or for no account: a sign-in message is sent, a wrong code is a wrong code. So a block tells nobody that an address has an account. A session of a blocked account is nothing, also one put back in the table: every request reads the signed record, and a block that was undone by writing an earlier copy of the record is refused as any earlier copy is.
- **Changing the contact address.** The new address is proved with a six-digit code sent to it, with the limits of signing in by mail, and the attempt works for that account and that change alone: it signs nobody in. Asking answers the same for every address, and that an address is another account's is said only to whoever typed the code sent there. Asking needs a fresh proof (the next point), so a stolen session moves the account to an address of the thief's only within ten minutes of a sign-in or a confirmation; the old address is told, and support can block the account and cannot give it back (ADR 0017, ADR 0022).
- **Confirming again.** Adding or removing a passkey or a provider, "passkey only", recovery codes, a new contact address, deleting the account and every change an admin makes need a proof of who the person is from the last ten minutes: the sign-in itself, a passkey of the account, or a code sent to its contact address unless it is "passkey only" (ADR 0022). When it was made is in the session's entry, signed: whoever writes to the table cannot make a session fresh, and putting back an earlier copy of the entry only makes it less fresh. What is made to confirm (an attempt, a ceremony) confirms that session alone and signs nobody in, and is kept like a sign-in: sealed, once. A stolen session is still a way to make these changes for the minutes its proof lasts, and by mail for whoever also reads the person's mail.
- **Admins** (ADR 0022). The super admin is whichever account has, as its contact address, the address compiled into the image (`super_admin`, `hello@permaily.com`): worked out from the signed record each time, never stored. Other admins are named in their signed records, set only by the super admin through the enclave. Nothing written in the table makes an admin. An admin acts only while the account is "passkey only", so neither the admin's mail provider, nor SES, nor whoever administers the AWS account, nor a provider that lies, is an admin; until the super admin's account is "passkey only", whoever reads `hello@permaily.com` is the super admin. Admins act through the same narrow service as the operator's token, which has nothing that changes an address or a way in; an admin who is not the super admin acts on no admin's account and sets no provider's application; nobody blocks or deletes the super admin's account there. Someone who is not an admin gets the same 404 on every route of the panel. An admin's power is the operator's power over availability, told by mail to the person and counted on `/status`.
- **The admin log** is entries in the storage, signed: who did what to which account, invitation or mailbox (by identifier: never a mailbox's address or label), and when, kept 400 days and read by admins. Whoever writes to the table cannot add or change an entry, and can delete them: the log is a convenience for the admins, and the counts on `/status` stay the public trace. The log names accounts by identifier; an address is read from the record when the log is read, so the log keeps no address of an account that is gone. It is never in the enclave's log. The pointer from an address is what keeps two accounts from having one: the record names the new address before the pointer is written, and a failure in between leaves an account that both addresses find or only the old one, never one that cannot be found.
- **Notices by mail.** A person is told of a sign-in from a new device, a change in how the account is signed into, a change of address, a deletion asked or cancelled, and a block or an unblock. A notice goes out through SES like a sign-in message, with the same watch (ADR 0021), and holds no code, link or token: reading one lets nobody in. Its subject is fixed words. It repeats nothing a person typed, and nothing a browser said of itself: the notice of a new device names the browser from fixed words ("Firefox on Mac", or "not recognised"). Whoever got into an account must not be able to write the text of a message from Permaily to its person. What a notice tells of the account (that it exists, when it was used) is read by AWS and by the person's mail provider, as the sign-in message is. A notice can be kept from arriving by whoever can stop SES or the enclave's readings of it: then nothing is sent, and the action it tells of is done all the same.
- **Devices.** A browser that signs in keeps a cookie of its own (`__Host-permaily-device`, random, `HttpOnly`, `Secure`, `SameSite=Lax`), and the account keeps a hash of it made with the account's identifier, so the same browser is not told as new each time. The cookie stands for nothing and signs nobody in; it is not logged. Whoever writes to the table can cause one notice more, by deleting an entry, or one less, by putting back one that was dropped: nothing else. Whoever steals a session cookie usually has the device cookie too, so a notice of a new device is a sign of a new browser, not of every theft.
- **Guessing.** A code takes five tries and an address ten wrong codes a day; an address gets five messages an hour (ADR 0017). The counts are in each enclave's memory, where whoever writes to the table cannot set them back: with two enclaves each is twice what it says (ten tries on one code, one in a hundred thousand). A restart sets them back, and ends the sign-ins that were waiting with them: an enclave ends no sign-in made before it started, so a restart gives nobody more tries.
- **Telling who has an account.** Starting a sign-in answers the same, and as fast, for every address; the lookup and the message come after the answer.
- **Sessions.** The cookie is `__Host-permaily-session`, `Secure`, `HttpOnly`, `SameSite=Strict`, and a request that changes something must come from the app's own origin. Accepted: a session that was closed and is put back in the table works again, for whoever still holds its cookie, until its thirty days end (ADR 0017).
- **Invitations** are made with the operator's token, of which the image holds only the hash. Whoever holds it decides who may sign up. The ones not used yet are listed for the operator under random identifiers, never by their code, which is kept only as a hash; one that is revoked is deleted and signs nobody up.

## Mailboxes (F2 step 2, ADR 0026, built by its pull requests 0 to 4)

What step 2 adds, as built.

- **Who can read mail.** Only the account that owns the mailbox, through a session, inside the enclave. Each mailbox has its own data key, wrapped under the root secret in the mailbox's anchored record; every request reads the record, checks the owner, the state and what the account's standing allows, and unwraps the key for that request alone. The operator's token and the admin panel have no route that opens a message, and see of a mailbox only its readable record: owner, state, dates, retention, whether Google confirmed a Gmail account. Never the address, the label or the Gmail account, which are sealed under the mailbox key.
- **What the table shows.** That an account has mailboxes and how many, their states and dates, how many messages each holds and their sizes and times (as in F1), that a search entry, a claim and a mark exist per message. Not an address: the pointer from one is named by an HMAC under a key from the root secret, and holds only the mailbox's identifier.
- **What writing to the storage can do.** A pointer written by hand leads to nothing the record does not bear out; a record put back to before a disconnect or a pause is refused (`store.Anchored`); mailboxes and accounts' lists are strict records (ADR 0016): two commits of different digests at any version of one, which a delete marker in the anchors bucket makes possible, refuse it everywhere and for good, whatever is written above them, instead of one of the two being chosen (`store.ErrForked`); a copy of a commit replayed at its key changes nothing. Disconnecting, or an account's removal, always ends in a terminal commit: a record whose newest value was deleted is removed, so putting that value back later brings back nothing; a forked one cannot take a commit, refuses mail and is opened by nobody for the lock period (ten years), keeps its slot in its account's list, and its pointer is deleted. Removing an account always leaves its list closed, made closed if it had none, so no creation in flight lands after it; and delivery reads that list at `RCPT TO` and again before storing, so mail stops the moment the list is closed, lost or forked, even when writing a mailbox's own terminal commit failed (PR #91's review). A strict record whose newest value is gone is refused and shows on `/status` as `lost`, as a fork does. A cancelled or removed mailbox is never made again (`CreateNew`); a mailbox cannot be moved to another account (the record is signed, the key's wrap is bound to the mailbox). Still possible, as for every message since F1: deleting messages, or putting a deleted one back until the audit log exists (ADR 0019); deleting a `seen#` mark so a message resent is stored twice; putting back an older label or retention, which gives nothing the storage's owner lacks (ADR 0026, "What is anchored, and what is not"). None of it lets anyone read mail or move it to another account. Accounts, the providers' applications and the TLS identity are not strict: a fork there is noticed in `/status`, not prevented, as before (ADR 0016).
- **Delivery.** `250` is answered only when every accepted mailbox holds the message complete (raw object, search entry, item, mark, each acknowledged by the storage); a failure in between is `451`, and the retry writes the same items with the same identifier, received time and expiry, fixed by the first claim, so a crash neither loses a message nor stores it twice while its claim lives (seven days). Memory is taken as `DATA` arrives, never at `MAIL FROM` or from a declared `SIZE` (64 sessions, 128 MiB of `DATA`, 128 MiB of mail open for reading, per enclave; eight sessions per remote address at the host's proxy), every phase of a session has an absolute deadline, and a refused `DATA` closes the connection instead of reading the rest. Every command line is counted at the connection, `BDAT` chunks after the first included; a failed delivery counts as a refusal; the read deadline of a message's bytes is its stall, restarted by bytes and cut to the transaction's and the session's ends; `RSET` and its kind do not extend an idle session; a delivery's context ends with the session; parsing a message, and taking text out of its HTML with x/net/html's tokenizer, is linear in its size, bounded in what it keeps, and stopped by the delivery's deadline (PR #91's review); a sender can make the service refuse mail for a while, not exhaust the enclave or hold its memory without sending.
- **Disconnecting, exactly.** From the write of `disconnecting` (or the removal of a lost record), no new request of any enclave opens the mailbox and no new mail is accepted; a request or delivery already running writes nothing after its own deadline, a minute from its start (a context handed to the store, parsing and the response, not only the HTTP server's write timeout) or from the end of `DATA`. The sweep deletes the mail within minutes, and its last pass waits three minutes after the disconnect (the longest deadline, a minute of clock difference between enclaves, a minute of margin) for a write that read the record just before; anything written later is ciphertext under a key no record holds, and expires with its retention (at most 365 days). This is a refusal enforced by the code of public releases, not destruction of the key: a saved copy of the table from before the disconnect, together with the root secret, opens a saved copy of the mail. The root secret exists only inside enclaves of public releases and in records locked by their KMS keys (ADR 0013), and every release whose KMS key still exists can open it, so an old release with a flaw is part of that boundary until its key is deleted; the guarantees of mailboxes assume the releases before them no longer run against the data, and their keys are deleted once the release is verified. The commits of the record stay locked for ten years: its name (the mailbox identifier), versions, times, hashes and authentication codes, never a key or a value.
- **The F1 test mailbox.** Retired by the release that builds this (ADR 0026): nothing in it reads the test mailbox, its token is gone, and its address refuses mail. Mail it ever received was readable with the operator's token and by every release up to v0.11.0; nothing makes it unreadable in retrospect except deleting its items and retiring those releases' KMS keys.
- **Senders.** Anyone may send to an address they know; an address is a capability to send, never to read. Ordinary addresses are private; the mailbox that receives TLS reports has its address known to the operator and published in DNS, by design. Every refusal at `RCPT TO` is the same, so a sender learns only accept or refuse, and the address has 100 random bits. A Gmail confirmation counts as Google's word only when it has one `From`, one `To` and one `Subject`, comes from Gmail's forwarding address, carries a passing `google.com` signature over `From`, `To`, `Subject` and its whole body, is addressed to this mailbox, has the template's `Subject`, from which its code and requester are read (never from the body), and is Gmail's forwarding template naming this mailbox (Google signs other products' mail too); it then says that this Gmail account asked to forward here, nothing more. Until a real confirmation captured in staging passes those checks, none is marked confirmed. A genuine confirmation for another address, sent here, says nothing. Someone who learns an address can ask Gmail to forward their own account to it: the person sees that account's address before copying any code, and forwarding starts only when someone types the code into Gmail.
- **Access by standing.** A closing account reads, searches and downloads its mail and disconnects mailboxes; one that has not agreed to changed terms downloads its mail and disconnects mailboxes. The server decides it per route; the web app only shows what is allowed.
- **What reaches the browser.** The text, and the HTML only cleaned and inside a sandboxed frame ("Mail shown in the app", below); attachments and the raw message only as downloads (`application/octet-stream` or `message/rfc822`, `Content-Disposition: attachment`, `nosniff`, a sandbox CSP). Built for the person's routes (pull request 2): every answer has `nosniff`, errors are JSON with fixed words, a sender's filename is cleaned of paths, control and formatting characters (bidirectional overrides among them) and quotes before it reaches the header, and the text of a message whose only text is HTML is taken out inside the enclave by x/net/html's tokenizer, never built into a tree or shown as markup.
- **Reading is bounded.** A raw message is read from the bucket only after its bound (the item's size and the seal, 32 MiB at most) is taken from the 128 MiB of mail open for reading, and never past it: a size set by whoever writes to the table makes a read fail, not grow. A list page reads at most 500 items and a search page at most 2,000 entries, expired ones included; four searches run at once and an account asks thirty pages a minute, per enclave. Every request runs under a context that ends a minute after it started, handed to the service, the store and the response.
- **Logs.** No address, subject, sender, content, code, or account, mailbox or message identifier; `TestTheLogHoldsNothingOfAnyone` and `TestMailInEndToEnd` check it for the new paths and `TestMailEndToEnd` through the API, one redactor, `domain.Redacted`, takes identifiers of every kind (accounts, sessions, attempts, ceremonies, invitations, mailboxes, 32-hex message identifiers and longer digests) and addresses out of every error accounts, mailboxes and the API log, and logs a transport error (whose URL names records and objects) as its category and method only; and `/status` names a strict record's regression `mailbox`, marked `fork`, `unlocked` or `lost` where it is one.
- **The operator's power** over mailboxes is to pause and resume one, ten times in thirty days at most: it refuses mail and deletes nothing, is told to the person by mail, counted on `/status` and, through the panel, written in the admin log (each by the call that changed the mailbox: a pause of a paused mailbox leaves no trace and tells nobody), where an admin needs a fresh proof and acts on an admin's mailbox only as the super admin. The operator cannot disconnect a mailbox or delete mail. Finding the mailbox of an address (for a report of abuse) answers the readable record of that mailbox, with its account, or the same empty list for every address that leads to none; it takes one exact address a request, and needs no proof and writes no log entry, so an admin can ask it without a trace beyond the enclave's request logs. What bounds it as a way to test addresses is what bounds `RCPT TO`, which anyone can ask without a limit: an address is 100 random bits. It tells whose an address someone already knows is, which is what it is for. The answers of these routes, the admin log, `/status` and the enclave's log hold no mailbox address and no label, and errors of the mailboxes service are logged with nothing of what they say (tests in `internal/services/accounts` and `internal/httpapi`, ADR 0026's O2 and O5).

## Mail shown in the app (F2 step 2, ADR 0026, built by its pull request 5)

Mail is input from anyone on the internet, shown inside the app that holds the session. How it is shown is ADR 0026, "Showing a message's HTML", revised after an adversarial review on 2026-11-12; what it promises and what it rests on:

- **The promise, exactly.** A message cannot change the app's real interface or act in the app. It can draw a picture of anything inside its frame, a fake sign-in included, as any mail client's content can; around the frame the app always shows its own label ("Email content. Permaily never asks you to sign in or confirm anything inside a message."), the sender as the enclave parsed it, and the frame's border. Opening or reading a message makes no request the sender or anyone outside can see. Following a link is the person's act: it goes to the address the link page shows, and that site learns it was followed and when, and may identify the reader by the link itself, whatever the referrer policy. Browser services the person turns on (translation in Safari and Chrome, reader mode, extensions) see what the browser shows them; `translate="no"` in the frame is a courtesy, not a guarantee.
- **Nothing in a message runs.** First line, the browser: the frame's `sandbox` attribute without `allow-scripts`, `allow-same-origin`, `allow-forms` or `allow-top-navigation*`, and the same `sandbox` in the frame's own CSP with `default-src 'none'`, `form-action 'none'`, `base-uri 'none'`. Second line, the sanitiser in the enclave: an allowlist of elements, attributes, URL schemes and CSS on `golang.org/x/net/html`. Its output must parse back to itself in Go; that catches a tree x/net/html would itself read differently, and does not show what a browser builds, so the browser tests inspect each browser's DOM of the output. Each line is tested without the other.
- **Nothing remote is fetched because a message was opened.** First line, the frame's CSP: `img-src data:` and nothing else remote. Second, the sanitiser writes no address of the message into any attribute or CSS, and drops every `<link>`. The first line does not hold for one resource hint in one engine: Playwright's WebKit (1.65) opens a connection to the host of a `<link rel=preconnect>` of the raw message under the frame's CSP, and sends nothing through it (a known failure of run A, 2026-11-12); since the sanitiser drops every `<link>`, the document the frame is actually given has no hint, and run B shows no connection and no lookup in any engine. What the host of such a hint could learn, were the sanitiser to fail, is that the message was opened and from which network address. Remote images are never loaded or proxied, and there is no "Load images". Images that travel in the message are shown as `data:` URIs the sanitiser rebuilt, PNG, JPEG, GIF or WebP by their bytes, static, within limits of bytes and of pixels read from their headers without decoding; never SVG, never animated. Nothing is decoded or re-encoded in the enclave.
- **The message cannot reach the app.** The frame's origin is opaque: it cannot read the app's DOM, cookies or storage, and its requests are cross-site (`Sec-Fetch-Site: cross-site` in every engine tested). The second line is the server's: every request under `/api/` on the app's host whose `Sec-Fetch-Site` is present and is neither `same-origin` nor `none` is refused (403 `forbidden`, the same answer with a session cookie or without) before a session is looked up (`httpapi.RefuseCrossSite`, ADR 0026, "The API", "Another site"), so it holds whatever a browser does with cookies. That matters: Chromium 158 and Firefox 159 send no `SameSite=Strict` session cookie on the sandboxed document's requests, but Playwright's WebKit 27.2 does, on every one and on the link page's first navigation (observed on 2026-11-12, ADR 0026, "Corrected while building pull request 5"). What this does not cover is a browser that sends no Fetch Metadata (Safari before 16.4); there what holds is that nothing in the frame can make a request (the frame's CSP, and the sanitiser, which writes no URL of the message) or read an answer (opaque origin, no script), and that no GET changes state. Whether Safari itself sends the cookie is in the release gate. Only one route under `/api/` answers a request from another site, by design: the provider callback (its own state and browser binding); a later one is added to `httpapi.CrossSiteExceptions` with its reason or is refused. The device and provider cookies are `SameSite=Lax`, sent on a top-level navigation such as the link page's new tab, and neither authorises reading mail. It cannot navigate the app's window. The app's own GET routes (`/me`, sessions, passkeys, admin lists) return private data, but nothing in the frame can read an answer; no GET changes state, and one that must carries its own check (the provider callback's state).
- **Other sites cannot frame it** (`frame-ancestors` naming the app). When the browser sends Fetch Metadata the route answers only `Sec-Fetch-Dest: iframe` with `Sec-Fetch-Site: same-origin`; a browser that sends none (Safari before 16.4, a proxy that strips them) gets the document, and the CSP `sandbox`, which applies to a top-level document too, is what holds then. Also `Cross-Origin-Resource-Policy: same-origin`, `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. The app's own CSP gains only `frame-src 'self'`.
- **Links.** The frame never navigates itself: the sanitiser keeps only `http` and `https` links to a DNS name (no userinfo, no IP address in any spelling, which a browser and Go read differently) and rewrites each to a page of the app, opened in a new tab without opener or referrer. Its address carries a token bound to the destination by an HMAC under the mailbox's key, so a renumbered link answers `link_changed`, never another address. The link page parses the address with the browser's own `new URL()`, shows the host in ASCII as text, never as a link, warns when the link's text named another host, and contacts nothing until the person presses a button. `allow-popups` would also let a link reach custom protocols; the sanitiser keeping `http` and `https` only is what holds that, and every other scheme becomes text. A link cannot be made invisible or put over other content: the CSS that positions, layers or hides boxes is removed, each link carries its own style with `!important`, and so does every element that holds a link (`html` and `body` included), so that no ancestor hides, clips or shrinks it whatever a style sheet says; no rule of a style sheet keeps `display: none`.
- **The enclave's work is bounded while it happens.** Limits on the part, the tokens, an upper bound of the tree counted before it is built, the output as it is written, the CSS and the images; two renders at once per enclave with a bounded queue and a share per account; a deadline that stops the parse. A hostile message can make its own HTML fall back to text, not slow other people's.
- **What is stored.** Nothing: the HTML is sanitised on every read, the same on every enclave.
- **What a message costs the enclave.** A render is admitted once, before the raw message is read: a slot of the enclave and of the account, then the render's deadline of two seconds over the read, the MIME walk, the charset and the render; CSS is bounded while it is read (its tokens, its depth, every loop under the deadline), and an image is read only when its structure is unambiguous. A message cannot crash the enclave by its CSS (a sheet nested a million deep did, through Go's fatal stack overflow, until the review of pull request 5).
- **How it is tested.** The hostile corpus runs twice in Chromium, Firefox and WebKit (the frame alone, unsanitised; the sanitiser alone, with no CSP and no frame), against the real routes in `internal/mailhtml/frametest`, with the browsers on a Docker network that has no route out: their only proxy and their only DNS server are the test server's, which records every request and lookup and resolves no name, so a host a hostile message names can reach nothing outside (`tests/message-frame/run.sh`, in CI).
- **The back/forward cache.** `no-store` does not keep a page out of it everywhere; the message view hides a restored message until the session and the message are checked again.
- **Not covered.** A browser bug that breaks both the sandbox attribute and the CSP `sandbox` (a separate origin for message content would be the third line, ADR 0026 says when); a browser extension, which reads any page; what the person does once they follow a link. Whether each browser sends the session cookie on the frame's request, and the rest of the release gate in docs/acceptance.md, is shown in real browsers before release.

## Logging

Never log email content, email addresses, tokens, cookies, codes, presigned URLs or keys, in the enclave or on the host. Enclave logs leave through the untrusted host (vsock port 8003, printed by `permaily-host` into the instance's journal; ADR 0015), so they are public: a log line needs the same care as an API response. `TestMailEndToEnd` fails if a line logged while handling a message names an address, the subject, the body or the token.

## Review checklist

For every change that touches the enclave, the host, auth, storage or the build:

1. Does it add a way for the parent instance or a third party to read or alter user data?
2. Does it read configuration or code from outside the image at runtime?
3. Does it add an outbound destination? Is it on the allowlist and in this document?
4. Does it log anything from the list above?
5. Does every new rejection path have a negative test?
6. Does the image still build identically on x86_64 and arm64?
