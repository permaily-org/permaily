# Web app

The web app people use to decide what each app, agent or vendor can read from their mailbox.

## What it covers

| Section | Purpose |
| --- | --- |
| Overview | Your rules, then each connection and what it asks for, and anything waiting for a decision. It opens at `/` and is out of the sidebar for now |
| Connections | Each vendor, such as Claude, with its connections underneath, which can be hidden. A vendor's page opens on its overview: its connections and what applies to the vendor as a whole, such as the mailboxes it reaches and revoking all of its connections. A connection is one query on your mail, and opens in its own tab on that page. The tab shows the query and its output for each email, readable or as the exact YAML file, when it runs (when asked, on a schedule, or on new mail through a webhook), the queries it ran and what it has read. It also lists the person's rules that apply, and ticking them there changes the rules themselves. Find any connection, and revoke one or all of a vendor's |
| Rules | The person's own filters. Each one holds back the whole email, or takes out the parts picked, such as the subject, attachments or data described in words like a home address, before any query runs, for every connection or only the vendors and connections picked with a search, set here or from a connection's page. A rule matches mail by criteria people can name. Each criteria is a set of conditions that must all hold, such as "Message mentions my home address" and "Sender isn't amazon.es", and mail meets the rule when it meets any of its criteria. A condition is a field, an operator such as is, contains or isn't, and its values. New accounts get one suggested for sign-in and security mail |
| Activity | A receipt for every email that leaves, showing who got it, which parts and why |
| Accounts | Connected mailboxes and how Permaily reaches them |
| Settings | Profile, sign-in, notifications and your data, and deleting the account |
| Sign in, sign up | The only screens open without a session. Everything else sits behind one |
| Admin | For the service's admins only, and only while their account signs in with passkeys only: the accounts and what can be done to them, invitations, the providers' applications, the admins, and what admins did. Nobody else sees that it exists |

Apps and agents also send people to the consent screen. There they see the query the connection asks for, and a preview of exactly what it would get, before they allow it. The approved query caps what that connection can fetch. A vendor that wants something else asks for another connection, which is approved, listed and revoked on its own.

The proof that the running service matches the public code is a separate public page, not part of this app.

## Stack

React, TypeScript, Vite, Tailwind v4 and React Router. The app builds to static files that ship inside the measured enclave image, served on `app.permaily.com`. Fonts are bundled with the app, so it makes no requests to font services.

## Develop

The app lives in `web/` and uses bun.

```sh
cd web
bun install
bun run dev        # http://localhost:5173
bun run build      # type check, then build to dist/
bun run test       # type check the tests, then run them with coverage
bun run --cwd .. lint   # Biome, from the repo root
```

The app sits behind a session, so `bun run dev` needs something to sign in to. The dev server hands `/api` and `/dev` to an enclave in dev mode on the same machine, by default the one `go run -tags dev ./cmd/permaily-enclave -port 8443 -admin-token-sha256 <hex>` starts (see [internal/AGENTS.md](../internal/AGENTS.md)). Set `PERMAILY_DEV_APP` when the enclave uses another domain or port, for example `PERMAILY_DEV_APP=https://app.permaily.test:18443 bun run dev`. Make an invitation with `scripts/invite.sh`, sign up at `/sign-up`, and read the message, which is kept instead of sent, at `http://localhost:5173/dev/outbox`. Its link names the enclave's own address: open its path and fragment (`/sign-in#attempt=...`) on the dev server instead. Without an enclave the app says it cannot be reached. The proxy belongs to the dev server only and is not part of the build.

The production build is embedded in the enclave binary (`internal/webui`) and is part of PCR0, so it must stay reproducible. See [build.md](build.md).

Design tokens, typography and the design language are in [design.md](design.md).

## Tests

`bun run test` runs Vitest with Testing Library in jsdom (`web/vitest.config.ts`, `web/tests/`). The tests and their configuration live outside `web/src`, so `tsc -b` and `vite build` never see them, and `web/src/styles/index.css` tells Tailwind not to look in them for class names (`@source not`), which it would otherwise do with every file of the project: `dist/` is the same with or without them, byte for byte, and the same as the Nix build, whose sources do not include them.

- **The server is the one thing played.** `fetch` answers what each test says (`web/tests/helpers/server.ts`), and a request no test expected fails it. Everything else is the app's own code, started as `src/main.tsx` starts it: `open(address)` in `web/tests/helpers/app.tsx` loads every module fresh, reads and cleans the address, and renders the routes. Calling it again is a reload: memory is gone, and storage, the address and the history stay.
- **`web/tests/lib/`** tests each module of `src/lib` by itself. **`web/tests/components/`** and **`web/tests/pages/`** drive the screens as a person would, by role and label, and each file runs axe on what it renders (`expectAccessible`, WCAG 2.0 to 2.2, A and AA). jsdom draws nothing, so contrast is not measured there.
- **What the screens promise about secrets is asserted**: `expectNotKept` fails when a code, a token, an invitation or an address is in `localStorage`, `sessionStorage`, the address bar or the history's state.
- **A browser with passkeys** is made by a test (`web/tests/helpers/passkeys.ts`): `navigator.credentials` and `PublicKeyCredential` answer what the test says. No real authenticator is involved.
- **Coverage** has a threshold for each area that talks to the server (`src/lib`, `SessionGate.tsx`, `Confirm.tsx`, `src/pages/auth`, `src/pages/settings/signin` and `account`, `src/pages/admin`), set to the measured value rounded down. The screens on sample data have none.
- After React draws it still has work to do, such as moving focus. An assertion about that waits (`waitFor`), and one that says something did not happen lets the page finish first (`settle`).

## Signing in and the session

The screens talk to the accounts API of [ADR 0017](decisions/0017-accounts-and-sign-in.md) under `/api/v1/` on the app's own host (`web/src/lib/api.ts`): `POST auth/email/start`, `POST auth/email/look`, `POST auth/email/finish`, `GET me` and `POST auth/sign-out`. Requests are JSON and same origin, which is all the server lets through.

- **The session is the server's cookie and nothing else.** It is `HttpOnly`, so the app cannot read it: when the app opens it asks `GET /api/v1/me` (`web/src/lib/session.tsx`). Without a session every route leads to `/sign-in`, and after signing in the person lands where they were going. The destination travels in the router's state, never in the address. Someone who signs out on purpose is not taken back. When the server gives no answer the app says so and offers to try again; only the server saying so signs anyone out. Coming back to the tab asks again, so a link opened in another tab, or a session that ended there, shows here too.
- **Sign in and sign up are one flow** (`web/src/pages/auth/`): an address, and to sign up an invitation, then the six-digit code of the message. The invitation can be typed with or without dashes and is shown in groups of four, as the server writes it.
- **The link of the message** opens `/sign-in#attempt=<id>&token=<token>`. The fragment is read and taken out of the address bar before anything renders (`web/src/lib/arrival.ts`), also when the link is pasted over an open sign-in screen. The same goes for `?invitation=` on `/sign-up`.
- **Opening the link signs nobody in.** Someone can start a sign-in for their own account and send its link to another person, who would then be inside that account and connect their mailbox there. So the page first asks the server whose sign-in the link is (`POST auth/email/look`, which ends nothing), then who is signed in, and shows a question (`web/src/pages/auth/LinkConfirmation.tsx`): the address, that the link signs this browser in to its account, to go on only if the address is theirs and they asked for the message, and not to if someone sent them the link. The address shown is the server's answer, never anything read from the link. Only "Sign in" calls `finish`, with the token kept in the page's memory; "Don't sign in" forgets the link. Focus lands on the question, not on an action, and neither action is styled as the one to take.
  - A browser already signed in to the account of that address opens the app: nobody is signed in again and the link is forgotten unused.
  - A browser signed in to another account is told so, with both addresses: going on changes which account it is in ("Switch account"), and "Don't switch" leaves it where it was.
  - A link that was used, has ended or was cut short gets "That link no longer works" with the form to ask for another, unless the browser is signed in already, which just opens the app. The same when the link ends between the question and the answer; a browser that is in another account then is told it is still signed in there before the app opens.
  - No answer from the server keeps the link: "Permaily can't be reached" and Try again before the question, a message under the question after it.
  - Reloading while the question shows loses the link, which is nowhere but the page's memory: the ordinary sign-in screen follows. That is accepted, and the link is not stored to survive it.
- **The text after asking never says whether the address has an account**: the server answers the same either way, so the screen says "If this address can sign in, a message is on its way". It does not promise a code either: after too many wrong codes the message carries only the link, and the code field says to open the link instead.
- **Nothing typed or received here is stored.** No code, token or invitation goes to `localStorage`, `sessionStorage`, the address or a log. They live in the page's memory until they are used.
- **Every failure has words a person can act on** (`web/src/pages/auth/messages.ts`): an address the server cannot use, an invitation that is not valid or was used, a code that is wrong or has ended, too many attempts, no network, and anything else.
- **A blocked account is said after the proof, and only then** (`web/src/pages/auth/Blocked.tsx`). A sign-in that proved who it is and ends at an account the operator blocked is answered `account_blocked` (403), and nobody is signed in: by `auth/email/finish` (the code, or the link once the person said yes), `auth/passkey/finish`, `auth/recovery`, `auth/provider/confirm/finish`, and as the reason `account_blocked` in the fragment a provider comes back with. Every one of them leads to the first step of the sign-in screen, which says "That account is blocked", that nobody was signed in, and to write to `support@permaily.com`, a `mailto:` link: the app sends nothing itself, and the enclave's `Content-Security-Policy` needs nothing added, since it has no directive about where a link leads. The words are fixed and name neither a person nor a provider, since the reason can come from the address bar. It is not an error to try again: nothing is styled as one, no action repeats the try, the address that was typed is cleared, and the form stays for signing in to another account. A browser that was in another account when it said yes to the link is told on the screen that says it is still signed in there. A session of an account that gets blocked ends like any other, with 401.
- **Who is signed in and the way out** are in the account menu at the foot of the sidebar, and of the drawer on a phone: the address, and Sign out.

## Passkeys, recovery codes and sessions

The API is the one of [ADR 0017](decisions/0017-accounts-and-sign-in.md), under `/api/v1/` (`web/src/lib/api.ts`): `auth/passkey/start` and `finish`, `auth/recovery`, `passkeys` (with `start`, `finish` and `{id}`), `account/passkey-only`, `account/recovery-codes`, and `sessions`.

- **The browser's part** is in `web/src/lib/webauthn.ts`. The server's options go through `PublicKeyCredential.parseCreationOptionsFromJSON` or `parseRequestOptionsFromJSON`, and the answer comes from `toJSON()`, when the browser has them; when it has not, the same shapes are made by hand, with binary values as base64url without padding. A browser without WebAuthn, or a page that is not a secure context, is offered no passkey anywhere.
- **Signing in with a passkey** is one action on the sign-in screen and asks for no address: the browser shows the passkeys it has, and the passkey says which account it is for (`web/src/pages/auth/PasskeySignIn.tsx`). The prompt opens only when the person asks. A prompt the person closed is said calmly ("No passkey was used"), as a status and not as an error: a browser does not say whether it was closed, ran out of time or found no passkey. A refusal by the server says what may be so (the passkey was removed from its account, or the wait was too long) and what to do. Leaving the screen closes a prompt that is still open.
- **A recovery code** is for someone who lost every passkey of an account that signs in with passkeys only: "Use a recovery code" on the sign-in screen asks for the address and one code (`web/src/pages/auth/RecoveryStep.tsx`). Once it signs in, the app opens on Settings instead of where the person was going, and the Sign-in section says that the code is used up and invites them to add a passkey; the words take focus, are gone once a passkey is added, and are not kept across a reload. The code is typed with or without dashes, in any case, and is written in groups of four as it is typed (`web/src/lib/codes.ts`, shared with invitations). Every refusal by the server is one message, whether the code is wrong or used, the address has no account, the account takes no codes or too many were tried: it never says whether an address has an account. Only what cannot be a code at all (not 16 letters and digits) and no network read differently, and so does `account_blocked`, which the server answers only once the address and the code were right.
- **Settings, Sign-in** (`web/src/pages/settings/signin/`) reads `GET passkeys` and `GET sessions` when it opens and again after every change. When it cannot be read it says so and offers to try again; a session that ended leads to the sign-in screen.
  - **Passkeys**: each with its name, the day it was made and whether it is synced. "Add a passkey" asks for a name first, suggesting the browser and system ("Firefox on Mac", with a number when that is taken), then opens the browser's prompt. Should the server refuse the name, or not answer, the browser's answer is kept in the form's memory and sent again, so no second passkey is made. Rename is done in place. Remove asks first, and says that the passkey may stay listed on the device or in the password manager; for the last one it says that mail signs in afterwards. The last passkey of an account that signs in with passkeys only has no Remove: the row says why.
  - **"Passkey only"**: On or Off, with what it means behind the info icon and in the question that turning it on asks: a message to the address no longer signs in, recovery codes are the only other way in, and Permaily cannot let anyone in either. Without a passkey it is not offered, and the row says to add one. Turning it off asks too: mail signs in again and the codes stop working.
  - **Recovery codes** are shown once, when the server gives them, in a dialog that Escape and a click outside do not close (`RecoveryCodes.tsx`): ten numbered codes in monospace, "Copy all" (one a line), that they will not be shown again, and a box to tick ("I've kept these codes") before Done takes them away. Closing or reloading the tab meanwhile makes the browser ask first. The row shows how many are left. "Make new codes" asks first, saying how many codes stop working.
  - **The authenticator is told what the server has**, where the browser can (`forgetPasskey` and `acceptedPasskeys` in `web/src/lib/webauthn.ts`): `PublicKeyCredential.signalUnknownCredential` for a passkey the server refused when it was made and for one removed here, and `signalAllAcceptedCredentials` with the server's list when the section is first read, so a passkey removed from another device is no longer offered. A browser without them changes nothing, and a refusal is silent. A sign-in the server refused tells nothing: the wait may only have been too long. Neither does a failure of the server's own while a passkey is made, which leaves it unknown whether the passkey was kept.
  - **Sessions**: how many devices are signed in, and under Review each one as a browser and a system read from what it said of itself (`web/src/lib/device.ts`), "This browser" for the current one and when the others were last used, to the hour at best, which is all the server keeps. Another device is signed out from here; this one from the account menu.
- **Focus starts at the page's heading** when the page is new to the person: after a sign-in, after a deletion is cancelled, and on going to another page (`usePageFocus` in `web/src/components/SessionGate.tsx`, the one place that does it). The heading takes `tabindex="-1"` and shows no ring. When the app opens straight on a page, focus stays where the browser put it, and something on the page that took focus for itself keeps it.
- **Focus** follows what changed: a form's field when it opens and the action that opened it when it closes; the heading of a question or of the codes, never the action that answers it, so Enter answers nothing unread; the action that opened a dialog when it closes; the section when the row that had focus is gone. What changed without moving focus is said in a status for screen readers.
- **Nothing of this is stored.** A recovery code, a browser's answer and the server's name for a ceremony never go to `localStorage`, `sessionStorage`, the address or a log. Recovery codes are in the page's memory only while they are on screen, and "Copy all" puts them on the clipboard because the person asked.

## The account: name, address and deleting it

The API is the one of [ADR 0017](decisions/0017-accounts-and-sign-in.md) ("Settings, deleting an account and the operator's tool"), under `/api/v1/` (`web/src/lib/api.ts`): `PATCH account`, `POST account/address/start` and `finish`, `POST account/delete` and `POST account/delete/cancel`. All but `address/start` answer with the account, which `GET me` carries too with its `state` (`active` or `closing`) and, while closing, `closes_at` and `closing_by` (`person` or `operator`).

- **Profile** (`web/src/pages/settings/account/Profile.tsx`) shows the account as the session has it. The name is changed in place (Edit, or Add when there is none) and taken away with Remove or by saving an empty field. A name of more than 80 characters, or with a character the server does not keep (anything but letters, marks, digits, punctuation, symbols and the plain space), is said before it is sent, and the server has the last word (`invalid_name`). The contact address has Change, below. The language is shown with no action. The server's answer to a change goes to the session (`accountChanged`), so the account menu follows without a reload.
- **The contact address is changed with a code sent to the new one** (`web/src/pages/settings/account/ContactAddress.tsx`). Change opens a dialog that says, before anything is asked, that a message with a code goes to the new address and that nothing changes until the code is entered. An address without an `@`, and the one the account has already, are said before the server is asked. `POST account/address/start` sends the code, and no link; the dialog then shows the code step of signing in (`CodeForm` in `web/src/pages/auth/CodeStep.tsx`), so a wrong code, too many tries, a code whose time has passed, "Send another message" and "Use another address" read as they do there. `POST account/address/finish` answers with the account: it goes to the session (`accountChanged`), so the row, the account menu and the question that deleting asks all have the new address without a reload, and the row says that the address changed and that both the old and the new one were sent a notice. That is said once: not after a reload, and not once another change starts.
  - Every refusal has fixed words. `invalid_address` is said in the field and covers both an address Permaily cannot use and the account's own. `too_many_requests`, no network and anything else say that no message was sent. `address_in_use` comes only after the code: the dialog goes back to the address, with what was typed, and says it belongs to another account. `account_closing` and a session that ended say nothing there: the screen that says so follows.
  - The new address, the code and the server's name for the change live in the component's memory only: nothing goes to storage or to the address bar. The dialog cannot be closed while the code is on its way to the server.
- **Delete my account** (`web/src/pages/settings/account/DeleteAccount.tsx`) asks first, in a dialog that says what happens before the server hears anything: the account stops working at once and every other device is signed out; it is deleted for good in seven days, with the day; until then the person can sign in and cancel; after that nothing brings it back, and the address returns only with a new invitation, as a new account. To go on the person types the account's address, in any case. Nothing in the dialog is the default: focus opens on the question, Enter in the field only checks what was typed, and "Keep my account" comes before "Delete my account". Asking without the address says so in the field and asks nothing of the server.
- **An account that is closing shows one screen** (`web/src/pages/auth/AccountClosing.tsx`): that it is being deleted, the day and the time with its zone, in the person's own time zone, how many days are left by their calendar ("in 7 days", "tomorrow", "today"), and "Cancel the deletion" and "Sign out". When `closing_by` is `operator` it says "Permaily's operator asked for this account to be deleted on" that day instead of "It will be deleted for good on"; anything else, also no word from an older server, reads as the person. The person can cancel either. Settings has no words of its own for this: like every route it shows this screen while the account is closing. `RequireSession` (`web/src/components/SessionGate.tsx`) shows it in place of every route, the way every route leads to sign-in without a session, also after a reload and after signing in again. The address stays where the person was, so cancelling goes back to that page, and a screen reader is told the account works again.
- **Every way of finding out leads to that screen.** The answer to the request to delete; `GET me` when the app opens or the tab is come back to, which now also follows a name or a state changed in another tab; and any request refused with `account_closing` (409), such as a change made in a tab that was open before: `web/src/lib/api.ts` tells the session, which asks `GET me` again, and the part of the page that asked says nothing (`failed` of the session answers null, as it does for a session that ended).
- **When the day comes** the account is removed and its session stands for nothing: the next request is answered 401, and the sign-in screen follows, as for any session that ended. A closing screen left open asks the server once its own clock reaches the day; only the server's answer signs anyone out.
- **Why the person is on the sign-in screen is said once.** While the app sees a closing account it keeps the day it closes in `localStorage` (`permaily-closes-at`), and nothing else: no address, id or name (`web/src/lib/closing.ts`). When nobody is signed in and that day has passed, the sign-in screen says that an account used in this browser was deleted on that day, unless that was cancelled from another device, and forgets it. It names nobody, since whoever reads it may not be whose account it was. Cancelling the deletion, or seeing an account that works, forgets the day. What is in storage is shown only when it is a date this app wrote, and with storage unavailable nothing is said.
- **Dates** are written by `Intl` (`web/src/lib/closing.ts`), never by hand. The day in the dialog is this browser's clock plus seven days, as the day only; the closing screen shows the server's `closes_at`.
- **No answer from the server** is said where it was asked: under the name, in the dialog ("it isn't known whether your account is being deleted", since the request may have arrived) and on the closing screen, each with focus back on what can be tried again. Asking to delete twice changes nothing: the day stays.

## Google, GitHub, Meta and Microsoft

The API is the one of [ADR 0017](decisions/0017-accounts-and-sign-in.md) ("Google, GitHub, Meta and Microsoft"), under `/api/v1/` (`web/src/lib/api.ts`): `GET auth/providers`, `POST auth/provider/start`, `GET auth/provider/pending`, `POST auth/provider/confirm/start` and `finish`, and for the account that is signed in `GET providers`, `POST providers/start` and `DELETE providers/{provider}`.

- **Meta is called Facebook on screen.** The trip goes to Facebook's sign-in and Meta's own rules name the action "Continue with Facebook", so the button, the rows of Settings and every message say Facebook. The identifier stays `meta` in the API, in the code and in the rest of the documentation; `providerNames` in `web/src/lib/providers.ts` is the one place that maps an identifier to its name.
- **Only the providers that are on are offered**, in one fixed order (Google, GitHub, Meta, Microsoft), each as one action named in words: "Continue with Google". The sign-in and sign-up screens ask `GET auth/providers` when they open (`useProvidersOn` in `web/src/lib/providers.ts`); until the answer comes, when none comes and when none is on, nothing about providers is shown. No mark of a provider is drawn or loaded: the app loads nothing from other origins, and Google's, Microsoft's and Meta's rules for their marks ask for their own colours, which the design system does not have.
- **Starting** (`web/src/pages/auth/ProviderSignIn.tsx`) asks the server where to go, with where the person was going (`return_to`) and, on the sign-up screen, the invitation typed or arrived by link. With no invitation typed the provider is offered all the same, since the account may exist already; one that cannot be an invitation is said in its field before anything starts, and so is one the server refuses. The answer's `url` is the one place the app sends the browser to another site (`leaveFor`): only to an `https:` address the server answered, never to one read from the address bar. The one exception is `http://127.0.0.1`, where an enclave in dev mode plays the providers. While the browser leaves, every action of the group waits; coming back with the browser's Back button frees them again.
- **Coming back** is the server's redirect, and how it ended is in the fragment, which is read and taken out of the address bar before anything renders (`web/src/lib/arrival.ts`), like the sign-in link: `/sign-in#provider_confirm`, `/sign-in#provider_error=<reason>`, `/settings#provider_error=<reason>`, and `/settings#linked=<provider>`, which is the `return_to` Settings gives when it starts linking. Next to a reason the server adds `&provider=<id>` when it still knew the trip, so the words name the provider; the app takes only the four identifiers it knows, and says "that provider" or nothing for anything else. Meta's stray `#_=_` is taken out on any screen. A fragment proves nothing, since anyone can write an address: it is only ever turned into fixed words, and "linked" is said only when the server's own list agrees.
- **Each reason has words a person can act on, and none says more than its code** (`providerProblems` and `linkProblem` in `web/src/pages/auth/messages.ts`). `provider_failed` covers a provider that said no, an answer that came late or to another browser, and an account that takes no providers: the screen says it did not work, that nobody was signed in, and to try again or sign in another way. A reason the app does not know reads as that one. `account_blocked` reads as every blocked sign-in does (see "A blocked account" above), and to someone who turns out to be signed in to another account Settings says that nothing was linked and why. `invitation_needed` and `invalid_invitation` lead to the sign-up screen, where the invitation is typed, with the providers still offered. The words stay until the person tries something else, and are not kept across a reload.
- **Confirming an address** (`web/src/pages/auth/ProviderConfirm.tsx`) is where `#provider_confirm` leads: the provider said who the person is there, and not that an address is theirs (Meta never does; Microsoft does not for a work or school account). The screen says so, asks which address is theirs with the one the provider gave as the default, sends the message and asks for its code with the code step of signing in by mail (`CodeStep.tsx`, shared, also with changing the contact address), under its own words: the code links the provider to that address's account and signs in, and the link of the same message signs in without linking. Like signing in by mail it never says whether the address has an account: without one and without an invitation no message comes, and the screen says where to start again. Then the app opens where the person was going, which the server's answer says (`return_to`).
- **What waits is the server's**, tied to this browser by a cookie the app cannot read. So the screen asks `auth/provider/pending` when it opens, and again after a reload: that a confirmation was asked for rides in the router's state (`providerConfirm`), with where the person was going, and nothing else. When nothing waits any more (it was confirmed, its time passed, or the address was opened in another browser) the screen says so and offers to start again; when the server gives no answer it says that and offers to try again. "Sign in another way" leaves it for good.
- **Settings, Sign-in** (`web/src/pages/settings/signin/Providers.tsx`) has a row for each provider that is on or linked: "Linked since" and the day, with Unlink, or "Not linked", with Link. Linking leaves the app and comes back to Settings, where the result is said in the section and takes focus: that it is linked, or why nothing was. Unlink asks first, and says that Permaily may stay listed in the provider's account. A provider that is the only way left to sign in has no Unlink and says why (`last_way_in` from the server is said in the question too); a linked one that is off, or that signs nobody in because "passkey only" is on, says so in its row.
- **Someone who is signed in and arrives at `/sign-in` with a failure** lands in the Sign-in section of Settings, which says that nothing was linked (`providerArrivalSignedIn` in `web/src/lib/arrival.ts`, `GuestOnly` in `web/src/components/SessionGate.tsx`). Linking that ends without a trip the server still knows (the wait was too long, or the answer was opened twice) comes back there, for want of knowing it was started from Settings. A stale answer opened again with the Back button reads the same, which is true of it too. Someone who was told on the sign-in screen and then signed in is not followed, and `#provider_confirm` opened while signed in just shows the app.
- **An invitation crosses the trip.** The trip unloads the page, and with it the invitation that arrived by link or was typed, which `invitation_needed` then asks for again. So when the browser is about to leave for a provider and an invitation is in memory, it is written to `sessionStorage` (`permaily-invitation`, never `localStorage`), and it is read and taken out as soon as the app loads again, whatever the trip came to (`keepInvitation` and `takeArrival` in `web/src/lib/arrival.ts`). The sign-up screen then has it filled in. Coming back with the Back button forgets it, since the page still has it; only what can be an invitation is read; and with storage unavailable the person types it again. An invitation is a one-use code that names nobody.
- **Nothing of a provider's answer is stored.** The server keeps which provider and which account of it, and the app is told only that. No reason, address or state goes to `localStorage`, `sessionStorage`, the address or a log.

To try it by hand, serve the built app from the dev enclave as for passkeys below: the provider's cookie is `Secure` and `SameSite=Lax`, and the trip is a navigation between the app and the provider, which the Vite dev server does not carry. Dev mode plays the four providers itself and signs anyone in as `person@<provider>.example`, vouched for, without asking; Meta still asks for the address to be confirmed, with the code from `/dev/outbox`.

## Confirming it's you

A session alone does not make the changes that decide who gets into an account. The server answers `confirmation_needed` (403) to adding or removing a passkey, "passkey only", new recovery codes, linking or unlinking a provider, changing the contact address, deleting the account and every change of the admin panel, unless the person proved who they are in the last ten minutes. A sign-in counts as that proof for its first ten minutes. `GET me` says until when the proof holds (`session.confirmed_until`).

- **One dialog does it for every action** (`web/src/components/Confirm.tsx`, set up by `RequireSession` around every page). An action runs through `useConfirmed()`: when the server answers `confirmation_needed`, the dialog opens, and once the person confirmed, the action runs again, once, with what they typed. A second refusal is said in the action's own place ("Nothing changed: Permaily needs you to confirm it's you first. Try again."), and not asked again. Two actions that need it at once share one dialog.
- **What it says**: "Confirm it's you", and "This change decides who can get into your account, so Permaily asks you to show it's you again. It counts for the next 10 minutes." It asks `GET auth/confirm` for the ways the account has. A passkey comes first ("Use a passkey") when the account has one and the browser can use it; a code by mail is the other choice ("Get a code by email instead") or the only one ("Email me a code"), with "It goes to" and the account's address. With neither: "There's no way to confirm it's you in this browser. Try again in a browser that can use your passkeys." The proof made meanwhile, such as in another tab, asks nothing and runs the action.
- **The passkey prompt opens from the click itself.** The options are asked for (`auth/confirm/passkey/start`) as soon as the dialog shows the passkey, and again after each try, so "Use a passkey" calls the browser at once. Options older than two minutes, or a request for them that failed, are asked for again at the click, and the prompt then opens after that request. A prompt the person closed is a status ("No passkey was used. You can try again."); a browser that cannot use one says "This browser can't use a passkey here." and adds "Get a code by email instead." when the account can; a passkey the server refused says "That passkey didn't confirm it's you. Use one of this account's passkeys, then try again."; `passkey_needed` takes the passkey away ("This account has no passkey any more.").
- **The code by mail** is the code form of signing in (`CodeForm`), so a wrong code, too many tries, a code that ran out and "Send another message" read as they do there; "Back" returns to the ways. `passkey_required`, before or after the message, takes the code away: "This account confirms with a passkey, not with a code." A message that could not be sent says "No message was sent." and why.
- **Cancelling leaves everything as it was.** Cancel or Escape closes the dialog, the action does nothing and says nothing, and focus is back on what the person clicked. The dialog cannot be closed while an answer is on its way. A browser gives focus back only to what can take it, so an action that may ask to confirm is never `disabled` while it waits: it is `aria-disabled`, and a second click does nothing.
- **The session follows** the server's answer to a confirmation (`confirmed` in `web/src/lib/session.tsx`). The answer is given to the action once the dialog has closed, so a dialog the action opens keeps its focus.
- **Linking a provider** confirms before the page is left: the request for the provider's address is the one that needs the proof. **Adding a passkey** confirms before the browser's prompt, which then opens after the request for its options, as it did before.
- Nothing of it is stored: the code, the server's name for the confirmation and the browser's answer live in the dialog's memory.

## The admin panel

Some accounts are admins of the service: one super admin, and the admins it makes. `GET me` says so (`account.admin`, `super` or `admin`), also while the account is not passkey only, when the panel does not work, and says whether it is passkey only (`account.passkey_only`). So does every other answer that is the person's own account. The API is under `/api/v1/admin/` (`web/src/lib/api.ts`).

- **Hidden from everyone else.** The sidebar has "Admin" only for an admin. Every route under `/admin` leads anyone else where an unknown route leads, which is `/` (the app has no not-found page), before anything asks the server (`AdminGate` in `web/src/pages/admin/AdminLayout.tsx`). A request answered `not_found` asks `GET me` again, so someone who stopped being an admin loses the panel.
- **Passkey only first.** While `me` says the account is not passkey only, the panel shows one screen and asks the server nothing: "Turn on passkey only to use the admin panel", that the panel works only for accounts that sign in with passkeys only, that while a message can sign the admin in anyone who reads their mail could act as an admin, and "Go to sign-in settings", which opens Settings with focus on the Sign-in section. Turning it on or off in Settings tells the session at once, so the panel opens or shuts without a reload, and a change made in another tab shows when the tab is come back to. The server has the last word: a request answered `passkey_only_needed` shows that screen too, and asks `GET me` again.
- **The numbers** sit at the top of every page: accounts, active, being deleted, blocked, unused invitations. When the server says they are incomplete: "Some accounts couldn't be read, so each number is at least what it shows." They are read again after a change.
- **Accounts**: every account, the oldest first, with its address (the link to its page), its name or "No name", its state in words ("Active", "Blocked", "Being deleted", "Blocked, being deleted") and the day it was made; "Show more accounts" pages; accounts the server could not read are counted under the list. "Find an account" takes the exact address and shows the account or "No account has the address" and the address. The address typed stays in the page's memory: never in the address bar or storage.
- **One account** shows its address as the heading, then the name, the state with the day it was blocked and the day it is removed and who asked, when it was made, when its address was checked, the language, passkeys and passkey only, the providers linked, how many devices are signed in, whether it is an admin and its id. "The admin panel can't change an account's address or how it signs in, and can't sign in as its owner." The actions are Block or Unblock, Delete or Cancel the deletion, and Sign out every device (when one is signed in). Each asks first with the account's address and one sentence: block, "Every device signed in to it is signed out, and nobody can sign in to it until it is unblocked."; unblock, "It can be signed in to again. Its devices stay signed out until the person signs in."; delete, "It stops working now and is removed for good in 7 days, on" the day, ". Until then the person can sign in and cancel, unless it is blocked."; cancel, "The account is kept, and works as it did before."; sign out, "Every device signed in to it is signed out. The person can sign in again." A deletion the person asked for has no cancel: "The person asked for this deletion: only they can cancel it." The admin's own account offers nothing ("This is your own account. Change it in Settings."), and neither does another admin's to an admin who is not the super admin ("Only the super admin can act on an admin's account."). A refusal for either reason reads the account again.
- **Invitations**: "How many" (1 to 20, said before asking: "Make 1 to 20 at a time."), then the codes in a dialog that only Done closes, with "These codes won't be shown again.", "Copy all" and the day they stop working; the browser asks before the tab is closed meanwhile. The list shows the unused ones by the time they were made and the day they stop working, with Revoke ("Whoever has its code can no longer make an account with it."). An invitation that was used, revoked or never made is said so, and the list is read again.
- **Providers**: each of the four, "Set up" with its client ID or "Not set up", Meta as Facebook. The super admin sets one up or changes it (client ID, and the secret in a password field, emptied the moment the form is sent, whatever the answer; "Permaily couldn't use that client ID and secret. Check them, then enter the secret again.") and removes one ("Nobody can sign in with" the provider ", or link it, until it is set up again."). An admin sees the list and "Only the super admin can set up providers."
- **Admins**: each with their address, name and since when. The super admin removes one who is not the super admin ("They keep their account, and can no longer use the admin panel.") and adds one by finding an account by its address ("They can block, delete and sign out accounts and make invitations, while their own account signs in with passkeys only."); an account that is an admin already says so. The server answers either change with the admins as they are after it, which the list shows without asking again. An admin sees the list and "Only the super admin can add or remove admins."
- **Activity**: what admins did, the newest first, with the time, the kind in words, the account (a link while it exists, "An account that is gone" and its id after), the invitation's identifier when it was about one ("Invitation inv_..."), and the admin; a kind the app does not know is shown as it is, in monospace. The server writes one entry for each invitation made, so making several at once reads as several "Made an invitation", each with its own identifier, and several entries can share a time. "Show older activity" pages.
- **Every list** says when it loads, when it is empty and when it could not load, with Try again; every refusal of the contract has its own words (`adminMessage` in `web/src/pages/admin/shared.tsx`, and `messageFor`). Every change goes through the confirmation above.
- **The layout and the words are a first pass for the designer to review**: the screens use the components of Settings (`SettingRow`, `SectionHeading`, `Dialog`, `Field`) and nothing of their own.

`Dialog` (`web/src/components/ui/Dialog.tsx`) takes `dismissable={false}` for a dialog that must be answered, and gives focus to the element marked `data-dialog-focus` when it opens.

To try passkeys by hand, the page's host must be the relying party and its certificate must be one the browser accepts, which the dev server on `localhost` is not. Serve the built app from the dev enclave on its own name (`-domain permaily.test -port 18443`, with `web/dist` copied to `internal/webui/dist` before building) and start Chromium with `--host-resolver-rules="MAP *.permaily.test 127.0.0.1"` and `--ignore-certificate-errors-spki-list=<base64 of the SHA-256 of the certificate's public key>`: Chromium refuses WebAuthn on a page with a certificate error, and with that flag the certificate counts as valid. A virtual authenticator from the DevTools protocol (`WebAuthn.enable`, `WebAuthn.addVirtualAuthenticator` with resident keys and user verification) stands in for a device.

The build keeps every asset as a file of its own (`assetsInlineLimit: 0` in `web/vite.config.ts`): a font put in the stylesheet as a `data:` URL is refused by the enclave's `Content-Security-Policy`.
