# internal/AGENTS.md: enclave service and host proxy

Go packages behind `cmd/permaily-enclave` (trusted, runs in the enclave) and `cmd/permaily-host` (untrusted, runs on the parent EC2 instance). Architecture: [../docs/architecture.md](../docs/architecture.md). Trust boundaries: [../docs/threat-model.md](../docs/threat-model.md).

| Package | Role |
|---|---|
| `enclave` | vsock listener, egress HTTP client through the host's CONNECT proxy (the parent instance is vsock CID 3), and the log sink that sends log lines to the host |
| `tlsacme` | one multi-SAN certificate via ACME TLS-ALPN-01; the certificate key and the ACME account key are kept sealed under the root secret (`Sealed`) and reused across restarts; with two enclaves one claims the order in the identity and the other serves what it stores, and the challenge of an open order is kept sealed in the storage so either answers the CA (ADR 0024) |
| `nsm`, `nsm/fakensm` | real NSM attester; fake attester for dev mode and tests |
| `contracts` | types and error codes that cross the boundary (API, MCP, command line, web app); imports nothing of the service (F2) |
| `domain` | rules that need only their arguments: session lifetimes, what an address or an invitation looks like; imports only `contracts` (F2) |
| `domain/mail` | a message as a list of blocks, and its two parts written from them: the plain text, and the HTML from the templates in `templates/`, which `packages/mail` writes and which are committed (ADR 0025) |
| `services/accounts` | accounts and sign-in (ADR 0017): invitations, sign-in by email, passkeys, "passkey only" and recovery codes, sessions, changing the contact address, what the operator may do to an account (`operator.go`), the notices by mail (`notices.go`, `devices.go`), confirming again before a sensitive change (`confirm.go`), the admins, their log and counts (`admins.go`, ADR 0022), and the sign-ins in progress, sealed in the storage so that any enclave ends them (`pending.go`); knows nothing of HTTP (F2) |
| `webauthn`, `webauthn/webauthntest` | the checks of what a browser answers when a passkey is made and used (ES256, EdDSA, RS256; no attestation trusted), written here so no WebAuthn library is in the image, and compared with one in `tests/webauthn-differential`; a software authenticator for tests and dev mode (F2) |
| `idp`, `idp/idptest` | the client side of signing in with Google, GitHub, Meta and Microsoft: the authorization code with PKCE, the check of an ID token against the provider's keys, and who holds an access token; written here so no OAuth or JWT library is in the image, and compared with one in `tests/idp-differential`; fake providers for tests and dev mode (F2) |
| `sesmail` | the service's own mail through SES (`Sender`), and the watch that reads whether SES would give someone else a copy of it and keeps every state seen, for `/status` (ADR 0021) |
| `httpapi` | `/attestation`, `/status` (the key that locks the root secret, the TLS identity), `/version`, mailbox API, `/v1/admin/handoff`, `/v1/admin/invitations` (made, listed, revoked), `/v1/admin/accounts` (the operator sees accounts, blocks, asks to delete and signs devices out, and changes no address and no way to sign in), `admin` on `/status` (how many of each kind of thing the operator and the admins did), and the web app's own API under `/api/v1/` (cookie, same origin), with the admin panel under `/api/v1/admin/` ; `session.go` is the session and same-origin helper the web app's API shares (`Sessions`, `withSession`, `fromTheApp`, `setSession`); `mailboxes.go` the person's routes under `/api/v1/mailboxes` (`MailboxesAPI`: the request's deadline, the read budget, search's limits, downloads that are never documents) |
| `router` | dispatch by Host (app, api, mcp, inbox) and security headers |
| `webui` | embeds the SPA build (`dist/` is copied in at build time) |
| `hostproxy` | TCP to vsock forwarding, allowlisted CONNECT proxy and printing of the enclave's log lines (host side) |
| `buildinfo` | commit set via ldflags |
| `smtpd` | MX on port 25 (vsock), STARTTLS with the enclave certificate, refuses mail without TLS (F1) |
| `inbox` | mailbox: parse, Gmail confirmation codes, seal, store, serve (F1); `read.go` and `search.go` are the inbox's `Reader` of ADR 0026 (pull request 2): list and search pages bounded by items read, one message's text (its text/plain part, or text the enclave takes out of its HTML with x/net/html's tokenizer), attachments and the raw message read under the read budget (`WithReadBudget`) and bounded, deleting |
| `services/mailboxes`, `services/mailboxes/mailboxestest` | mailboxes per account (ADR 0026): for now the seam only (the interfaces it needs and gives, its limits, `Access` by an account's standing, its errors) and fakes of each side for tests; the service comes with ADR 0026's pull request 1, and `inbox/box.go` and `inbox/inboxtest` are the stored format of a message and a stand-in that writes it |
| `msgauth` | DKIM verification with DNS-over-HTTPS (F1) |
| `keys` | keys for one purpose derived from the root secret (`Derive`); the root secret (`Root`): created in an enclave, stored one record per image under that image's KMS key, accepted only from an enclave of the same image or of a public release, handed only to a newer public release (ADR 0013); data keys wrapped under it; KMS with attestation (Recipient, CMS); the reader that watches the policy and grants of the image's key and keeps every state seen, for `/status`; local keys for dev |
| `envelope` | AES-256-GCM with key commitment and context binding (F1); `Sign` for values that stay readable outside the enclave and only an enclave can make (F2); `SealText` for sealed values kept as text, in entries |
| `store` | DynamoDB and S3 store for mailboxes, messages, the enclave's own records (sealed, or readable and signed) and entries (small versioned rows that can expire: sessions, invitations); `Anchored`, which refuses an earlier copy of a record and writes one only if no other enclave changed it since it was read; in-memory store for dev and tests. `strict.go`, `scan.go` and `parts.go` declare what ADR 0026's pull request 0 builds (strict records, the descending scan, a message's parts); nothing implements them yet |

## Rules

- `cmd/permaily-enclave` with `-tags dev` runs locally over TCP with a self-signed certificate and `fakensm`; never import `fakensm` from non-dev enclave code.
- No CGO, no files read at runtime inside the enclave; CA roots come from `x509roots/fallback`.
- New outbound destinations must be added to the host allowlist (`cmd/permaily-host`) and documented in [../docs/threat-model.md](../docs/threat-model.md).
- With two enclaves, only the enclave whose claim is in the stored identity asks the CA (`ensure`); a change of the identity is written with `Write` at the `Version` read, never with a plain write. A challenge goes to the storage before the CA is told to check (`publish`). Never adopt a stored identity with another key.
- The TLS key is created once and reused across restarts and upgrades; `/attestation` binds `sha256(SPKI)` as user data. It leaves the enclave only sealed. When the sealed record cannot be loaded the enclave waits: never fall back to a fresh key, which would break the CAA records and the certificate history that verifiers check.
- Log lines leave the enclave (ADR 0015). Before adding one, read it as if it were public; never put an address, a subject, content, a token or a key in it, and keep `TestMailEndToEnd`'s log check passing.
- Nothing outside the enclave sees plaintext mail: seal with `envelope` under the mailbox data key before calling `store`; never log addresses, subjects or content. A mailbox is made with `PutMailbox` at version 0 (only creates; on `ErrExists` use the one stored) and changed at the version read (on `ErrConflict` read and change again).
- Every KMS response is checked against the key that was asked (`keys.ErrKeyMismatch`), every key must be in the pinned account and region, and no key is used before `kmspolicy.Sealed` accepts it. Never use KMS without the Recipient parameter.
- A record whose going back to an earlier copy would matter (the TLS identity, later permissions) is stored through `store.Anchored`, never straight into the table. Decide for each what `store.ErrLost` means: made again, or refused (ADR 0016).
- An anchored record that is read, edited and written back is read with `GetRecordAt` and written with `PutRecordAt`, never with `PutRecord`: two enclaves may run at once, and `PutRecord` writes over what the other just did. On `store.ErrChanged` read again and decide again, a bounded number of times, then fail. A lock in memory is no substitute: it holds in one enclave. The same goes for entries: `PutEntry` at the version read, `DeleteEntryAt` for an entry that is deleted because of what it says, and for a pointer that is replaced because of whom it leads to, `DeleteEntryAt` then `PutEntry` at version 0 (`repoint`).
- Layers (F2): `contracts` ← `domain` ← `services` ← adapters. A rule that needs no storage goes in `domain`; an adapter holds no rule. `depguard` fails a service that imports `net/http`, an adapter or the AWS SDK.
- Whoever runs the storage must not get into an account by writing to the table. An account's record is signed (`envelope.Sign`) and read through `store.Anchored`; a session or an invitation is an entry signed with its partition and key, kept by the hash of its secret; how long one lasts is read from what was signed, never from the entry's own expiry. What must not be set back at all (the count of wrong sign-in codes, and every other limit) lives only in the enclave's memory.
- An account that cannot be read (a record that does not verify, or whose committed version is gone) is an error, never "no such account": a sign-up would replace it.
- The answer to starting a sign-in is the same, and as fast, whether the address has an account or not.
- Passkeys, the "passkey only" switch and the hashes of recovery codes are part of the account's record, and that record changes only through `change` (or `rewrite`) in `services/accounts`. The edit given to it can run more than once, when another enclave changed the record in between: it decides everything from the record it is given, sets what it hands back on every run, and writes nothing else that it could not write twice. A passkey ceremony is a sealed entry that works once (`begin`, `end`), and every way it can fail is the same error. Never trust an attestation, and never accept an origin or a relying party that is not the app's.
- A provider's account leads to an account by its subject, never by its address, and an address is believed only where `idp` says the provider vouches for it. A provider's answer is ended only for the browser that started it, and the browser is then sent only to a path of the app (`domain.AppPath`). A provider's secret never leaves the enclave once given, and a new destination for a provider goes in `idp.Hosts()` and in the host's allowlist together (`TestEgressAllowsTheProviders`).
- An account is removed only through `RemoveRecord` of `store.Anchored`, which commits that it is gone: deleting its items by hand lets an earlier copy be read as lost, not as gone. The lists of accounts and of what is closing are entries that prove nothing: read the signed record before showing or removing anything they name. Dev mode can move the service's clock; the enclave build cannot.
- The link of a sign-in message never signs in by being opened: the page looks first (`LookEmail`) and asks the person. Keep `finish` behind that question in every client.
- Account, session and sign-in identifiers stay out of logs too: `httpapi` strips them from the errors it logs, and a mail system's errors, which carry addresses, are never logged.
- **Two enclaves (from 2026-11-12).** Any request may land on either of two enclaves behind one address (ADR 0017, "Two enclaves at once"). Where each kind of state goes:
  - What decides who gets into an account (its address, its ways in, its state, its role, the count of its sign-outs) is in the account's record: signed, anchored, changed only with `GetRecordAt` and `PutRecordAt` through `change`, `rewrite` or `operate`. The enclave's own secrets (the providers' applications) are a sealed anchored record changed the same way.
  - What a later request reads and the operator may see (a session, an invitation, a pointer, a list, a device) is an entry signed with where it is stored. What a later request reads and nobody outside may see (a sign-in in progress: a code's hash, a token, a challenge, a verifier) is an entry sealed with `stash` (`envelope.SealText`), ended once with `claim` or `match`.
  - Memory holds only caches (read again after a stated time, as `appsFresh`) and limits (counts each enclave keeps apart, at most N times the limit with N enclaves). Never a map of the `Service` that a later request needs: that request may land on the other enclave.
  - A flow that starts in one request and ends in another has a test that starts it through one enclave and ends it through the other (`w.enclave()`), and one where the same thing is ended through both at once.
  - An enclave ends nothing that was started before it started (`since`): its memory of tries is gone, and a restart must not give tries back.
  - A pointer or a list entry is replaced only as it was read (`repoint`, `DeleteEntryAt`), never by writing at the version read: versions repeat once an entry is deleted and made again. Each write of one carries a value of its own (`loginDoc.Write`).
  - What `/status` says is the enclave's that answered; do not add to it anything a person would read as the whole deployment's.
  `enclaves_test.go` and `inprogress_test.go` have a test for each thing that must hold across two enclaves.
- A change that decides who gets into an account (a way in, "passkey only", recovery codes, the contact address, deleting, and every admin change) checks `confirmed` first and does nothing without a fresh proof (ADR 0022). The time of the proof is in the session's signed entry (`confirmed_at`); `confirm` is the only thing that writes it, at the version read. An attempt or a ceremony that confirms belongs to one session (`confirmFor`) and works for nothing else.
- Making an account takes the agreement to the terms in force (`domain.TermsVersion`, compiled in; the site's `TERMS_VERSION` and the web app's must be the same): a sign-up with an invitation names the version (`terms`), the agreement travels sealed with the sign-in in progress (`Agreed` in `attemptDoc`, `tripDoc` and `unconfirmedDoc`), never in memory, and `signUp` checks it again when the account is made, through whichever enclave. The record keeps `terms: {version, at}`; `change` refuses everything to an account that did not agree to the version in force (`ErrTermsChanged`), and so do the starts of passkeys, a new address, linking a provider and the admin panel. Only agreeing (`AgreeTerms`) and what a sign-in writes (`link`) go through `changeAgreed` without it; deleting, cancelling, confirming, signing out and reading stay open (ADR 0017).
- An admin's role is read from the account's record (`role`): the super admin from its address and `Config.SuperAdmin`, compiled into the image, never stored; the others from `admin` in the record, set only by `makeAdmin` and `removeAdmin` through `operate`. Nothing else writes it. The admin panel's routes are given `*accounts.Admin` as `httpapi.AdminOperator` and nothing else, and answer `not_found` to anyone who is not an admin.
- The operator's routes are given `httpapi.OperatorService` and nothing else. Never add to it a method that changes a contact address or a way to sign in, turns "passkey only" off or signs someone in, and never one that takes more than an identifier, an address to look up, a place in a list or a count: it would be a way into every account (ADR 0017). `TestTheOperatorsRoutesCannotChangeAnAddressOrAWayIn` names the methods.
- Whatever the operator or an admin does through the enclave is counted with `acted`, by a kind that is also in `attestation.AdminActions`, and logged by its kind alone. Never an account, an address or an identifier: `/status` and the logs are public. What an admin does is also written with `logged` in the admin log, which is in the storage and names accounts by identifier only.
- Every way of signing in ends in `enter` (`devices.go`), after the proof and never before: it refuses a blocked account, makes the session (confirmed from that moment) and tells of a new device. That an account is blocked is said nowhere else. Whatever a person changes of their account goes through `change`, which refuses a blocked one; the operator's own changes go through `operate`. Signing every device out is `signOut` on the record, in the same change as what causes it (a deletion asked, a block, the operator or an admin signing devices out): a session stands only while it carries the count of sign-outs the record has (`stands`), so one written through another enclave in that moment stands for nothing. Deleting session entries is only cleaning up.
- A contact address changes only through `move` (`address.go`): the record names the new address, then its pointer is written, then the record says it is done, then the old pointer goes as it was read. Keep the order, and keep writing the pointer again when it already leads to the account. A provider account is linked the same way (`link`): the record says it is being linked, the pointer is written, the record lists it; an unlink writes the record first and deletes the pointer after, only if the record no longer holds it (`unclaim`). An attempt belongs to what it was started for (`match`): a sign-in's changes no address, and an address's signs nobody in.
- A message is written as blocks of `domain/mail` and made with `compose`, which writes its text and its HTML from them: never a `Mail` with words of its own. A new message goes in `sampleMails` (`mail_samples_test.go`) in every variant; `go test ./internal/services/accounts -run 'TestEveryMessageReadsAsItsGoldenText|TestThePreviewShowsWhatTheServiceSends' -update` writes its golden text and its fixture, and the checks of the HTML run on it. Never edit `domain/mail/templates` by hand: change `packages/mail` and run `bun run build` there.
- A notice by mail is sent with `notify`, after the change is stored, and never fails or holds it for more than `noticeTimeout`. Its subject and text are fixed words: no code, link, token or identifier, and nothing a person typed (a name, an address). Not even what the browser said of itself: a notice names it from fixed words with `domain.DeviceName`, whose tables are the web app's (`web/src/lib/device.ts`). Log that a notice of a kind was not sent, and nothing of the error.
- The device cookie (`__Host-permaily-device`) stands for nothing: never take it for a session, never log it, and keep of it only the hash made with the account's identifier.
- Mail the enclave sends goes out only through `sesmail.Sender` with its `Watch` set: no message leaves while SES says a configuration set applies to it, or does not say. Never name a configuration set in a request, and never send through another path. An error from SES is passed on and logged only as its status and its kind, never its text, which names addresses.
- The root secret never leaves the enclave in the clear, not even to KMS. Never create one when a record cannot be read or opened: an image without its record waits. Never accept a root record, or hand the secret over, on anything but the checks in `keys.Root`; who asks is not one of them.
- Which builds are releases (repository, workflow, ref) and Sigstore's trust root are compiled into the image (`deploy/enclave.json`, `pkg/provenance`). A change to either changes who can receive the root secret: it needs an ADR. A running enclave takes a newer trust root only through `provenance.TrustRoot.Update`, which never changes who issues signing certificates; keep it that way, and keep nothing of it across a restart.

## Commands

```sh
go test ./...
go run -tags dev ./cmd/permaily-enclave -port 8443   # needs web/dist copied to internal/webui/dist for the SPA
go run -tags dev ./cmd/permaily-enclave -port 8443 -mailbox-id dev -mailbox-address u-dev@inbox.permaily.com -mailbox-token-sha256 <hex>   # SMTP on :2525
go test -tags dev ./cmd/permaily-enclave             # whole service end to end
# Dev mode has accounts on: make an invitation with scripts/invite.sh (PERMAILY_API, PERMAILY_ADMIN_TOKEN, -admin-token-sha256),
# and read the sign-in message, which is kept instead of sent, at https://app.<domain>:8443/dev/outbox (the notices are there too).
# scripts/accounts.sh finds, blocks, unblocks, deletes and signs out; scripts/invite.sh list and revoke.
# Dev mode can change the version of the terms in force: POST /dev/terms?version=<v> on the app's host (without one, the compiled version again); accounts that agreed to another are then asked again.
# The super admin of dev mode is admin@permaily.test (-super-admin); sign it up, add a passkey and turn "passkey only" on to use /api/v1/admin/. Without DNS for the dev names,
# point curl at the enclave: CURL_HOME=<dir with a .curlrc of 'connect-to = "api.<domain>:8443:127.0.0.1:8443"' and 'insecure'>
```
